## 摘要
各行各业的企业用户日益依赖 AI 智能体通过自然语言查询其数据。然而，构建可靠的数据智能体仍然面临挑战，因为现实世界的数据通常分散在多个异构数据库系统中，存在不一致的引用，且信息往往隐藏在非结构化文本中。现有的基准测试仅解决了该问题的部分环节——例如，将自然语言问题转换为 SQL 查询，或针对上下文中提供的小型表格回答问题——但并未评估跨多个数据库系统进行数据集成、转换和分析的完整流程。为了填补这一空白，我们提出了数据智能体基准测试（Data Agent Benchmark, DAB），该基准基于对六个行业企业数据智能体工作负载的形成性研究。DAB 包含涉及 12 个数据集、9 个领域和 4 个数据库管理系统的 54 个查询。在 DAB 上，表现最好的前沿模型（Gemini-1.5-Pro）仅达到了 38% 的 pass@1 准确率。我们对五个前沿大语言模型（LLM）进行了基准测试，分析了它们的失败模式，并为未来的数据智能体开发总结了核心启示。我们的基准测试和实验代码已发布在 github.com/ucbepic/DataAgentBench。

## Abstract
Users across enterprises increasingly rely on AI agents to query their data through natural language. However, building reliable data agents remains difficult because real-world data is often fragmented across multiple heterogeneous database systems, with inconsistent references and information buried in unstructured text. Existing benchmarks only tackle individual pieces of this problem -- e.g., translating natural-language questions into SQL queries, answering questions over small tables provided in context -- but do not evaluate the full pipeline of integrating, transforming, and analyzing data across multiple database systems. To fill this gap, we present the Data Agent Benchmark (DAB), grounded in a formative study of enterprise data agent workloads across six industries. DAB comprises 54 queries across 12 datasets, 9 domains, and 4 database management systems. On DAB, the best frontier model (Gemini-3-Pro) achieves only 38% pass@1 accuracy. We benchmark five frontier LLMs, analyze their failure modes, and distill takeaways for future data agent development. Our benchmark and experiment code are published at github.com/ucbepic/DataAgentBench.

**研究动机：** 现实中的企业数据通常是**碎片化**的（存储在异构系统中，如 PostgreSQL 和 MongoDB）、**脏乱**的（关联键格式不一致）且**非结构化**的（关键信息埋藏在文本字段中）。论文旨在填补这一空白，提出了一个端到端的基准测试 **DAB**，用于评估智能体在集成、转换和分析跨多个异构数据库系统数据时的综合能力。

#### 2. 论文提出的方法论
论文的方法论建立在对六个行业（科技、金融、医疗等）企业工作负载的**形成性研究**之上，总结出真实数据查询的四个核心挑战：
*   **核心思想：** 通过系统性地“扰动”开源数据集，模拟企业环境中的复杂性，并要求智能体在 ReAct（推理+行动）循环中解决问题。
*   **关键技术细节：**
    *   **四项属性诱导：** (i) **多数据库集成**（跨不同 SQL 方言和 NoSQL）；(ii) **格式错误的关联键**（如添加前缀、空格或缩写）；(iii) **非结构化文本转换**（将分类或数值信息嵌入长文本，需正则或语义提取）；(iv) **领域知识**（需应用特定行业的公式或定义）。
    *   **智能体架构：** 采用 ReAct 模式，为智能体提供四种工具：`list_db`（查看表名）、`query_db`（执行 SQL/Mongo 查询）、`execute_python`（处理复杂逻辑和数据清洗）、`return_answer`（提交最终答案）。
    *   **确定性验证：** 答案基于原始未扰动数据预先计算，验证脚本检查智能体输出中是否包含正确的基准值，确保评估的客观性。

#### 3. 实验设计
*   **数据集/场景：** 包含 12 个数据集，涵盖 9 个领域（如 CRM、金融市场、基因组学、专利等）。
*   **Benchmark 构成：** 共 54 个自然语言查询，分布在 4 种数据库管理系统（PostgreSQL, MongoDB, SQLite, DuckDB）中。
*   **对比方法：** 评估了五个前沿大模型智能体：
    *   **GPT-5.2** 与 **GPT-5-mini**
    *   **Gemini-3-Pro** 与 **Gemini-2.5-Flash**
    *   **Kimi-K2**
*   **评估指标：** 使用 **pass@k**（估计 k 次尝试中至少成功一次的概率），其中 $n=50$。

#### 4. 资源与算力
*   **算力说明：** 论文未提及模型训练的 GPU 资源（因为使用的是商业 API），但详细记录了推理成本。
*   **实验成本：** 总计运行了 13,500 次试验，API 总成本约为 **3,150 美元**。
*   **运行限制：** 每次试验限制在 100 个迭代轮次或 1 小时墙钟时间内，单个工具调用超时为 600 秒。

#### 5. 实验数量与充分性
*   **实验规模：** 每个查询针对每个模型运行 50 次独立试验，总计 13,500 条轨迹，样本量充足，能够有效抵消 LLM 输出的随机性。
*   **客观性与公平性：** 论文通过分层平均（按数据集平均后再按总数平均）来防止某些查询较多的数据集主导结果。此外，还进行了深入的**失败模式分析**（FM1-FM5），由人工和 GPT-5 共同标注了 1,147 条失败轨迹，分类细致且客观。

#### 6. 论文的主要结论与发现
*   **性能低迷：** 即使是表现最好的模型（Gemini-3-Pro），其 **pass@1 准确率也仅为 38%**，pass@50 也不超过 69%。
*   **失败主因：** 85% 的错误源于**规划错误（FM2）**或**实现错误（FM4）**。智能体通常能找到正确的数据源，但在如何计算和编写代码/查询上出错。
*   **文本提取瓶颈：** 智能体过度依赖正则表达式进行文本提取，面对复杂的自然语言日期或实体时表现极差（如专利数据集准确率为 0）。
*   **探索策略：** 表现较好的智能体通常分配约 20% 的工具调用用于数据探索（查看模式、采样数据）；探索太少或过度串行探索都会降低效率。
*   **成本效益：** GPT-5-mini 在成本仅为 Gemini-3-Pro 的 1/20 的情况下，达到了 30% 的准确率，性价比最高。

#### 7. 优点
*   **真实性强：** 基准测试的设计直接源于对真实企业用户的调研，而非学术假设。
*   **异构性支持：** 首次在基准测试中强制要求跨 SQL 和 NoSQL 系统进行数据集成，贴合实际生产环境。
*   **高质量标注：** 每一个查询和答案都经过人工验证，并提供详细的提示文件（Hints）以区分“缺乏背景”和“推理失败”。

#### 8. 不足与局限
*   **规模限制：** 54 个查询虽然质量高，但绝对数量相对较小。
*   **验证偏差：** 验证脚本采用子字符串匹配，倾向于高召回率，可能会漏掉智能体返回正确值但同时包含错误冗余信息的情况。
*   **动态性缺失：** 移除了实时 API 集成和开放式分析问题，以保证答案的确定性，这限制了对智能体处理动态数据能力的评估。
