## 摘要
现代编程智能体越来越多地将专门的子任务委托给子智能体，即处理搜索、调试或终端执行等特定职责的小型专注智能体循环。这种架构模式通过将冗长的输出（如构建日志、测试结果等）隔离在子智能体上下文中，从而保持主智能体的上下文窗口整洁。通常，当智能体为此类任务使用子智能体时，会采用前沿模型。在本文中，我们研究了经过微调的小语言模型（SLM）在智能体终端执行任务中是否能达到与前沿模型相当的性能。我们提出了 Terminus-4B，这是一个专门针对该任务，通过有监督微调（SFT）和使用基于评分细则的 LLM-as-judge 奖励的强化学习（RL）进行后训练的 Qwen3-4B 模型。在涵盖各种前沿模型、训练消融实验和主智能体配置的广泛评估中，我们发现，与“无子智能体”基准相比，Terminus-4B 能够将主智能体的 token 使用量减少高达约 30%，且不会影响其在 SWE-Bench Pro 和我们内部的 SWE-Bench C# 基准测试（该基准通常包含大量冗长的执行任务）上的性能。此外，Terminus-4B 提升了关键指标，表明主智能体更依赖子智能体的输出，并减少了自身执行终端任务的次数。我们观察到，我们的模型不仅缩小了原始 Qwen 模型与 Claude Sonnet / Opus / GPT-5.3-Codex 等前沿模型之间的差距，甚至往往能超越它们的性能。

## Abstract
Modern coding agents increasingly delegate specialized subtasks to subagents, which are smaller, focused agentic loops that handle narrow responsibilities like search, debugging or terminal execution. This architectural pattern keeps the main agent's context window clean by isolating verbose outputs (e.g. build logs, test results, etc.) within the subagent context. Typically when agents employ subagents for such tasks, they use frontier models as these subagents. In this paper, we investigate whether a finetuned small language model (SLM) can achieve comparable performance to frontier models in the task of agentic terminal execution. We present Terminus-4B, which is a post-trained Qwen3-4B model via Supervised Finetuning (SFT) and Reinforcement Learning (RL) using rubric-based LLM-as-judge reward, specifically for this task. In our extensive evaluation spanning various frontier models, training ablations and main agent configurations, we find that Terminus-4B is able to reduce the token usage of the main agent by up to ~30% compared to the No Subagent baseline with no impact to agent performance on benchmarks like SWE-Bench Pro and our internal SWE-Bench C# benchmark, which tends to be heavy in verbose execution tasks. Furthermore, Terminus-4B improves key metrics showing the main agent relying on the outputs of the subagent and doing fewer terminal execution tasks by itself. We see that our model not only closes the gap between the Vanilla Qwen model and frontier models like Claude Sonnet / Opus / GPT-5.3-Codex, but often even exceeds their performance.

*   **核心问题**：能否开发一个专门的小型模型（如 4B 参数量），作为“执行子智能体”（Execution Subagent）来独立处理这些繁琐的终端任务，并仅向主智能体返回精简的结构化摘要？其性能是否能媲美甚至超越昂贵的前沿大模型（Frontier LLMs）？

### 2. 方法论
*   **核心思想**：采用“主-从”架构。主智能体将执行任务委托给子智能体，子智能体在隔离的循环中运行命令，吸收所有冗长输出，最后输出 XML 格式的 `<final_answer>`。
*   **关键技术细节**：
    *   **模型基础**：选用 Qwen3-4B 作为基座模型。
    *   **两阶段后训练**：
        1.  **有监督微调 (SFT)**：利用内部遥测数据中的专家轨迹进行微调，让模型学会基本的工具调用和摘要格式。
        2.  **强化学习 (RL)**：采用 **GRPO（群组相对策略优化）** 算法。
    *   **奖励设计（LLM-as-judge）**：引入基于评分细则（Rubric）的奖励机制。为了降低对比成本，研究者先将原始轨迹转化为“执行计划”（Execution Plan），再由前沿模型根据执行质量、失败模式、答案质量等 14 个维度对候选轨迹进行打分。
    *   **解耦训练框架**：在 RL 阶段将子智能体与主智能体解耦，使用轻量级模型模拟主智能体发出指令，从而实现低成本、高并发的 Rollout 训练。

### 3. 实验设计
*   **数据集与基准测试**：
    *   **SWE-Bench Pro**：跨语言（Python, JS, Java 等）的软件工程基准测试。
    *   **SWE-Bench C#**：内部构建的针对 C# 语言的基准，包含大量重度执行任务。
*   **对比方法**：
    *   **基准线**：无子智能体（主智能体直接操作终端）。
    *   **前沿模型子智能体**：使用 Claude 3 Opus/Sonnet 或 GPT 系列作为子智能体。

*   **主智能体配置**：分别测试了 GPT-5.3-Codex、Claude Sonnet 4.6 和 Claude Opus 4.6 作为主智能体时的表现。

*   **训练细节**：SFT 训练了 2 个 epoch；RL 阶段使用了 16 个 prompt 的 rollout batch size（每组 8 个样本），总计 128 个并行 rollout。

### 5. 实验数量与充分性
*   **实验规模**：论文进行了多维度的消融实验，包括不同主模型与子模型的组合、有无终端工具的对比、跨语言泛化测试等。
*   **充分性评价**：实验设计非常充分且客观。研究者不仅关注了最终的“解决率”（Resolve Rate），还深入分析了行为指标（如主智能体对子智能体的信任度、Token 节省率），并引入了第三方 LLM 裁判进行 5 维度的响应质量评估，确保了结论的可靠性。

### 6. 主要结论与发现
*   **Token 节省显著**：Terminus-4B 相比无子智能体方案，可减少主智能体约 **30% 的 Token 消耗**。
*   **性能不降反升**：在解决率上，Terminus-4B 能够匹配甚至在某些场景下超过使用前沿模型作为子智能体的表现。
*   **信任度提升**：行为指标显示，主智能体在获得 Terminus-4B 的反馈后，极少需要重新运行终端命令（Distrust 信号低），证明了其摘要的准确性和行动力。
*   **RL 的必要性**：实验证明，单纯 SFT 无法达到理想效果，RL 阶段对于提升摘要的细节准确性和减少幻觉至关重要。

### 7. 优点
*   **架构优雅**：通过子智能体模式解决了长上下文管理的痛点。
*   **成本效益极高**：用 4B 模型替代前沿模型处理高频、高 Token 消耗的任务，极大地降低了生产环境的推理成本。
*   **训练方法创新**：提出的“执行计划”对比奖励机制和解耦训练框架，为智能体子任务的微调提供了可借鉴的范式。

### 8. 不足与局限
*   **平台覆盖有限**：训练和评估主要集中在 Unix/Bash 环境，未涵盖 Windows (PowerShell) 或 Mac (Zsh) 等其他终端环境。
*   **基准测试局限**：主要基于类 SWE-Bench 的 GitHub 问题，可能无法完全代表现实中更复杂、更混乱的工业级开发场景。
