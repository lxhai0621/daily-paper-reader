## 摘要
挖掘软件仓库通常需要将提交（commits）、评审（reviews）、代码行或整个仓库等工件（artifacts）进行分类。人工标注成本高昂且容易出错；有限的上下文经常导致误分类或标签的不确定性。我们研究了通过标准 bash 命令动态探索仓库的 LLM 代理，是否能够达到接收预构建上下文的简单 LLM 的分类质量。在四项任务、八种方法配置和 4943 次分类中，尽管代理是自行检索上下文，但仍实现了具有竞争力的准确率。其主要优势在于鲁棒性：代理避免了上下文窗口溢出，并且其扩展性不受工件大小的影响。对 100 个方法与基准真相（ground truth）不一致的案例进行人工诊断后发现，存在规范歧义以及在有限上下文下生成的标签，这表明针对此类基准真相的准确率可能会低估具有更广泛上下文访问权限的方法。

## Abstract
Mining software repositories often requires classifying artifacts like commits, reviews, code lines, or entire repositories into categories. Human labeling is expensive and error-prone; limited context frequently leads to misclassifications or uncertainty in labels. We investigate whether LLM agents that dynamically explore repositories through standard bash commands can match the classification quality of simple LLMs that receive pre-engineered context. Across four tasks, eight approach configurations, and 4943 classifications, agents achieve competitive accuracy despite retrieving their own context. The primary advantage is robustness: agents avoid context-window overflows and scale independently of artifact size. A manual diagnosis of 100 cases where approaches disagree with the ground truth reveals specification ambiguities and labels produced under limited context, suggesting that accuracy against such ground truth may underestimate approaches with broader context access.

#### 1. 核心问题与整体含义
在软件仓库挖掘（MSR）领域，对提交（commits）、代码评审、代码行或整个仓库进行分类是研究的基础。传统方法依赖人工标注（昂贵且易错）或预设上下文的机器学习/LLM模型。然而，**“如何为模型提供最佳上下文”**一直是一个工程难题。
本研究提出了**代理式仓库挖掘（Agentic Repository Mining）**，旨在探讨 LLM 智能体能否通过自主执行 Bash 命令动态探索仓库，从而摆脱对人工预设上下文的依赖，并解决长文本导致的上下文窗口溢出问题。

#### 2. 方法论
*   **核心思想**：将 LLM 置于一个隔离的 Docker 容器中，赋予其标准 Bash 工具（如 `git`, `grep`, `cat`, `ls` 等）的访问权限。智能体不再被动接收固定的上下文，而是根据任务目标自主决定读取哪些文件、查看哪些历史记录。
*   **关键技术细节**：
    *   **代理循环（Agentic Loop）**：LLM 生成推理步骤 -> 输出工具调用指令 -> 暂停生成 -> 执行 Bash 命令 -> 将结果反馈给 LLM -> 继续推理。
    *   **工具调用变体**：
        *   **原生调用（Native）**：利用模型供应商提供的 API（如 Amazon Bedrock 的 Converse API）进行结构化调用。
        *   **停止序列（Stop-Sequence）**：使用 XML 标签（如 `<bash>...</bash>`）自定义解析，更具透明度和跨模型通用性。
    *   **提示词缓存（Prompt Caching）**：针对智能体多轮对话导致的 Token 累积问题，采用缓存机制降低重复输入成本。

#### 3. 实验设计
*   **任务与数据集**：
    1.  **Herbold (纠缠提交)**：判断 bug 修复提交中的某一行代码是否真正贡献了修复（行级）。
    2.  **Härtel (安全评审)**：识别 PR 评论是否讨论了潜在的安全缺陷（评论级）。
    3.  **Levin (维护活动)**：将提交分类为纠正性、适应性或完善性维护（提交级）。
    4.  **Munaiah (仓库分类)**：区分“工程化软件项目”与作业、玩具项目（仓库级）。
*   **对比方法（Baselines）**：
    *   **简单 LLM（Simple LLMs）**：提供人工预设的上下文（如 Diff 块、README、元数据），包括思维链（CoT）和非 CoT 模式。
    *   **记忆基准（Memorization）**：仅提供最小标识符，测试模型是否仅凭训练数据记忆进行分类。
*   **模型选择**：Claude 3.7 Sonnet, Mistral Large 3, Llama 3.3 70B。

#### 4. 资源与算力
*   **算力平台**：实验通过 **Amazon Bedrock** API 调用云端模型，未直接使用本地 GPU 进行训练。
*   **成本与时长**：
    *   智能体平均耗时 21-29 秒/样本，而简单 LLM 仅需 2-6 秒。

    *   使用了 Claude 3.7 的提示词缓存功能，节省了约 35%-40% 的成本。

#### 5. 实验数量与充分性
*   **实验规模**：共进行了 **4943 次有效分类**，覆盖 4 个任务和 8 种方法配置。
*   **统计严谨性**：采用了**分层准确率模型（Hierarchical Accuracy Model）**和 Stan 概率编程语言进行贝叶斯推断，提供了 95% 置信区间，确保了不同任务难度下对比的公平性。
*   **诊断分析**：对 100 个分歧案例进行了深度人工诊断，分析了基准真相（Ground Truth）本身的局限性。

#### 6. 主要结论与发现
*   **鲁棒性优势**：智能体在处理大规模工件（如超大 README 或复杂 Diff）时表现极佳，**完全避免了简单 LLM 常见的上下文溢出错误**。
*   **准确率对等**：尽管智能体需要自行寻找信息，其准确率与拥有“上帝视角”（人工预设最佳上下文）的简单 LLM 相当，甚至在某些任务中更优。
*   **基准真相的局限**：诊断发现，许多“分类错误”实际上是因为智能体获取了比原始标注者更丰富的上下文，从而发现了原始标签的错误或歧义。
*   **不确定性处理**：LLM 及其代理在处理“不确定（unclear）”类别时依然表现较弱，倾向于给出确定性答案。

#### 7. 优点
*   **动态性**：摆脱了繁琐的提示词工程（Prompt Engineering），智能体能像人类专家一样按需探索。
*   **可扩展性**：成本和 Token 使用量与仓库实际大小解耦，仅取决于智能体探索的深度。
*   **透明度**：通过分析智能体的 Bash 命令轨迹（Trajectories），研究者可以清晰了解模型的推理和取证过程。

#### 8. 不足与局限
*   **成本与延迟**：多轮交互显著增加了 API 费用和等待时间，不适合实时性要求极高的场景。
*   **数据泄露风险**：在仓库分类任务中，模型表现出明显的记忆效应，可能在训练阶段已见过相关项目。
*   **工具调用失败**：尽管比例较低（约 2%），但智能体仍可能因 Bash 语法错误或逻辑死循环导致任务失败。
*   **应用限制**：目前仅在隔离环境中使用 Bash，未涉及需要互联网访问或复杂交互的挖掘任务。
