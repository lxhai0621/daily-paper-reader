## 摘要
随着AI智能体从研究原型转向企业生产系统，它们所调用的工具接口仍根植于以人为中心的CRUD（增删改查）范式。本文识别了传统API与自主智能体需求之间的五个基本架构失配：精确标识符依赖、面向渲染的响应、单次交互假设、等同于用户的授权以及不透明的错误语义。我们提出了“Agent优先工具API”范式，包含三个集成机制：（1）六动词语义协议，将工具交互分解为搜索、解析、预览、执行、验证和恢复阶段；（2）归一化工具契约（NTC），提供包括置信度分数、证据链和建议后续操作在内的结构化决策支持元数据；（3）结合静态能力策略与动态风险升级的双层治理流水线。该范式已在一个生产级多租户SaaS平台中实现并验证，该平台服务于跨6个业务领域的85个注册工具。针对50个真实操作任务的对比实验表明，Agent优先API实现了88%的端到端任务成功率，而优化的CRUD基准线仅为64%（提升了37.5%），同时减少了72.7%的人工干预，并将自主错误恢复能力提升了5.8倍。我们确定该范式与MCP等传输层标准是正交且互补的，作为现有工具发现和调用协议之上的语义应用层运行。

## Abstract
As AI agents transition from research prototypes to enterprise production systems, the tool interfaces they consume remain rooted in human-oriented CRUD paradigms. This paper identifies five fundamental architectural mismatches between conventional APIs and autonomous agent requirements: exact-identifier dependence, rendering-oriented responses, single-shot interaction assumptions, user-equivalent authorization, and opaque error semantics. We propose the Agent-First Tool API paradigm, comprising three integrated mechanisms: (1) a Six-Verb Semantic Protocol that decomposes tool interactions into search, resolve, preview, execute, verify, and recover phases; (2) a Normalized Tool Contract (NTC) providing structured decision-support metadata including confidence scores, evidence chains, and suggested next actions; and (3) a dual-layer governance pipeline combining static capability policies with dynamic risk escalation. The paradigm is implemented and validated in a production multi-tenant SaaS platform serving 85 registered tools across 6 business domains. Comparative experiments on 50 real operational tasks demonstrate that Agent-First APIs achieve 88% end-to-end task success rate versus 64% for optimized CRUD baselines (+37.5%), while reducing required human interventions by 72.7% and improving autonomous error recovery by 5.8x. We establish that the paradigm is orthogonal and complementary to transport-layer standards such as MCP, operating as the semantic application layer above existing tool discovery and invocation protocols.

### 1. 核心问题与整体含义（研究动机和背景）
*   **核心矛盾**：现有的企业级 API 是为人类操作的 UI 设计的（CRUD 模式），而 LLM 智能体是“推理者”而非“渲染者”。
*   **五大失配**：
    1.  **参数精确性**：传统 API 要求精确 ID（如 UUID），而智能体通常只有模糊的自然语言意图。
    2.  **响应内容**：传统 API 返回 JSON 数据用于展示，智能体则需要置信度、证据链和后续行动建议。
    3.  **交互频率**：传统 API 假设单次请求即可完成，智能体则处于多轮推理循环中。
    4.  **权限模型**：传统权限绑定用户，智能体需要额外的“工具能力”与“对象范围”双层治理。
    5.  **错误处理**：HTTP 状态码对智能体无意义，它们需要结构化的恢复策略。
*   **研究目标**：重新构思工具接口，将其从“表单提交终点”转变为“目标达成协议”。

### 2. 方法论
论文提出了三个核心贡献：
*   **六动词语义协议（Six-Verb Semantic Protocol）**：将工具调用结构化为有限状态机（FSM），包含：
    1.  `semantic_search` (S)：语义搜索，接受模糊描述返回候选集。
    2.  `resolve_candidates` (R)：解析候选，处理歧义。
    3.  `preview_action` (P)：动作预览，在执行前展示影响和风险。
    4.  `execute_action` (E)：执行动作，确保幂等性。
    5.  `verify_result` (V)：结果验证，对比执行结果与原始意图。
    6.  `recover_from_error` (C)：错误恢复，提供结构化引导。
*   **归一化工具契约（NTC）**：标准化的响应格式，包含 `ok`（状态）、`answer`（自然语言总结）、`confidence`（置信度）、`evidence`（证据）、`result_refs`（结果引用）和 `next_actions`（后续建议）。
*   **双层治理流水线**：
    *   **能力权限**：RBAC 模式，决定 Agent 能否调用某工具。
    *   **对象范围**：四级隔离（租户→品牌→门店→用户），确保数据安全。
    *   **动态风险升级**：根据影响实体数量、是否跨品牌等因素动态调整风险等级，触发人工审批。

### 6. 主要结论与发现
*   **性能提升**：任务成功率从 64% 提升至 **88%**（+37.5%）。
*   **错误减少**：ID 幻觉错误从 28% 降至 **4%**；自主错误恢复能力提升了 **5.8 倍**。
*   **人工干预降低**：需要人工介入的比例从 22% 降至 **6%**。
*   **成本权衡**：单次调用的延迟增加（+48%）和 Token 消耗增加（+37%），但由于减少了无效的重试循环，**单任务的总 API 调用次数从 4.8 次降至 3.2 次**。

### 7. 优点
*   **范式创新**：首次系统性地定义了“智能体原生”的 API 应该长什么样，而非仅仅在模型端做 Prompt Engineering。
*   **安全性高**：内置的风险评估和审批门禁（Approval Gate）非常符合企业级生产环境的合规需求。
*   **兼容性**：与 MCP（Model Context Protocol）标准互补，Agent-First 负责语义层，MCP 负责传输层。
*   **实用性**：通过将“解析模糊描述”的压力从 LLM 转移到后端确定性逻辑，极大地缓解了幻觉问题。

### 8. 不足与局限
*   **工程成本**：需要维护两套 API 表面（CRUD 用于 UI，Agent-First 用于 AI），增加了开发负担。
*   **置信度校准**：目前的置信度分数部分依赖于开发者静态分配，虽然引入了贝叶斯更新，但仍有优化空间。
*   **模型依赖**：虽然在中等规模模型（MiniMax-M2.7）上表现良好，但在不同参数量级的模型上，这种范式的边际收益可能存在差异。
*   **协议强制性**：目前六动词协议主要靠命名规范约束，缺乏强类型的接口定义语言（IDL）支持。
