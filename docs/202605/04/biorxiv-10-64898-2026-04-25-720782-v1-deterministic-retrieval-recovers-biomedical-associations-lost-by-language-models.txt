ABSTRACT 

Large language model (LLM)-based retrieval systems miss biomedical associations through output truncation, synonym mismatch and run-to-run variability, but the magnitude of this loss remains unclear. We present BioChirp, an open-source framework that uses LLMs for query interpretation and candidate filtering, combining multi-source consensus entity resolution with deterministic graph-based retrieval. Across four major biomedical databases, BioChirp recovered more associations with higher reproducibility than conventional LLM-based retrieval approaches. 

Main 

How many biomedical associations do conversational retrieval systems miss? The question matters because missing associations can compromise downstream analyses in drug discovery and translational research 1, yet the extent of this loss has not been systematically quantified 2–4 . Current approaches fail in three recurring ways. MCP clients and agentic pipelines can truncate large result sets, time out on complex queries or fail through invocation errors 5–7 . NL2SQL systems depend on exact surface-form matching 8 and therefore miss records filed under synonyms 9,10 ; for example, a search for cancer-associated drugs may overlook entries indexed under leukemia, lymphoma or carcinoma. Language-model outputs are also stochastic, so identical queries can return different result sets across runs, whether the model generates a structured retrieval plan or enumerates associations directly, undermining reproducibility 11–16 . Together, these failure modes erode retrieval completeness in ways that have not been measured against real biomedical databases.

Here we introduce BioChirp, an open-source framework built around a single design principle: language models interpret the query, whereas deterministic algorithms execute retrieval. User questions are first processed by a lightweight reasoning layer in which low-cost language models from different providers generate candidate interpretations in parallel; an orchestrator then combines, corrects or reconciles these candidates to produce a single validated interpretation (Fig. 1a–b). A central technical component is a multi-source consensus entity-resolution module that maps entity mentions to canonical database identifiers through fuzzy lexical matching, semantic vector retrieval and curated synonym expansion, followed by an LLM-based consensus filter that removes false positives. After candidate filtering and entity resolution, no language model participates in retrieval planning or execution. Resolved identifiers are passed to a graph-based planner that models each database schema as a graph of entity tables and relationship edges, identifies a compact connected join plan linking the required fields, and executes only schema-validated operations (Fig. 1c). Because the planner is deterministic, identical queries always produce identical structured outputs, although the accompanying natural-language summary may vary. BioChirp currently supports four major biomedical databases: Open Targets 17 , Comparative Toxicogenomics Database (CTD) 18 , Highly Confident Drug-Target Database (HCDT) 19 and Therapeutic Target Database (TTD) 20 . Implementation details, schema definitions and preprocessing procedures are described in the Methods. To illustrate the workflow, we queried BioChirp for drugs used to treat TB. The system resolved the request to the canonical Open Targets disease entry, expanded the query through ontology traversal to capture descendant terms such as pulmonary tuberculosis and meningeal tuberculosis, retrieved 161 drug–disease associations, removed duplicates and returned 53 unique drugs with full provenance in under 20s (Fig. 1d). An equivalent query on exact-match systems would miss associations filed under these descendant terms. BioChirp preserved these results as a complete, downloadable association table for inspection and downstream analysis, motivating systematic evaluation of completeness across broader benchmarks. We next benchmarked retrieval completeness against MCP-based systems using the official Open Targets MCP server. Six queries (Extended Data Table 1) spanning three biomedical association types (disease–target, drug–disease and gene–disease) were evaluated in both top-ranked and exhaustive retrieval modes across multiple model and client environments (Extended Data Table 2) (see Methods). Representative queries included CML targets, diseases treated with aspirin and diseases associated with TP53. Across two independent runs, MCP-based systems frequently failed owing to invalid requests, invocation timeouts and upstream retrieval errors (Fig. 2a). No MCP-based system returned a complete result set for any exhaustive query, whereas BioChirp retrieved complete results for all six queries (Fig. 2b)(Supplementary Table 1). These failures reflect one source of retrieval incompleteness: breakdowns in agentic execution. We next asked whether incompleteness also persists in systems that can successfully generate executable database queries but remain vulnerable to naming variation in biomedical names. To test this, we designed seven synonym-paired queries (Extended Data Table 3) on the HCDT database, including Aspirin versus Vazalore, chronic myelogenous leukemia versus chronic myeloid leukemia versus CML, and EGFR versus ERBB1. Across four NL2SQL frameworks paired with four language models from different providers (Extended Data Table 4), correct results were returned only for canonical names; all synonym queries failed. NL2SQL systems also returned 52 rather than the correct 48 entries for Aspirin because false-positive substring matching pulled in nitroaspirin-related records. BioChirp returned the correct 48 associations for both canonical names and all synonyms (Fig. 2c). Together, these results show that incompleteness arises both from execution failures in agentic retrieval pipelines and from synonym brittleness in NL2SQL systems, whereas BioChirp preserves complete structured retrieval across both settings. Having shown that MCP-based and NL2SQL systems frequently return incomplete or inconsistent results, we next examined the quality of the language-model layer that drives both query interpretation and entity-candidate filtering in BioChirp. Both tasks require biomedical reasoning to correctly identify relevant entities and relationships from ambiguous queries spanning multiple biomedical concepts. We used the MedQA benchmark 21 , a standardized set of medical reasoning questions, as a proxy for this capability. On 100 questions evaluated across three independent runs, the multi-model orchestrated system achieved higher median accuracy than any individual model (Fig. 2d–e) (Extended Data Table 5), supporting the use of ensemble-based reasoning upstream of deterministic retrieval. We evaluated BioChirp’s entity-resolution module separately because complete retrieval requires accurate normalization of biomedical names to database-specific canonical forms. Using a benchmark of 48 entities (19 diseases, 14 drugs and 15 genes) (Extended Data Table 6) with Open Targets synonym resources as ground-truth labels, BioChirp configurations combining fuzzy, semantic and curated matching achieved the highest recall and F1 across all three entity types, outperforming four direct language-model baselines (Extended Data Table 7) with only modestly higher median latency (Fig. 2f–l). Finally, we assessed reproducibility and coverage across 70 natural-language queries (Supplementary Table 2), each run five times on nine systems comprising four direct language-model baselines (Extended Data Table 8), BioChatter 22 , and four structured retrieval backends accessed through BioChirp. The Open Targets backend alone returned a median of 584 entries per query, compared with single-digit medians for generative models, at moderately higher but stable latency (Fig. 2m–n). Run-to-run reproducibility, measured by median Jaccard similarity, was 1.0 for all four BioChirp backends, whereas generative models showed substantially greater variability (Fig. 2o). Together, these results show that multi-source consensus entity resolution combined with deterministic graph-based retrieval recovers a substantial and previously unquantified fraction of biomedical associations. In practice, this provides more reliable and reproducible database access with clear provenance. Because language interpretation is separated from schema-defined retrieval, extending the framework to another structured biomedical database requires a schema definition, identifier mappings and adapted prompts.

Methods 

BioChirp was implemented in Python 3.11 for deterministic natural-language querying of biomedical databases (Fig. 1a). The architecture comprised an interpretation layer for extracting intent and entity mentions from free-text input, synonym expansion and entity-resolution services, a deterministic planner for selecting the required retrieval strategy, and source-specific retrieval modules for Open Targets 17 , CTD 18 , HCDT 19 and TTD 20 . Open Targets was queried at runtime through a live GraphQL API, whereas CTD, HCDT and TTD were preprocessed offline and stored locally (see Data preprocessing and Open Targets online retrieval). Implementation details and schema definitions are provided in the GitHub repository. At runtime, each user query was first routed to the interpretation module, which returned inferred intent and structured entity mentions. These entities were then expanded through synonym and resolution modules, after which the planner generated a source-specific retrieval strategy. Each retrieval module applied this plan to the corresponding data source. The complete result set was returned as a downloadable CSV file. A language-model-generated summary based on a preview of the retrieved table (default: first 50 rows; user-configurable) was provided alongside the full structured output. 

Data preprocessing 

BioChirp accesses source data through two complementary modes. Open Targets is queried at runtime through a dedicated resolver (see “Open Targets retrieval”), while we preprocess CTD, HCDT and TTD offline and store them locally to support deterministic query execution. We processed each local database independently into a consistent internal schema with harmonized column names and a fixed relational structure. Preprocessing followed a common pattern across CTD, HCDT and TTD (Extended Data Fig. 1a–c). For each database, identifier and name fields were standardized, unnecessary prefixes and placeholder values were removed, and cells containing multiple values were split so that each row described a single entity or relationship. A deterministic priority rule was applied to assign exactly one canonical identifier to each entity (Supplementary Note 1). Cleaned records were organized into master tables (one identifier and one name per row) and association tables (paired identifiers representing relationships between entities). After assembly, duplicate rows, missing identifiers and malformed entries were removed. The final tables were written as separate files for each database. At runtime, these files were loaded and validated before each query. Source-specific deviations are described in Supplementary Note 2, Supplementary Note 3 and Supplementary Note 4. 

Reasoning layer and multi-model orchestration 

BioChirp uses a two-stage reasoning workflow (Fig. 1a, panel B) to convert free-text questions into inputs suitable for deterministic retrieval. In the first stage, query rewriting and biomedical scope classification are performed independently using a multi-model ensemble (Supplementary Note 5). Both tasks are carried out by four language models running in parallel, whose outputs are consolidated by a judge model into a single result for each task. This design reduces single-model failure modes, including abbreviation expansion errors, synonym ambiguity and malformed reformulations, while preserving deterministic downstream execution. In the second stage, the rewritten query is converted into a structured representation containing the biomedical fields relevant to the request (Supplementary Note 6). BioChirp supports fields including drug, target, gene, disease, pathway, biomarker, mechanism and approval status. The interpreter distinguishes between fields that are not relevant, fields requested without a specific value, and fields constrained by user-provided terms. If any component fails at either stage, BioChirp applies conservative fallback behavior: failed candidate models are excluded while the remaining outputs are consolidated, and a failed rewriting step falls back to the original query. Queries outside the biomedical schema are redirected to a general-purpose web-based response. 

Multi-source consensus entity resolution 

Because synonymy, abbreviations and ontology variation are major causes of missed biomedical associations, BioChirp treats entity resolution as a dedicated retrieval problem rather than a simple normalization step. After query interpretation, BioChirp resolves user-specified biomedical terms into database-compatible representations. This step maps query terms to the forms used in the underlying databases, including synonyms, ontology descendants and biologically appropriate alternatives such as brand names for drugs. For local knowledge-base routes (CTD, HCDT and TTD), BioChirp generates candidate matches through three complemen-tary strategies applied in parallel: fuzzy lexical matching (Supplementary Note 7), semantic vector retrieval (Supplementary Note 8) and curated synonym expansion (Supplementary Note 9). Fuzzy matching recovers near-string variants and formatting differences, semantic retrieval captures semantically similar biomedical terms that may not share surface form, and curated synonym expansion incorporates aliases, brand names and ontology-derived terms. Candidate sets are passed to an LLM-based filtering stage (Supplementary Note 10) before database execution. Two selector models from different providers are run in parallel, and only candidates accepted by both are retained directly. Disagreements

Graph-based query planning and deterministic retrieval for offline databases 

For local retrieval from CTD, TTD and HCDT, BioChirp did not use a language model to write SQL or decide how database tables should be connected 22,23 . Instead, each database schema was represented as a graph in which tables were nodes and declared identifier-based relationships were edges (Supplementary Note 11, Supplementary Note 12). Formal definitions and algorithmic guarantees for this deterministic planning procedure are provided in Supplementary Note 13. Planning began by mapping each active concept from the interpreted query to its unique table in the schema. If all concepts were present in a single table, no joins were required. Otherwise, BioChirp applied a Steiner tree approximation over the schema graph to identify a minimal connected set of tables linking all requested concepts through declared relationships. The resulting table set was converted into a fixed execution tree with deterministic ordering, ensuring that equivalent inputs always produced the same plan across runs. Resolved entity values were first used to filter the selected tables before any joins were executed, reducing intermediate result size. BioChirp then executed only schema-validated joins, returned the requested output fields and removed duplicate rows. Because this procedure was deterministic, identical structured inputs always produced the same result. For example, for the query drugs for TB” (Fig. 1c), BioChirp first interpreted the request as asking for drug output constrained by the disease term TB”. Entity resolution then normalized TB” to the canonical disease concept tuberculosis”. The planner mapped these concepts to the drug and disease master tables and, finding no single table containing both, applied Mehlhorn’s Steiner tree approximation over the schema graph to identify the drug-to-disease association table as the minimal bridge. This yielded a three-table execution tree in which all join keys were verified against the declared schema. The disease table was then filtered to tuberculosis and its resolved synonyms, linked through the validated associations to the drug table, and returned as a deduplicated result table. 

Open Targets online retrieval 

For Open Targets, BioChirp queries the platform’s GraphQL API at runtime rather than relying on a preprocessed local copy. We resolve entity mentions to canonical Open Targets identifiers, selecting the highest-ranked match deterministically. Each domain-specific retrieval function resolves entity surface forms to canonical identifiers independently before accessing data, so that grounding remains robust even when the initial resolution is imprecise. Disease queries are further expanded through ontology traversal to include descendant terms and synonyms. Unlike the offline pipeline, Open Targets retrieval does not use the schema-graph planner. Instead, each resolved entity type is routed to a fixed retrieval function for targets, drugs or diseases. These functions execute predefined GraphQL queries with exhaustive pagination. Returned records are deduplicated, sorted by association score or clinical phase, and written as a downloadable CSV file. Fixed selection and routing rules ensure that identical queries yield identical structured outputs. Open Targets was queried through the live GraphQL API, and all results reported in this study reflect the database state accessed on 27 February 2026. 

Response generation 

BioChirp separates structured retrieval from narrative synthesis so that language-model-generated text does not alter the underlying tabular evidence. After retrieval, a summary language model generates a concise textual response based on a preview of the result table, with an optional web-based verification step to check clinical context. The complete structured table exported as CSV is the canonical output; the natural-language summary is provided only for readability and does not replace the retrieved records. Provenance is preserved at both the record and response level (Fig. 1a, panel D). 

Evaluation of retrieval completeness in MCP-based systems 

We benchmarked three categories of MCP-enabled system: agentic, chat-endpoint and desktop client, using the Open Targets MCP server as the shared data source. Six queries tested three biomedical association types (disease–target, drug–disease, gene–disease), each posed in top-ranked and exhaustive retrieval modes (Extended Data Table 1). The agentic and chat-endpoint systems were evaluated with five OpenAI models, and Claude Desktop with two Anthropic models (Extended Data Table 2). Each query-model pair was run twice. Run outcomes were classified as Pass , Partial or Fail by comparison with the complete reference set obtained by direct API query. BioChirp was evaluated on the same queries for direct comparison (Extended Data Fig. 2).

NL2SQL synonym robustness benchmark 

The benchmark comprised seven natural-language queries organized into three groups of semantically equivalent formulations: brand versus generic drug names (Vazalore versus aspirin), lexical and abbreviation variants of a disease name (chronic myelogenous leukaemia, chronic myeloid leukaemia and CML), and gene alias variants (EGFR versus ERBB1) (Extended Data Table 3). We evaluated four NL2SQL frameworks across four language-model endpoints drawn from different providers (Extended Data Fig. 3; Extended Data Table 4), yielding 16 framework-model combinations. All combinations received the same system prompt comprising the full database schema, table descriptions, SQL-generation constraints. BioChirp was evaluated on the same query set for direct comparison. 

MedQA benchmark evaluation 

To assess whether multi-model orchestration improved interpretation quality, we evaluated systems on MedQA 21 , a standardized five-option (A–E) medical question-answering benchmark. A fixed subset of 100 questions from the MedQA test split was used across all systems. Each system was tested in three independent runs to account for stochastic variation in language-model outputs. All runs used the same prompt template. BioChirp was compared with direct single-model baselines and two BioChatter-wrapped configurations (Extended Data Table 5). For BioChirp, four candidate models each generated one answer per question; these were adjudicated by a separate judge model to produce the final answer (Extended Data Fig. 5). Accuracy was defined as the fraction of correct responses per run, with mean accuracy calculated across the three runs. 

Entity resolution benchmark 

To evaluate entity resolution directly, we assembled a benchmark of 48 biomedical entities comprising 19 diseases, 14 drugs and 15 genes. Reference labels were derived from Open Targets synonym resources, which provided the ground-truth set of valid alternative names for each entity (Extended Data Table 6). We compared BioChirp configurations based on curated lookup alone, fuzzy lexical matching alone, semantic retrieval alone and the consensus combination of all three, together with four direct language-model baselines. Performance was quantified using recall and F1 score, computed separately for diseases, drugs and genes. 

Reproducibility and coverage evaluation 

To quantify run-to-run consistency within systems and agreement across systems, we evaluated nine systems comprising four direct language-model baselines (Extended Data Table 8), BioChatter 22 , and four structured retrieval backends accessed through BioChirp (Open Targets, TTD, CTD and HCDT). All systems were evaluated on the same set of natural-language queries (Supplementary Table 2). Each query was run five times per system using identical prompts, schema context and model configuration. Failed queries were retried up to three times before being recorded as failures. For each run, outputs were converted to identifier-grounded row tuples so that equivalent entities returned under different surface names (for example, aspirin and acetylsalicylic acid) were matched by canonical identifier rather than string comparison. Query strings were normalized by lowercasing and collapsing whitespace, and a manually curated alias map was used to merge variant phrasings of the same term across systems. For each system and query, results from all five runs were pooled into a single union set, representing the largest set of associations that the system returned across repeated executions. This union set was used for all downstream comparisons. Coverage and Jaccard agreement were computed only over rows for which a valid canonical identifier could be assigned. Coverage was computed as the fraction of associations in one system also present in another, aggregated across shared queries. Jaccard similarity between the union sets of each system pair was used as a complementary measure of overlap, treating both systems equally rather than defining one as the reference. Ordinary least-squares regression was fitted on log-transformed latency against log-transformed row count separately for each system to assess the relationship between response latency and result-set size.

Supplementary Note 1. Deterministic identifier assignment and schema assembly 

BioChirp assigned one canonical identifier to each entity within each local database using a deterministic priority rule that selected the first available non-missing identifier. This procedure was applied independently within each database to support stable downstream joins, rather than to create a single identifier system shared across all sources. When multiple identifier fields were available for the same entity, a fixed priority order was applied and the first non-missing value was selected. For example, pathway identifiers were resolved by checking available pathway-linked fields in order until a usable identifier was found, and gene identifiers were resolved in the same way from available gene-linked fields. Disease identifiers were assigned preferentially from structured disease-code fields; when no valid coded identifier was present, the disease name was used as a surrogate identifier within the local schema. This priority-based resolution is summarized in Extended Data Fig. 1b. 

Example. For an HCDT pathway record with pathway_id=0 , reactome_id="R-HSA-5673001" and kegg_hsaid= "hsa04110" ,the zero-like pathway_id value was treated as missing, and the resolved canonical identifier became "R-HSA-5673001" . If the Reac-tome field was also missing, the KEGG identifier "hsa04110" was used instead. For a TTD disease-linked record with no valid ICD-11 code and disease_name="chronic myeloid leukemia" , the cleaned disease name was used as the local disease_id .After identifier assignment, cleaned records were assembled into a fixed master–edge table schema (Extended Data Fig. 1c). Master tables stored one canonical identifier and one corresponding entity name per row, for example drug_id and drug_name . Association tables stored paired identifiers representing relations between entity types, for example drug_id and disease_id . This design ensured that every relation resolved to valid entities and that downstream retrieval could be performed through deterministic, identifier-based joins.

Supplementary Note 2. CTD preprocessing 

CTD preprocessing converted raw CTD source files into four master tables (chemical, gene, disease and pathway) and five association tables covering chemical–gene, chemical–disease, gene–disease, gene–pathway and disease–pathway relationships. Column names were standardized to the local schema and identifier formats were harmonized across files. Database-specific prefixes (MESH, REACT, KEGG) were stripped, and rows with missing identifiers were excluded. Chemical–gene records were restricted to human data. Each association table was reduced to unique identifier pairs. Master tables were assembled by concatenating entries from CTD vocabulary files with entity records extracted from the cleaned association tables. Duplicate identifiers were resolved with priority given to vocabulary-file entries. The final CTD output comprised four master tables and five association tables, each written as a separate Parquet file to support deterministic local retrieval. 

Supplementary Note 3. HCDT preprocessing 

HCDT preprocessing converted five raw source files into four master tables (drug, gene, disease and pathway) and four association tables covering drug–gene, drug–disease, drug–pathway and pathway–gene relationships. Column names were standardized, placeholder values were converted to missing values, and cells containing multiple entries were split so that each row described a single entity or relationship. In pathway-gene records, multi-gene cells were split into one gene per row, and symbols that could not be matched to the resolved HCDT gene vocabulary were discarded. Canonical identifiers were assigned using the deterministic priority rule described in Supplementary Note 1. For each entity type, available identifier fields were checked in a fixed priority order until a usable value was found. Rows missing required identifiers after resolution were removed, and each association table was reduced to unique identifier pairs. Master tables were built separately for each entity type from the cleaned association records and, for drugs, supplemented with entries from the raw drug source file. All master tables were deduplicated by retaining the first occurrence of each identifier, and a final cleanup removed rows containing empty or placeholder values. The final HCDT output comprised four master tables and four association tables, each written as a separate Parquet file. 

Supplementary Note 4. TTD preprocessing 

We preprocessed the TTD source files into five master tables (target, drug, disease, pathway and biomarker) and five association tables covering target–pathway, biomarker–disease, target–disease, drug–target and drug–disease relationships. Several TTD files are distributed as long-form keyword-oriented blocks rather than standard tabular formats, so we first reshaped these blocks into structured rows before further processing. We then standardized column names, converted placeholder values to missing values, and split cells containing multiple entries—such as semicolon-delimited gene names or mechanism-of-action annotations—so that each row described a single entity or relationship. Drug–target records retained their mechanism-of-action annotations, and drug–disease records retained approval status. Canonical identifiers were assigned using the deterministic priority rule described in Supplementary Note 1. For each entity type, we checked the available identifier fields in a fixed priority order until a usable value was found. For diseases, structured codes (such as ICD-11) took precedence when available; otherwise the disease name served as a surrogate identifier. We dropped rows that still lacked a required identifier after resolution and reduced each association table to unique identifier pairs. We built master tables separately for each entity type from the respective source and association files. The disease master table, for instance, was assembled by pooling disease entries across all disease-linked association tables. All master tables were deduplicated by keeping the first occurrence of each identifier, and a final pass removed rows containing empty or placeholder values. The output was written as one Parquet file per table. 

Supplementary Note 5. Multi-model query rewriting and biomedical scope classification 

Before retrieval, BioChirp performs two preparatory steps: query rewriting and biomedical scope classification. The first clarifies the user’s wording; the second determines whether the request can be handled within the BioChirp framework. 

Query rewriting. The raw user query is first rewritten into a clearer retrieval-ready form. Four low-cost language models from different providers run in parallel on the same input, and a judge model combines their outputs into one final rewrite. This reduces dependence on any single model and helps limit inconsistent reformulations caused by provider-specific errors or differences in training. For example, the shorthand query “TB meds with approval status” is rewritten as “List the drugs with disease name as tuberculosis and with approval status as requested.” This step resolves abbreviations, omitted subject terms and underspecified phrasing before downstream interpretation. 

Biomedical scope classification. The rewritten query is then assessed by the same four-model ensemble using a separate scope-checking prompt. The judge model combines the candidate outputs into one final decision on whether the query is fully supported, partially supported or outside the scope of BioChirp, along with a brief explanation. Fully and partially supported queries proceed through BioChirp retrieval,

Supplementary Note 6. Schema-constrained interpretation and validated structured output 

After query rewriting and scope assessment, BioChirp converts the user request into a validated structured representation for downstream retrieval. The output contains one entry for each supported field: drug, target, gene, disease, pathway, biomarker, mechanism of action and approval status. Each field is assigned one of three states: not relevant to the query, requested without a specific value, or constrained by one or more user-provided terms. This lets BioChirp distinguish between broad requests for all matching entities and requests centered on a specific named entity. The output also records whether the query is valid, partially valid or invalid with respect to the BioChirp schema, and whether execution should proceed through BioChirp retrieval or be redirected to web fallback. A short user-facing explanation is included with the interpretation. For example, the query “drugs for tuberculosis” produces an output in which the drug field is marked as requested without a specific value and the disease field is constrained to tuberculosis, whereas all other fields are marked as not relevant. The query is therefore classified as valid and routed to BioChirp retrieval. When a query contains both supported and unsupported elements, BioChirp retains the supported component and records the unsupported elements separately. For example, the query “Give SMILES of diabetes drug” is classified as partially supported because SMILES strings are not part of the retrieval schema. The interpreter retains the request for diabetes-associated drugs and routes it through BioChirp retrieval. The SMILES request is recorded as unsupported. Equivalent inputs are normalized to the same internal form so that minor differences in wording or formatting do not alter downstream execution. Once a query has been interpreted, the same input yields the same retrieval plan. 

Supplementary Note 7. Fuzzy lexical candidate generation for local entity resolution 

We use fuzzy lexical matching to recover near-string matches that arise from typographical errors, abbreviated surface forms, punctuation differences, token reordering and partial lexical overlap. A disease query containing a misspelling such as tuberculsis , for instance, can still surface candidates for tuberculosis on the basis of lexical similarity alone. For each constrained field, the user-provided term is compared against the field-specific vocabulary of the target database using the Python library RapidFuzz. Importantly, matching is restricted by entity class and database field: disease terms are searched only against disease vocabularies, gene terms only against gene vocabularies, and drug terms only against drug vocabularies. This keeps cross-entity contamination low while still allowing broad candidate recovery within each field. We evaluate four complementary similarity measures in parallel: exact character overlap, partial substring match, reordered-token similarity and shared token sets. A candidate is retained whenever any of the four measures exceeds a threshold of 90 on a 0–100 scale. This cutoff was chosen empirically to balance recall against specificity. Because this stage is designed to favour recall, its output is not used for database execution directly. Candidates are instead forwarded to an LLM-based filtering stage that removes false positives and restores precision before deterministic retrieval (Supplementary Note 10). 

Supplementary Note 8. Semantic vector candidate generation for local entity resolution 

We use semantic vector retrieval to recover entities that are related to the query term but different in surface form, for example, abbreviations versus full names, database-specific naming conventions, or synonyms that string similarity alone would miss. A short disease query such as TB, for instance, can retrieve candidates for tuberculosis through embedding proximity even when lexical overlap is negligible. For each constrained field, we encode the query term with three biomedical sentence-embedding models (Supplementary Table 3). We found that no single model reliably handled the full range of naming variability across entity types, so using three in combination gave more consistent coverage. The resulting embeddings are searched against pre-indexed vector collections containing field-specific entity representations for the target database. Retained hits are ranked by cosine similarity. Rather than applying a fixed score threshold, which tends to be too stringent for some queries and too permissive for others, we detect the knee point in the ranked similarity profile to obtain a query-adaptive cutoff. This preserves the strongest semantic matches while discarding weaker neighbours. Because high semantic similarity does not guarantee that a candidate is the intended biomedical entity, retained candidates are forwarded to an LLM-based filtering stage that removes false positives before deterministic retrieval (Supplementary Note 10). 

Supplementary Note 9. Curated synonym candidate generation for local entity resolution 

Curated synonym expansion was used to recover biomedical aliases, ontology-linked terms and grouped biological entities that may not be identified reliably by lexical or semantic matching alone. For example, a gene query for EGFR may need to recover ERBB1, and a drug query for aspirin may need to recover alternate names such as Vazalore when these are represented differently across databases. Supplementary Note 10. LLM-based candidate filtering for false-positive removal 

Candidate sets produced by fuzzy lexical matching, semantic retrieval and curated synonym expansion were designed to maximize recall and were therefore not used directly for database execution. Instead, BioChirp applied an LLM-based filtering stage to remove false positives and retain only candidates that were valid members of the intended biomedical entity class. For each constrained field, the candidate set was evaluated in parallel by two selector models from different providers to reduce provider-specific bias during filtering (Supplementary Table 4). Each selector received the same filtering prompt and was instructed to retain only candidates that were true matches for the queried entity class while excluding loosely related, semantically adjacent or spurious terms introduced during upstream expansion. Semantic retrieval sometimes returns related concepts rather than true entity matches. Synonym expansion may introduce broader terms that do not correspond to the queried entity. By filtering before execution, we ensure that only well-grounded candidates reach the deterministic retrieval stage.

Supplementary Note 11. Deterministic schema-graph construction and join-plan genera-tion 

Once the language model has finished interpreting a biomedical query, BioChirp hands off all subsequent planning to a deterministic module with no further dependence on the language model. Table selection and join construction therefore follow declared schema structure exclusively. Each local database is represented as an undirected graph G = ( V, E) whose nodes are tables and whose edges are foreign-key relationships. Two auxiliary structures accompany the graph: a table-to-column index recording which columns belong to each table, and a join-specification lookup storing the key pairs for every linked table pair.

Concept-to-table mapping. The interpretation stage returns a set of active query concepts C = {c1, . . . , cm}, encompassing both requested output fields and constrained biomedical entities. By design, BioChirp’s schema assigns each queryable biomedical concept to exactly one table. Identifier columns can appear across multiple tables, but these serve only as join intermediates and are never exposed as user-facing concepts. Given a concept c, we define 

M(c) = {v ∈ V : c ∈ Col (v)},

with Col (v) denoting the column set of table v. If a concept maps to no table ( |M(c)| = 0) or to more than one ( |M(c)| > 1), planning halts immediately. When the mapping is unique, we write μ(c) ∈ V for the single table in M(c). Concept grounding therefore reduces to direct schema lookup, without heuristic field matching. 

Steiner-tree connection. The mapped tables form the terminal set 

T = {μ(c) | c ∈ C }.

A single-terminal query produces a trivial one-table plan. When |T | > 1, the planner must find a minimal connected subgraph of G that spans the terminals, potentially introducing bridge tables to complete the foreign-key paths. This is a standard Steiner tree problem 24 . Because practical queries involve only a handful of terminal tables, the problem remains tractable on the schema graphs considered here. We solve it with Mehlhorn’s approximation algorithm 25 via its NetworkX implementation. If the terminals are disconnected in G, the planner rejects the query outright rather than attempting joins without schema support. 

Join-tree extraction. The Steiner tree identifies which tables are required, but execution still requires a concrete join order. BioChirp therefore selects a fixed root and orients the tree into a parent–child hierarchy. For every edge (u, v) in this rooted tree, the planner looks up the declared join specification and checks that the required key columns appear in both Col (u) and Col (v). The tree defines execution order, while join validity is determined by the schema itself. If any join specification is missing or inconsistent with the schema, planning is aborted. The resulting plan contains the rooted join tree, parent map, per-table concept annotations, and validated join-key pairs, which are passed unchanged to the execution engine without further language-model involvement. 

Illustrative example. Consider a query that asks for drug_name , gene_name , and disease_name . The planner maps each concept to its unique master table, yielding three terminals. Mehlhorn’s algorithm then finds the minimal bridge structure connecting them, which in a typical schema introduces two association tables. The resulting five-table Steiner tree is rooted and converted directly into an execution plan for the engine. 

Supplementary Note 12. Plan execution 

Once the planner has produced a validated join plan, BioChirp executes only the joins that the plan specifies. This preserves a clear record of the tables, keys and filters used, and prevents structural changes during execution. 

Pre-join filtering. Before any joins take place, resolved entity values are applied as column-level filters to the participating tables. String comparisons are case-insensitive. These filters narrow the working set early, without altering the plan structure. 

Join execution. The executor carries out only joins present in the validated plan. Under the default strict setting, a missing join specification causes immediate failure rather than automatic recovery, so that every executed join traces back to a declared schema relationship. For efficiency, the executor may reorder currently valid next joins using table-size estimates; this affects runtime order only and leaves the schema-validated join structure unchanged. 

Post-join projection and deduplication. Once all joins have completed, results are projected to the requested output columns and deduplicated on those columns before being returned. No token budget, pagination limit, or generation-length truncation is imposed in this retrieval path. When execution succeeds, the result therefore contains all rows matching the validated plan against the current database snapshot.

2 Strict concept mapping 

Let C denote the active query concepts. For each concept c ∈ C , define

Planning is rejected if |M(c)|̸ = 1 for any concept. When |M(c)| = 1, let μ(c) ∈ V denote the unique element of M(c). The terminal set is

Because every concept must resolve to a single table before the planner proceeds, connectivity is only considered once grounding is complete. 

3 Steiner connection and rooted tree construction 

If |T | = 1, the planner emits a single-table plan. Otherwise, BioChirp first checks that all terminals lie in the same connected component of G

and then computes a Steiner tree GS ⊇ T using Mehlhorn’s approximation algorithm. The tree is rooted at a fixed terminal table and traversed with sorted neighbour processing, producing a unique parent–child execution structure. 

4 Join-specification validation 

For each edge (u, v) in the rooted tree, the planner retrieves the declared join specification for that table pair and checks that the required key columns appear in both Col (u) and Col (v). If any check fails, planning is aborted. The rooted orientation determines execution order; join validity follows from the schema metadata alone. 

5 Main guarantees 

Theorem 1 (Schema soundness) . Any plan accepted under strict mode satisfies: (a) every concept in C is mapped to exactly one table in the plan; and (b) every join in the plan is backed by a declared schema-defined join specification whose key columns are present in the participating tables. Proof. For (a), strict concept mapping requires each concept to have a unique covering table, and the planner rejects the query whenever this condition fails. The Steiner procedure adds only bridge tables and does not reassign any concept. For (b), each join specification is looked up from schema metadata and accepted only after confirming that the key columns exist on both sides. 

Theorem 2 (Deterministic reproducibility) . Given the same database snapshot, planner configuration, interpreted query and fixed runtime environment, BioChirp produces the same join plan and the same set of output rows on every run. Final row order may differ because no explicit global sort is imposed. Proof. Plan construction is deterministic: concept mapping uses direct schema lookup, Steiner connection is computed on a fixed graph and terminal set, and tree rooting follows a fixed root with sorted neighbour traversal. No step involves runtime inference, so the same interpreted query yields the same validated plan under a fixed snapshot and configuration. Execution then applies the same filters, joins and projection steps to the same underlying state, making the output row set invariant across runs. BioChirp does not impose a global ordering on the final output, however, so materialisation strategies such as parallel or chunked processing may change the order in which rows appear without changing which rows are returned. 

Theorem 3 (Completeness relative to database state) . If execution completes successfully, the output contains every unique projected row that satisfies the resolved entity filters and the validated join plan. Proof. The execution engine scans the filtered contents of each participating table and applies the validated joins without token-budget limits, result summarisation or implicit pagination. Results are then projected to the requested output columns and deduplicated before return. Theorem 3 distinguishes BioChirp from language-model outputs constrained by context length and from tool-calling pipelines in which retrieved results may be truncated or summarised before final presentation. 

6 Complexity 

Let n = |V |, e = |E| and m = |C |. Under direct schema lookup, strict concept mapping requires at most O(nm ) table-membership checks, as each active concept may be compared against all tables. Constructing the schema graph from declared foreign-key metadata requires O(n + e)

time, and rooting or traversing the resulting Steiner tree is linear in the size of that tree. Mehlhorn’s Steiner approximation runs in worst-case time O(e + n log n) 25 .In practice, planning latency is negligible relative to query interpretation and data retrieval for the schema sizes used in BioChirp.
