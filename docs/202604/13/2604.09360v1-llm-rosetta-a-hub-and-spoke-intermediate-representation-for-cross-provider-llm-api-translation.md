## 摘要
大语言模型（LLM）供应商的迅速增加——每个供应商都提供专有的 API 格式——导致了一个碎片化的生态系统，使得应用程序与特定供应商紧密耦合。切换或桥接供应商需要 $O(N^2)$ 个双边适配器，这阻碍了可移植性和多供应商架构。我们观察到，尽管存在显著的语法差异，但主要的 LLM API 共享一个共同的语义核心：实际挑战在于语法变化的组合表面，而非深层的语义不兼容。基于这一发现，我们提出了 LLM-Rosetta，这是一个基于星型中间表示（IR）的开源转换框架。该 IR 通过 9 种类型的内容模型和 10 种类型的流事件模式，捕捉了共享的语义核心——包括消息、内容部分、工具调用、推理轨迹和生成控制。模块化的操作组合（Ops-composition）转换器架构使得每种 API 标准都可以独立添加。LLM-Rosetta 支持请求和响应负载的双向转换（供应商到 IR 再到供应商），包括具有状态上下文管理的块级流式传输。我们为四种 API 标准（OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 和 Google GenAI）实现了转换器，涵盖了绝大多数商业供应商。实验评估表明，该框架具有无损的往返保真度、正确的流式行为以及低于 100 微秒的转换开销——在提供双向性和供应商中立性的同时，其性能可与 LiteLLM 的单次转换方法相媲美。LLM-Rosetta 通过了 Open Responses 合规性测试套件，并已在阿贡国家实验室（Argonne National Laboratory）的生产环境中部署。代码可在 https://github.com/Oaklight/llm-rosetta 获取。

## Abstract
The rapid proliferation of Large Language Model (LLM) providers--each exposing proprietary API formats--has created a fragmented ecosystem where applications become tightly coupled to individual vendors. Switching or bridging providers requires $O(N^2)$ bilateral adapters, impeding portability and multi-provider architectures. We observe that despite substantial syntactic divergence, the major LLM APIs share a common semantic core: the practical challenge is the combinatorial surface of syntactic variations, not deep semantic incompatibility. Based on this finding, we present LLM-Rosetta, an open-source translation framework built on a hub-and-spoke Intermediate Representation (IR) that captures the shared semantic core--messages, content parts, tool calls, reasoning traces, and generation controls--in a 9-type content model and 10-type stream event schema. A modular Ops-composition converter architecture enables each API standard to be added independently. LLM-Rosetta supports bidirectional conversion (provider-to-IR-to-provider) for both request and response payloads, including chunk-level streaming with stateful context management. We implement converters for four API standards (OpenAI Chat Completions, OpenAI Responses, Anthropic Messages, and Google GenAI), covering the vast majority of commercial providers. Empirical evaluation demonstrates lossless round-trip fidelity, correct streaming behavior, and sub-100 microsecond conversion overhead--competitive with LiteLLM's single-pass approach while providing bidirectionality and provider neutrality. LLM-Rosetta passes the Open Responses compliance suite and is deployed in production at Argonne National Laboratory. Code is available at https://github.com/Oaklight/llm-rosetta.

### 论文总结：LLM-Rosetta 跨供应商 LLM API 转换框架

#### 1. 核心问题与整体含义（研究动机和背景）
随着大语言模型（LLM）供应商（如 OpenAI, Anthropic, Google 等）的激增，各家均采用私有的 API 格式。这种碎片化导致了两个主要问题：
*   **供应商锁定（Vendor Lock-in）：** 开发者被迫编写特定于供应商的胶水代码，难以灵活切换模型。
*   **$O(N^2)$ 适配难题：** 若要在 $N$ 个供应商之间实现两两互通，需要编写 $N^2$ 个双边适配器。
论文观察到，尽管各 API 语法差异巨大，但其**语义核心高度一致**（如消息角色、工具调用、流式输出等）。因此，研究动机是建立一个通用的中间表示（IR），将适配复杂度降低到 $O(N)$。

#### 2. 方法论：核心思想与关键技术
LLM-Rosetta 采用了编译器设计中常见的**星型（Hub-and-Spoke）架构**：
*   **中间表示（IR）：** 定义了一个供应商中立的语义层，包含 **9 种内容类型**（文本、图像、工具调用、推理链等）和 **10 种流事件模式**（流开始、内容块增量、工具调用增量等）。
*   **操作组合（Ops-composition）架构：** 将转换逻辑解耦为四个正交模块：
    1.  **ContentOps：** 处理原子内容（如 Base64 图像、工具输入）。
    2.  **MessageOps：** 处理消息序列和角色映射（如 System 提示词的位置）。
    3.  **ToolOps：** 处理工具定义和选择逻辑。
    4.  **ConfigOps：** 处理生成参数（Temperature, Top-p 等）。
*   **双向转换与流式状态管理：** 支持“供应商 $\leftrightarrow$ IR $\leftrightarrow$ 供应商”的双向路径。针对流式传输，引入了 `StreamContext` 来管理跨数据块的状态（如累积工具调用参数），确保在不同 SSE（Server-Sent Events）架构间转换时的顺序正确性。

#### 3. 实验设计
*   **测试场景：** 涵盖简单文本对话、多模态输入、工具调用、推理链（Reasoning/Thinking）以及复杂的生成配置。
*   **Benchmark 与对比方法：**
    *   **LiteLLM：** 作为性能基准，对比其单向转换（OpenAI $\rightarrow$ 其他）的延迟。
    *   **Open Responses 合规性套件：** 用于验证 API 实现的标准化程度。
    *   **往返保真度测试：** 验证 $A \rightarrow IR \rightarrow A$ 转换后数据是否无损。
    *   **跨供应商转换测试：** 验证 $A \rightarrow IR \rightarrow B$ 的语义一致性。

#### 4. 资源与算力
*   **算力需求：** 由于该框架是 API 翻译层而非模型本身，其运行不依赖 GPU。

#### 5. 实验数量与充分性
*   **实验规模：** 论文共运行了 **1,364 组单元测试**，其中包含 987 个转换器级别测试和 255 个流式测试。
*   **充分性：** 实验覆盖了目前市场上主流的四种 API 标准（OpenAI Chat, OpenAI Responses, Anthropic Messages, Google GenAI），这些标准覆盖了绝大多数商业 LLM。
*   **客观性：** 通过了第三方的 Open Responses 合规性套件，并在阿贡国家实验室（Argonne National Laboratory）的生产环境（Argo-Proxy）中进行了实际部署验证，证明了其在真实高并发场景下的鲁棒性。

#### 6. 主要结论与发现
*   **极低开销：** 转换延迟中位数低于 **100 微秒（$\mu$s）**，仅占端到端网络延迟的不到 0.01%，性能与 LiteLLM 相当，但提供了更强的双向性和中立性。
*   **无损转换：** 在“保留模式（Preserve mode）”下，往返转换可实现字段级的完全一致。
*   **语义对齐：** 证明了不同厂商的复杂特性（如 Anthropic 的思维块与 Google 的推理部分）可以通过 IR 实现完美的语义对齐。

#### 7. 优点
*   **架构优雅：** 采用星型 IR 解决了适配器爆炸问题，模块化设计使添加新供应商变得简单。
*   **双向性：** 不像 LiteLLM 强绑定 OpenAI 格式，LLM-Rosetta 允许任何格式作为源或目标。
*   **生产就绪：** 针对流式传输中的状态乱序、工具调用碎片等细节处理非常成熟，且有实际生产部署案例。

#### 8. 不足与局限
*   **模态覆盖：** 目前仅专注于 Chat/Completions 模态，尚未覆盖 Embedding、微调（Fine-tuning）或 Batch 处理 API。
*   **维护成本：** 随着供应商 API 的快速迭代，转换器逻辑需要持续更新以支持新字段。
*   **语义鸿沟：** 某些特定厂商的独有功能（如 Anthropic 的显式缓存断点）在转换为其他不支持该功能的厂商格式时，不可避免地会丢失信息（尽管 IR 尝试通过扩展字段保留）。
