## 摘要
大语言模型（LLM）智能体在长上下文交互中经常面临挑战。随着智能体积累更多的交互历史，滑动窗口和提示词压缩等上下文管理方法可能会遗漏后续步骤所依赖的早期结构化信息。最近的基于检索的记忆系统虽然能提取相关内容，但仍忽视了多步推理所需的因果和逻辑结构。我们推出了 ContextWeaver，这是一个选择性且具有依赖结构化的记忆框架，它将智能体的交互轨迹组织成推理步骤图，并为未来的行动选择相关的上下文。与之前的上下文管理方法不同，ContextWeaver 支持：（1）基于依赖的构建和遍历，将每一步与其所依赖的早期步骤联系起来；（2）紧凑的依赖摘要，将从根到步骤的推理路径压缩为可重用的单元；以及（3）一个结合了执行反馈的轻量级验证层。在 SWE-Bench Verified 和 Lite 基准测试中，ContextWeaver 在 pass@1 指标上优于滑动窗口基准，同时减少了推理步骤和 Token 使用量。我们的观察表明，建模逻辑依赖关系为使用工具的 LLM 智能体提供了一种稳定且可扩展的记忆机制。

## Abstract
Large language model (LLM) agents often struggle in long-context interactions. As the agent accumulates more interaction history, context management approaches such as sliding window and prompt compression may omit earlier structured information that later steps rely on. Recent retrieval-based memory systems surface relevant content but still overlook the causal and logical structure needed for multi-step reasoning. We introduce ContextWeaver, a selective and dependency-structured memory framework that organizes an agent's interaction trace into a graph of reasoning steps and selects the relevant context for future actions. Unlike prior context management approaches, ContextWeaver supports: (1) dependency-based construction and traversal that link each step to the earlier steps it relies on; (2) compact dependency summarization that condenses root-to-step reasoning paths into reusable units; and (3) a lightweight validation layer that incorporates execution feedback. On the SWE-Bench Verified and Lite benchmarks, ContextWeaver improves performance over a sliding-window baseline in pass@1, while reducing reasoning steps and token usage. Our observations suggest that modeling logical dependencies provides a stable and scalable memory mechanism for LLM agents that use tools.

#### 1. 核心问题与整体含义（研究动机和背景）
大语言模型（LLM）智能体在处理复杂、长程任务（如软件工程修复）时，交互历史会迅速积累并超出上下文窗口限制。现有的管理方法（如滑动窗口、提示词压缩或基于语义相似度的检索）存在显著缺陷：它们往往只关注**近期性**或**表面相似性**，而忽略了推理步骤之间的**逻辑依赖和因果关系**。这导致智能体在长任务中容易丢失关键的早期决策信息，产生重复劳动或逻辑断裂。本文的研究动机是构建一种能够识别并保留“推理路径”的记忆系统，确保智能体在有限的 Token 预算下，始终能看到对其下一步行动最具逻辑支撑力的历史上下文。

#### 2. 方法论：核心思想与关键技术
ContextWeaver 的核心思想是将智能体的交互轨迹组织为一个**有向无环图（DAG）**，而非线性的消息流。其关键技术流程如下：
*   **依赖感知构建（Dependency-Aware Construction）**：将每个推理步骤（思考、行动、观察）提取为结构化节点。利用 LLM 作为“逻辑依赖分析器”，识别当前步骤所依赖的前序节点（Parent Selection），从而构建依赖图。
*   **祖先依赖提取（Ancestry Construction）**：通过广度优先搜索（BFS）从当前节点向上遍历，提取所有直接或间接支撑当前步骤的“祖先”节点。
*   **上下文编织（Context Weaving）**：在生成下一次提示词时，对属于“祖先路径”的节点保留完整的交互细节，而对非相关节点仅保留摘要或省略观察结果，从而在 Token 限制内最大化保留逻辑链条。
*   **依赖摘要器（Dependency Summarizer）**：增量式地为每个节点生成从根节点到该点的推理路径摘要，提高可解释性并减少重复计算。
*   **验证与测试层（Validation Layer）**：记录每个步骤的执行反馈（如测试通过/失败）。失败或被替代（Superseded）的节点在后续构建中会被跳过，防止智能体基于错误的假设进行推理。

#### 6. 主要结论与发现
*   **性能提升**：ContextWeaver 在 Pass@1 指标上显著优于滑动窗口。例如，使用 Claude 3.5 Sonnet 时，在 Verified 集合上从 63.2% 提升至 66.0%。
*   **效率优化**：在提升成功率的同时，ContextWeaver 减少了解决问题所需的平均推理步骤（约减少 4.7%-7.3%）和每个成功修复所需的 Token 消耗。
*   **稳定性增强**：相比滑动窗口，ContextWeaver 在多次运行中的性能波动更小（标准差更低），表明结构化记忆能提供更稳定的推理支撑。
*   **适用场景**：依赖结构化记忆在需要跨文件协作、处理复杂逻辑依赖的任务中优势最明显；而在简单的线性任务中，滑动窗口表现尚可。

#### 7. 优点
*   **逻辑驱动**：突破了传统的“时间近邻”假设，通过逻辑依赖选择上下文，更符合人类解决复杂问题的思维方式。
*   **增量式设计**：依赖摘要和图构建是增量的，避免了每次交互都重新处理整个历史，具有较好的扩展性。
*   **闭环验证**：引入验证层，利用外部执行反馈（测试结果）动态调整记忆的可靠性，减少了“幻觉”的累积。

#### 8. 不足与局限
*   **依赖分析器开销**：需要额外的 LLM 调用来分析节点间的依赖关系，虽然减少了总步骤，但单步成本略有增加。
*   **领域局限性**：目前主要在代码修复（SWE-Bench）这种具有明确执行反馈的场景下验证，在缺乏自动测试工具的开放域任务中，验证层的效果可能受限。
*   **模型依赖性**：记忆构建的质量高度依赖于“逻辑分析器”的能力，如果底层模型无法准确识别依赖关系，可能会导致关键上下文丢失。
