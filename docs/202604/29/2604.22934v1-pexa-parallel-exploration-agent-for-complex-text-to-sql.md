## 摘要
基于大语言模型（LLM）的 Text-to-SQL 智能体通常面临延迟与性能之间的权衡，即性能的提升往往以延迟为代价，反之亦然。我们从软件测试覆盖率的角度重新构建了 Text-to-SQL 生成过程，其中原始查询被准备为一组包含更简单、原子化 SQL 的测试用例，这些用例并行执行，共同确保对原始查询的语义覆盖。在对测试用例覆盖率进行迭代后，仅在收集到足够信息时才生成最终 SQL，并利用已探索的测试用例 SQL 来辅助最终生成。我们在最先进的 Text-to-SQL 基准测试 Spider 2.0 上验证了我们的框架，达到了 70.2% 的执行准确率，刷新了该领域的最高水平。

## Abstract
LLM-based agents for text-to-SQL often struggle with latency-performance trade-off, where performance improvements come at the cost of latency or vice versa. We reformulate text-to-SQL generation within the lens of software test coverage where the original query is prepared with a suite of test cases with simpler, atomic SQLs that are executed in parallel and together ensure semantic coverage of the original query. After iterating on test case coverage, the final SQL is generated only when enough information is gathered, leveraging the explored test case SQLs to ground the final generation. We validated our framework on a state-of-the-art benchmark for text-to-SQL, Spider 2.0, achieving a new state-of-the-art with 70.2% execution accuracy.

### 2. 方法论：软件测试视角的并行探索
PExA 框架的核心思想是将复杂的自然语言查询拆解为一组简单的、可验证的“单元测试用例”，通过并行执行这些测试来收集证据，最后合成最终 SQL。

*   **核心子智能体（Sub-Agents）**：
    1.  **Planner（规划者）**：负责“测试规划”。将用户查询分解为多个独立的、自包含的自然语言“探测问题”（Probes），每个探测问题针对查询的一个语义维度（如特定的过滤条件、聚合或连接）。
    2.  **Test Case Generator（测试用例生成者）**：负责“测试执行”。将每个探测问题转化为可执行的 SQL，并利用 SQL Executor 工具在数据库上运行。它采用**单步多路径搜索**，在一次调用中生成多个候选 SQL 以提高成功率。
    3.  **SQL Proposer（SQL 提议者）**：负责“测试集成”。收集所有成功、失败及探索性的测试结果，利用这些上下文信息合成最终的长格式 SQL。
*   **关键技术细节**：
    *   **并行化策略**：包括并行规划（单次生成所有探测点）、并行执行（所有测试用例同时运行）和单步多路径搜索（减少顺序重试）。
    *   **语义验证器（Semantic Verifier）**：通过将生成的 SQL 反向翻译为自然语言，并与原始需求对比，确保语义一致性。
    *   **数据库压缩**：在生成测试用例前，先进行轻量级的模式链接（Schema Linking）以缩小搜索范围。

### 6. 主要结论与发现
*   **性能突破**：PExA 在 Spider 2.0 上达到了 **70.2%** 的执行准确率，创下了提交时的 SOTA（最高纪录）。
*   **延迟优化**：通过并行化，PExA 的延迟曲线被“拉平”，总耗时受限于最慢的单个操作而非所有操作之和。理论分析显示其延迟比顺序执行降低了约 2 倍。
*   **模型协同**：发现 GPT-o3 和 GPT-5 在 SQL 生成和长上下文推理方面表现最强，而 Claude 模型在规划阶段表现良好，但在复杂 SQL 合成阶段略逊一筹。

### 7. 优点与亮点
*   **视角新颖**：将 Text-to-SQL 类比为软件测试覆盖率，为解决复杂逻辑分解提供了严谨的工程化思路。
*   **并行架构**：有效地解决了 Agent 框架中普遍存在的“高性能必高延迟”的痛点，提高了 Pareto 最优性。
*   **鲁棒性**：通过“过度生成”测试用例和多路径搜索，增强了对复杂数据库模式的探索能力，减少了因单次推理错误导致的失败。

### 8. 不足与局限
*   **成本高昂**：并行探索意味着更多的 API 调用次数，对于大规模商业应用来说，Token 消耗和经济成本是一个挑战。
*   **依赖闭源模型**：实验高度依赖于 GPT-o3 等顶级闭源模型，在开源模型上的泛化能力和表现尚未得到充分验证。
*   **错误瓶颈**：错误分析显示，主要的失败源于高层语义理解错误（Incorrect Approach），这表明即便有强大的并行探索，底座模型的逻辑推理上限仍是最终瓶颈。
