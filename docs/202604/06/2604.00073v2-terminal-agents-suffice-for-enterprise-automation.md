## 摘要
人们对于构建能够与数字平台交互以自主执行有意义的企业任务的智能体表现出日益增长的兴趣。在已探索的方法中，包括基于模型上下文协议（MCP）等抽象构建的工具增强型智能体，以及通过图形界面操作的网页智能体。然而，考虑到成本和运行开销，目前尚不清楚此类复杂的智能体系统是否必要。我们认为，仅配备终端和文件系统的编程智能体，通过直接与平台 API 交互，可以更有效地解决许多企业任务。我们在多种真实世界系统中评估了这一假设，并表明这些底层终端智能体的表现与更复杂的智能体架构相当甚至更优。我们的研究结果表明，简单的编程接口结合强大的基础模型，足以满足实际的企业自动化需求。

## Abstract
There has been growing interest in building agents that can interact with digital platforms to execute meaningful enterprise tasks autonomously. Among the approaches explored are tool-augmented agents built on abstractions such as Model Context Protocol (MCP) and web agents that operate through graphical interfaces. Yet, it remains unclear whether such complex agentic systems are necessary given their cost and operational overhead. We argue that a coding agent equipped only with a terminal and a filesystem can solve many enterprise tasks more effectively by interacting directly with platform APIs. We evaluate this hypothesis across diverse real-world systems and show that these low-level terminal agents match or outperform more complex agent architectures. Our findings suggest that simple programmatic interfaces, combined with strong foundation models, are sufficient for practical enterprise automation.

#### 1. 核心问题与整体含义（研究动机和背景）
随着大语言模型（LLM）的发展，构建能够自主执行企业任务（如 IT 服务管理、ERP 操作）的智能体成为热点。目前主流方向有二：一是**GUI 驱动的网页智能体**（通过模拟点击和截图操作），二是**工具增强型智能体**（通过 MCP 等协议调用预定义的工具集）。
然而，这些方法存在明显弊端：网页智能体操作链条长、易碎且成本极高；工具增强型智能体则受限于预设工具的表达能力，缺乏灵活性。本论文的核心问题是：**在拥有稳定 API 的企业环境中，是否真的需要这些复杂的抽象层？** 作者提出，一个仅需终端（Terminal）和文件系统的简单编码智能体，通过直接调用 API，可能在效率和效果上都优于复杂架构。

#### 2. 论文提出的方法论：StarShell
作者提出了名为 **StarShell** 的终端智能体框架，其核心思想是将企业自动化简化为“编码与执行”任务。
*   **核心思想**：智能体运行在一个 REPL（读取-求值-打印）循环中。它不依赖预设工具，而是通过编写 Bash 命令（如 `curl`）或 Python 脚本直接与平台的 REST API 交互。
*   **关键技术细节**：
    *   **终端接口**：提供执行环境，允许智能体动态发现 API 端点、处理 JSON 负载并进行错误恢复。
    *   **文件系统**：作为持久化状态存储。智能体可以读取本地化的平台文档，并存储自生成的“技能”（Skills）。
    *   **技能积累机制**：智能体在执行任务过程中，会将成功的操作流程、字段映射关系和避坑指南记录在 `skills/` 目录下，供后续任务复用。
    *   **交互逻辑**：推理 -> 生成代码 -> 执行 -> 观察输出 -> 修正。

*   **实验规模**：总计进行了 **729 个独立任务**的评估，且每个任务在 4 种不同的 LLM 底座上运行，总实验组数超过 8000 组（考虑不同范式对比）。

    *   对比了有无文档访问（Documentation）的影响。

#### 6. 主要结论与发现
*   **终端智能体胜出**：在大多数场景下，终端智能体的成功率持平或超过 Web 智能体，且**成本通常低一个数量级**（例如在 ServiceNow 上成本仅为 Web 智能体的 1/5 到 1/9）。
*   **MCP 局限性**：工具增强型（MCP）智能体表现最差，主要原因是预设工具无法覆盖所有 API 参数，导致其在处理复杂查询时显得过于僵化。
*   **文档的双刃剑效应**：访问官方文档并不总是有效。如果文档是面向人类 UI 操作的，反而会误导智能体；而面向任务的 API 文档则有显著帮助。
*   **技能积累的价值**：允许智能体记录“技能”能显著提升在陌生平台（如 ERPNext）上的表现，并进一步降低探索成本。

#### 7. 优点
*   **架构极简**：挑战了“智能体需要复杂中间层”的固有认知，证明了底层接口的强大。
*   **高性价比**：为企业提供了一种既能保证高成功率，又能大幅削减 Token 消耗成本的方案。
*   **鲁棒性强**：通过代码重试和文件系统缓存，终端智能体展现出了比 GUI 智能体更强的自我修复能力。

#### 8. 不足与局限
*   **UI 依赖型任务失效**：对于没有 API 支持的操作（如某些复杂的拖拽式工作流编辑器）或需要视觉理解的任务（如从渲染后的图表中提取趋势），终端智能体无法胜任。
*   **安全风险**：终端智能体拥有执行 Bash 命令的权限，在生产环境中需要极严苛的权限控制和审计机制。
*   **API 依赖**：该方法的前提是企业平台必须提供稳定且功能完备的 API，对于老旧的“孤岛”系统，仍需依赖 Web 智能体。
