Abstract. Current approaches for knowledge graph construction with RML focus on full RDF graph materialization without considering user queries. As a result, mapping engines are inefficient in dynamic query environments, materializing large graphs even when only a small subset is needed to answer user queries. In this paper, we formally define sat-isfiability for SPARQL queries with respect to RDF data obtained via RML mappings and use this property to prune RML mappings for par-tial RDF graph materialization. Evaluation on the GTFS-Madrid bench-mark shows that pruning significantly reduces materialization time, and RDF graph size while also noticeably improving querying time. Thus, enabling existing materialization engines to efficiently support generat-ing RDF graphs in dynamic federated querying environment where user queries change frequently. 

## 1 Introduction 

State-of-the-art knowledge graph generation approaches generate RDF graphs from structured data like relational databases, or even semi-structured data such as JSON and XML. These approaches either rely on a mapping language (mate-rialization), such as RML [6,9] and SPARQL-Generate [11], granting them access to more diverse types of data sources, including those without a query language for partial retrieval of data, or they rely on translating SPARQL queries to equiv-alent queries (virtualization) supported by the underlying data sources, such as SQL, to generate a subset of the RDF graph necessary to answer the user’s query. To date, materialization approaches ignore user queries when generating RDF graphs, while virtualization approaches are limited by the types of data sources that they support. An approach that supports mapping heterogeneous types of data to RDF while considering user queries would unlock significant opportunities, especially for federated querying. Federation engines would be able to provide access to diverse types of data without being constrained by the fact that the aforemen-tioned virtualization approaches support only data sources with query languages, nor by the materialization approach of always materializing the full RDF graph, of which a significant portion may be irrelevant for the given query. In this work, we combine the support of heterogeneous types of data sources (with or without query languages) from materialization with the query-aware efficiency of virtualization to generate an RDF graph. Specifically, we use RML

This ap-proach advances federated querying by enabling query endpoints that support heterogeneous types of data sources while being efficient and query-aware as the virtualization-based endpoints. Our main contribution is an algorithm for pruning an RML mapping for a given SPARQL query (Section 6). In order to define the algorithm, we first de-fine the syntax and the semantics of mapping expressions that can be derived from an RML mapping document (Section 3.3 and 3.4). Using these mapping expressions, we define the notion of satisfiability of SPARQL triple patterns over mapping expressions, and formally show that determining the satisfiability of a triple pattern over a mapping expression is undecidable, which constitutes our second contribution (Section 4). Although the decision problem of satisfiability is undecidable, we show that there are cases where a given triple pattern is con-firmed to be not satisfiable over a mapping expression (Section 5). These formal results together provide the foundation for the pruning algorithm. As our final contribution, we show using a benchmark that an existing mapping engine can benefit from our pruning technique without modification, for faster materializa-tion and query time while generating a smaller RDF graph (Section 7).

## 3 Preliminaries 

We formalize our pruning approach in terms of the RML-related mapping algebra of Min Oo and Hartig [12]. This section provides the relevant background for this work by introducing the concepts of that algebra, and of RDF and SPARQL. 

3.1 Relevant Concepts of RDF and SPARQL 

Let S be the countably infinite set of all possible strings, and I be the subset of 

S that consists of all valid IRIs. L is the countably infinite set of all RDF literals where every such literal is a pair (lex , dt ) ∈ S × I in which lex is the lexical form and dt is the datatype IRI of the literal. Moreover, B is the countably infinite set of blank nodes (and is disjoint from S and L). IRIs, literals, and blank nodes are jointly referred to as RDF terms . An RDF triple is a tuple 

(s, p, o ) ∈ (I ∪ B ) × I × (I ∪ B ∪ L ), and an RDF graph is a set of RDF triples. For our definitions related to SPARQL we adopt the algebraic syntax of Pérez et al. [13]. Queries are formed using graph patterns , of which the most basic type is a triple pattern , that is, a tuple (s, p, o ) ∈ (I ∪ V ) × (I ∪ V ) × (I ∪ L ∪ V ),where V is a countably infinite set of variables (disjoint from S, L, and B). Other graph patterns can then be constructed recursively, using operators such as AND and OPT [13]. The result of evaluating any such graph pattern P over an RDF graph G is a set, denoted by [[ P ]] G, that consists of so-called solution mappings , which are partial functions of the form μ : V → I ∪ B ∪ L . If P is 4 S. Min Oo and O. Hartig 

a triple pattern tp = ( s, p, o ), then [[ tp ]] G consists of every solution mapping μ

for which dom( μ) = {s, p, o } ∩ V and μ[tp ] ∈ G, where μ[tp ] denotes the triple obtained by replacing the variables in tp according to μ. For other forms of graph patterns, we refer to Pérez et al.’s work for the definition of [[ P ]] G [13].

## 4 Satisfiability 

Our pruning approach is based on a notion of satisfiability of triple patterns with respect to RDF data obtained via mappings. This section provides the relevant formal results, for which we begin by defining this notion of satisfiability. 

Definition 10. Let tp be a triple pattern and M be a TrMap-expression such that {as, a p, a o} ⊆ schema (M ). tp is satisfiable over M if there exists a source assignment σ that is valid input for M such that [[ tp ]] G̸ = ∅ with G being the RDF graph resulting from the mapping relation M [σ].The following result 4 is the first building block of our pruning approach. It shows that, when evaluating a SPARQL graph pattern over an RDF graph cre-ated by applying an RML-specific mapping expression, the correct query result may be produced without explicitly considering every TrMap-expression of the given mapping expression. In particular, it is possible to ignore every TrMap-ex-pression over which none of the triple patterns of the graph pattern is satisfiable. 

Proposition 1. Let P be a graph pattern and let M and M ′ be RML-spe-cific mapping expressions such that TrMaps (M ′) ⊆ TrMaps (M ) and, for every TrMap-expression MTM ∈  TrMaps (M ) \ TrMaps (M ′), none of the triple pat-terns in P is satisfiable over MTM . Then, for every source assignment σ that is valid input for M , it holds that [[ P ]] G = [[ P ]] G′ , where G and G′ are the RDF graphs resulting from the mapping relations M [σ] and M ′[σ], respectively. Based on Proposition 1, we may prune TrMap-expressions from a given RML-specific mapping expression (when used in the context of evaluating graph pat-terns over the RDF graph produced by applying the mapping expression). To do so, however, we need to be able to determine which triple patterns are satisfiable over which TrMap-expressions, which leads us to the following decision problem. 

Problem: Satisfiability(TPoverTrMap) 

Input: a triple pattern tp and a TrMap-expression M

Question: Is tp satisfiable over M ?The following result shows that we cannot answer this question in general. 

Proposition 2. Satisfiability(TPoverTrMap) is undecidable.

## 5 Incompatibility 

While Proposition 2 shows that there is no general way to determine, for any given triple pattern tp and any given TrMap-expression M , whether tp is satisfi-able over M or not, there is a class of cases for which we can at least determine whether a triple pattern is guaranteed to be not satisfiable over a TrMap-expres-sion (which is indeed what we need to know to use Proposition 1 for pruning). 7.1 Benchmark 

We use the GTFS-Madrid benchmark [4] for our evaluation. It enables the gen-eration of a synthetic dataset based on real-world data about the Madrid subway network, scaled by a factor, along with 15 SPARQL queries based on actual user queries. The benchmark task is to answer these queries over the RDF represen-tation of the generated dataset, referred to as the full RDF graph for the rest of the section. The benchmark includes an RML mapping document containing 86 TrMap-expressions to generate the full RDF graph. The provided SPARQL queries are diverse, using SPARQL features such as FILTER , OPTIONAL , and GROUP BY , and contains 3-15 triple patterns each [4]. While GTFS-Madrid benchmark is mainly used to evaluate virtualization engines [4], it has also been adapted for evaluating materialization engines [2], making it relevant for our approach; we prune the benchmark RML mapping by considering a given SPARQL query to generate an RDF graph that is a subset of the full RDF graph. We configure the GTFS-Madrid benchmark to generate the synthetic dataset at scale fac-tor 10. This small scale factor fits our aim, which is to evaluate the performance impact of our pruning technique rather than the scalability of an end-to-end data-mapping pipeline. Furthermore, to limit the impact of a potential imple-mentation error in the underlying mapping engine when parsing complex input data, the benchmark is configured to generate data in CSV.

## 8 Related Work 

As introduced in the beginning of this paper, there exist two major approaches to generating RDF graphs from non-RDF data: materialization and virtualization .On one hand, materialization approaches like SDM-RDFizer [8], Morph-KGC [2], and RMLMapper [17] rely on a mapping language, in this case RML [6,9], to generate the full RDF graph by applying the declaratively defined mappings in RML. This gives materialization approaches access to diverse types of data sources (i.e., any data sources supported by RML). Moreover, materialization-based RDF graph generation is an active research domain, ranging from recent work on language-agnostic formal semantics of materialization [12] to several optimization techniques for materialization [8,2,17,10,7]. However, none of the approaches considers a user’s query while generating an RDF graph. On the other hand, virtualization approaches like Ontop [3], Morph-RDB [14], and Morph-CSV [5] use R2RML [16] mappings as a guide to translate a given SPARQL query to an equivalent query supported by the underlying data source. The translated query is then applied on that source, and the resulting data is returned directly as SPARQL query results. At first glance, this appears more efficient than materialization, as only query-relevant data is retrieved. However, virtualization is limited to using data sources that provide a query language into which a user’s SPARQL query can be translated. Consequently, sources without a query language cannot be used by virtualization systems. While virtualization is query-aware, it is less flexible than materialization in supported data sources, whereas materialization can handle diverse sources but generates unnecessary triples. Our approach bridges this gap by pruning map-pings, before materialization, to retain only those that are relevant to answering the user’s query. 16 S. Min Oo and O. Hartig 

## 9 Concluding Remarks and Future Work 

The approach presented in this work opens up new possibilities for research on using non-RDF data sources when evaluating SPARQL queries over a federation of data sources. More concretely, there are two scenarios in which our prun-ing approach is beneficial. First, a non-RDF data source can be wrapped as a SPARQL endpoint to provide access to an RDF view of the underlying data efficiently by pruning the irrelevant mappings. Second, a federation engine may access non-RDF data sources and convert the retrieved non-RDF data locally at query time. As an example of the latter case, consider a JSON-based REST API as such a data source: if a part of the SPARQL query over the whole federation is meant to be matched in the RDF views of the data from requests to that API, the pruning approach will speed up the process of both materializing the data retrieved from the API and evaluating the relevant sub-pattern of the SPARQL query over this materialized RDF view. Since our pruning approach works at the triple pattern level, a natural next step is to extend it to consider star-shaped and chained queries, allowing sat-isfiability checks across related triple patterns and pruning even more TrMap-expressions. Such an extension will enable materialization engines to generate even smaller RDF graph in less materialization time.
