## 摘要
大语言模型（LLM）智能体正从执行孤立指令的工具调用系统，演变为通过持续、多步交互追求用户目标的任务导向型智能体。然而，现有的个性化工具使用基准大多评估孤立的调用或反应式执行，未能明确智能体是否能够在长期交互中制定、执行和修订显式计划，同时保持用户偏好。为填补这一空白，我们提出 PDEU-Bench（Personalized plan Definition、plan Execution 和 plan Update Benchmark，即个性化计划定义、计划执行与计划更新基准），用于评估个性化工具使用智能体的完整规划生命周期。PDEU-Bench 包含 214 个长时程交互任务，覆盖 12 个日常领域和 94 种工具，并对偏好遵循和计划质量进行分阶段评估。对 15 个代表性开源和闭源 LLM 的广泛评估揭示了局部工具执行与动态规划之间的显著差距：LLM 通常能在单次调用中实例化偏好，却难以构建连贯的计划定义和计划更新。我们进一步评估了主流个性化与记忆增强方法。尽管这些方法改善了特定阶段，但所评估的方法均无法在整个生命周期中可靠地传播用户偏好，且其收益往往无法迁移到后续执行。细粒度错误分析进一步表明，偏好遗漏和冲突在整个规划生命周期中持续存在，凸显了未来研究需要为 LLM 参数化偏好感知的信息检索与记忆能力。我们在附录中提供了相关代码和数据，以支持未来研究。

## Abstract
Large language model (LLM) agents are evolving from tool-calling systems that execute isolated instructions into task-oriented agents that pursue user goals through sustained, multi-step interactions. However, existing benchmarks for personalized tool use largely assess isolated calls or reactive execution, leaving unclear whether agents can formulate, execute, and revise an explicit plan while preserving user preferences throughout long-term interaction. To address this gap, we introduce \textbf{PDEU-Bench} (\textbf{P}ersonalized plan \textbf{D}efinition, plan \textbf{E}xecution, and plan \textbf{U}pdate \textbf{Bench}mark), a benchmark for evaluating the complete planning lifecycle of personalized tool-using agents. PDEU-Bench comprises 214 long-horizon interaction tasks spanning 12 everyday domains and 94 tools, with stage-specific assessments of preference adherence and plan quality. Extensive evaluations of 15 representative open-source and closed-source LLMs reveal a pronounced gap between local tool execution and dynamic planning: LLMs can often instantiate preferences in individual calls, yet struggle to construct coherent plan definition and plan update. We further evaluate mainstream personalization and memory-augmentation methods. Although these methods improve particular stages, none of the evaluated methods reliably propagates user preferences throughout the complete lifecycle, and their gains frequently fail to transfer to subsequent execution. Fine-grained error analysis further reveals that preference omissions and conflicts persist throughout the planning lifecycle, highlighting the need for future research to parameterize LLMs with preference-aware information retrieval and memory capabilities. We provide the relevant code and data in the appendix to support future research.

## 1. 核心问题与研究动机

- **背景**：LLM 智能体正从“执行孤立指令的工具调用系统”转向“通过持续多步交互追求用户目标的任务导向智能体”。个性化工具使用不仅要求选对工具和参数，还要求智能体理解隐含用户偏好、分解复杂目标、协调子目标与工具依赖，并根据环境反馈修订计划。
- **现有缺口**：已有个人化工具使用基准主要评估两类能力：
  - **单轮执行**：孤立地评估一次个性化工具调用；
  - **多轮反应式执行**：延长交互轮次，但仍以任务完成为中心。
  - 二者都没有把“显式、持续演化的计划”作为核心评估对象，因此无法回答：智能体能否在长程交互中**制定、执行并更新**一个可执行且偏好一致的计划？
- **论文核心问题**：个性化工具调用智能体是否具备完整的规划生命周期能力，即计划定义、计划执行、计划更新，并在全过程中保持用户偏好、任务目标和计划依赖。
- **整体含义**：论文提出 PDEU-Bench，把计划视为显式且可版本化的评估对象，将个性化工具使用评估从“孤立调用”推进到“完整规划生命周期”，揭示当前 LLM 在局部执行与动态规划之间的显著能力鸿沟。

## 2. 方法论

### 2.1 核心思想

- 将个性化工具使用任务拆解为三个相互关联但可独立测量的阶段：
  - **Plan Definition（计划定义）**：能否结合不充分用户请求与个性化上下文，生成结构化、可执行、偏好对齐的初始计划。
  - **Plan Execution（计划执行）**：能否按计划选择工具，并将任务约束和用户偏好准确实例化为工具调用参数。
  - **Plan Update（计划更新）**：能否根据工具输出修订后续步骤，同时保留仍然有效的目标、依赖和偏好。
- 计划被维护为**显式、版本化的状态**，每次执行尝试后都必须进行计划更新。

### 2.2 Benchmark 构建

- **环境构建**：
  - 构建可扩展的**离线沙箱**，避免网络波动和在线 API 维护成本，保证评估稳定与可复现。
  - 使用真实世界 API 数据生成输出，例如 Open-Meteo Forecast API 的天气数据；用 GPT-5.5 生成新闻主题数据。
  - 统计显示 85.7% 数据基于真实场景。
  - 数据经清洗、归一化后序列化为统一 JSONL，并使用 `multilingual-e5-small` 预编码，构建离线语义索引。
- **工具构建**：
  - 构建 **94 个功能 API**，覆盖 **12 个日常领域**，包括信息查询和状态改变操作。
  - 遵循 OpenAI function-calling 规范，用 GPT-5.5 生成 API schema，并设计偏好敏感参数。
  - 两名专业标注者人工验证功能正确性和偏好敏感参数，不合格 schema 修订后重查。
- **偏好构建**：
  - 从 PersonaHub 采样 **300 个 persona 种子**，扩展为连贯虚构用户画像，如大五人格、爱好等。
  - 基于偏好构建理论，在十个日常领域中实例化多维偏好。
  - 偏好通过每个用户 **15–25 个两轮 episodic 交互**隐式表达，而非直接给出。
  - 三名专业标注者审核画像、偏好和交互一致性；83.0% 不变保留，17.0% 轻微修订，无丢弃。
- **任务构建**：
  - 为每个用户生成多步规划任务，依据用户画像、直接偏好和可用工具集；用户请求中**不显式暴露偏好描述**。
  - 三名标注者按两个二元标准评估：
    - **偏好相关性**：完成任务是否必须依赖画像偏好；
    - **任务合理性**：请求是否连贯且可用工具执行。
  - 仅在“同时缺乏偏好相关性且无法用工具完成”（F+F）时丢弃；45.0% 无需修订保留，41.0% 修订后保留，14.0% 丢弃。
  - 最终得到 **214 个任务**，其中 68 个简单、146 个困难；难度由三个异构 LLM 评估器多数投票，并由人工检查。

### 2.3 评估流程与指标

- **轨迹获取**：
  - 每个任务在标准化三阶段协议下执行，计划作为显式、版本化状态。

  - 任务输入、工具契约和沙箱状态固定，支持可复现、无泄漏评估。
