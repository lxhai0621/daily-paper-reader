## 摘要
执行长时程任务的LLM智能体会累积后续步骤可能需要的工具结果。将完整历史传递给每次调用代价高昂，即使它能容纳于上下文窗口内；而缩减历史则可能遗漏所需信息。现有上下文管理方法可能忽视较早的工具结果在后续执行中如何被使用，从而将所需信息排除在上下文之外。我们提出ContextRender，它通过一个持久化的执行依赖图来管理上下文。我们开发了工具流分析（Tool-Flow Analysis），以追踪后续操作如何复用较早工具结果中的信息，并提供一种称为“观测复用”（observed reuse）的信号。渲染器将该信号与新近性和语义相关性结合，在固定历史预算内选择结果，并保留被省略的结果以供后续使用。在AppWorld和8目标QA上，使用三种执行模型，ContextRender采用6K历史预算，优于所评估的上下文管理基线，该预算远低于模型的最大上下文窗口。在该预算内，其任务性能接近或超过传递完整历史的表现，同时相对于完整历史将平均推理成本降低10.2%-32.2%。消融实验表明，观测复用提高了任务性能以及对后续被复用结果的保留。

## Abstract
LLM agents performing long-horizon tasks accumulate tool results that later steps may need. Passing the full history to every invocation is costly even when it fits within the context window, while reducing it risks omitting needed information. Existing context management methods can overlook how earlier tool results are used in subsequent execution, leaving needed information out of context. We introduce ContextRender, which manages context through a persistent graph of execution dependencies. We develop Tool-Flow Analysis to track how later operations reuse information from earlier tool results, providing a signal called observed reuse. A renderer combines this signal with recency and semantic relevance to select results within a fixed history budget, retaining omitted results for later use. Across AppWorld and 8-objective QA with three execution models, ContextRender outperforms the evaluated context management baselines using a 6K history budget, well below the models' maximum context windows. Within this budget, it achieves task performance close to or above that of passing the full history while reducing mean inference cost by 10.2%-32.2% relative to Full history. Ablations show that observed reuse improves task performance and retention of results reused later.

# ContextRender 论文结构化总结

## 1. 核心问题与整体含义

- **研究背景**：LLM 智能体在执行长时程任务（软件工程、深度研究、跨应用操作）时，需要数十到数百次模型调用与工具交互，交互历史不断增长。早期工具结果中的信息（如邮箱、ID、路径、配置值）可能在很久之后的步骤中再次被使用。
- **核心矛盾**：
  - 每次调用都传入完整历史：即使未超出上下文窗口，推理成本也很高，还会引入无关上下文噪声。
  - 对历史做剪枝（pruning）或压缩（compaction）：可能把后续步骤所需的细节丢弃或摘要化，导致信息缺失，甚至需要额外的工具调用去重新获取。
- **现有方法的盲点**：剪枝、学习式压缩、检索式记忆、自适应/模型驱动的上下文选择（ACE、PACE、Sculptor、Self-GC 等）大多依据**新近度（recency）**、**语义相关性（relevance）**或**估计重要性**来决定保留什么，但**没有显式追踪早期工具结果在后续执行中是如何被使用的**。
- **论文主张**：上下文管理不应只维护按时间排序的交互列表，而应**追踪执行依赖关系**——即哪些后续模型输出和工具调用复用了早期工具结果中引入的值，并用这种“**观测复用（observed reuse）**”证据来指导每一步该向模型展示哪些历史工具结果。
- **典型例证（AppWorld 分账任务）**：Turn 8 的 `search_contacts` 返回三位室友联系方式；Turn 15/16 使用了 Kathryn 与 Troy 的邮箱，Turn 18 需要 Nancy 的邮箱。此时按新近度或语义相关性都会把 Turn 8 的结果排除，但该结果仍在被持续复用，其完整内容恰恰保留了 Nancy 的邮箱。

## 2. 方法论

### 2.1 核心思想
用一个**持久化上下文图（persistent context graph）**记录完整执行历史与复用关系，在每次模型调用前，于固定历史预算 B 内选择要暴露的**完整**工具结果；未被选中的结果仍保留在图中，可在后续调用中被重新选中。

### 2.2 三大组件

**（1）持久化上下文图 G**
- 按时间顺序存储消息、工具调用、完整工具结果，以及 TFA 识别出的复用边。
- 每个工具结果 r 保存：完整内容、位置、时间戳、内容嵌入向量（用于新近度与语义相关性计算）。

**（2）Tool-Flow Analysis（TFA）**
- 将执行轨迹视为直线式事件序列，抽取“限定值”：模式为 `[A-Za-z0-9][A-Za-z0-9_.\-]{4,}`；引号、括号、逗号、冒号、斜杠、空白作为分隔符；剥离首尾的 `.`、`-`、`_`；长度小于 6 的候选丢弃；必须包含下划线、大写字母、数字、连字符或句点之一；纯 Titlecase 单词排除。
- 复用检测：**精确、区分大小写的整词匹配**；后续模型输出或工具调用中出现某值时，将该次使用链接到**最早包含该值的那个工具结果**（中间副本不改变归属）。
- 复用分数：
  `c_t(r) = Σ_{m ∈ M_t(r)} 1 / n_t(m)`
  其中 `M_t(r)` 是调用 t 之前归属于结果 r 的复用匹配集合，每个不同值在每次后续模型输出/工具调用中只计一次；`n_t(m)` 是调用 t 之前图中包含该匹配值的历史工具结果数量。该权重降低被多个结果共享的值的贡献。

**（3）渲染器（Renderer）**
- 若累积历史 ≤ B，则整体传入；否则按效用分数选择完整工具结果。
- **新近度**：`e^{-λ a_t(r)}`，`a_t(r)` 为结果 r 产生后经过的轮数（1 轮 = 1 次模型调用），λ = 0.3。
- **语义相关性**：查询向量 `q_t = 0.4·unit(emb(x)) + 0.6·unit(emb(f_t))`，x 为任务首个用户消息（截断 2000 字符），f_t 为最新可见的用户+助手消息拼接；相关性 `s_t(r) = max(cos(emb(r), q_t), 0)`。
- **观测复用**：`1 - e^{-γ c_t(r)}`，γ = 0.2（边际递减）。
- **效用函数**：
  `U_t(r) = W_rec·e^{-λ a_t(r)} + W_reuse·(1 - e^{-γ c_t(r)}) + W_rel·s_t(r)`，三者权重均为 1.0。
- **贪心选择与去冗余**：`R_t(r | S) = U_t(r) - 0.5·D(r, S)`，`D(r,S) = max(0, max_{r'∈S} cos(emb(r), emb(r')))`，避免选入内容高度相似的结果。
- **预算可行性**：候选 r 可行当且仅当 `Tok(H_t(S ∪ {r})) ≤ B`；B 覆盖保留的历史消息、关联工具调用与选中结果文本，但**不含系统提示与当前用户消息**（故 B 与模型总上下文窗口不同）。平局按转录顺序、较早者优先。
- **超大结果兜底**：单个结果超过 B 时用 gpt-4.1 压缩，仅当整体仍满足预算才纳入，原始完整内容仍留在图中（实验中未触发）。
- 选中结果按时间顺序而非分数顺序返回；每次调用前重新计算分数，先前被省略的结果可再次入选。

### 2.3 运行时集成
- 作为独立服务器运行，通过适配器接入智能体运行时：适配器上报新消息/工具调用/结果，服务器更新图与复用边，并在每次模型调用前返回预算内渲染的上下文。
- 用 Jac 语言及其 Object Spatial Programming 抽象实现。
- 已接入 5 种运行时：opencode（插件钩子）、AppWorld ReAct agent（替换 `trimmed_messages` 属性）、AppWorld ACON UnifiedAgent（子类化 MemoryManager）、OpenClaw 与 Meta ARE（OpenAI 兼容代理），不修改提示、工具执行、解析与评分逻辑。

## 3. 实验设计

- **数据集 / 场景**：
  - **AppWorld**：跨 9 个模拟应用、约 100 个用户的多步工具使用任务；使用全部 168 个 Test-Normal 与 417 个 Test-Challenge 任务，配 AppWorld ReAct 智能体。
  - **8-objective QA**：用搜索工具回答 8 个 NaturalQuestions 查询并给出整合答案集；100 个测试任务，使用 ACON 发布的智能体实现。
- **执行模型**：GPT-4.1（OpenAI API）、Muse Glimmer 30B（本地 Ollama 0.34.0）、DeepSeek V4 Pro（Ollama Cloud）。temperature = 0.0，top-p = 1.0，seed = 42，每任务每方法执行一次。
- **预算设置**：主设置 B = 6K；GPT-4.1 上 AppWorld 扫描 B ∈ {3, 6, 12, 24}K，QA 扫描 B ∈ {2, 4, 6, 8, 12}K。
- **对比基线（均受同一预算 B 约束）**：
  1. **Prune**：从新到旧保留能装下的完整工具结果；
  2. **Compact (LLM)**：用 LLM 将整个交互历史压缩到预算内；
  3. **Recency + Summary**：保留近期结果、摘要较早结果；
  4. **Semantic Retrieval**：按与最新用户/助手消息的嵌入相似度检索（最近三轮优先，最多占 60% B）；
  5. **ACON**：使用作者发布的压缩实现与优化后的压缩准则；
  6. **Full history**：不做管理，传入全部历史（作为性能与成本参照）。
- **评价指标**：AppWorld 任务目标完成率（TGC，%）、8-objective QA 的 token 级 F1（%）、Later-Used Result Recall（复用发生时完整早期结果是否在上下文中的比例）。
- **成本模型**：`C = [2(1-ρ) + 0.5ρ]P + 8O + 0.13E`（单位：USD/百万 token），P/O/E 为输入、输出、嵌入 token 总量，ρ 为缓存命中比例，统一采用 Full history 中观测到的缓存率；成本在触发上下文管理的固定任务集上求均值并相对 Full history 归一化。
- **召回评测协议**：先记录 GPT-4.1 的 Full history 轨迹，再对每个变体的选择规则回放，判断某结果在复用事件前是否完整可见；词汇复用事件要求 token 首次出现于工具结果，且含大写字母或下划线、长度 ≥ 6。

## 6. 主要结论与发现

- **性能**：在 B = 6K（远低于模型最大上下文窗口）下，ContextRender 在全部 9 个设置中**任务性能均

不低于所有受预算约束的基线，且通常达到或超过 Full history"这样的表述，然后继续展开。

- **性能**：在 B = 6K（远低于模型最大上下文窗口）下，ContextRender 在全部 9 个设置中**任务性能均不低于所有受预算约束的基线**，并且在多数设置中与 Full history 持平或更优。例如在 AppWorld Test-Normal / GPT-4.1 上，ContextRender 达到与 Full history 相当的 TGC，而输入 token 与标准化成本显著更低；在 8-objective QA 上同样取得接近 Full history 的 F1，同时成本明显下降。相较之下，Prune、Compact (LLM)、Recency + Summary、Semantic Retrieval 与 ACON 在相同预算下普遍出现性能下滑，其中 Compact 与 Recency + Summary 在需要复用早期细节的任务上损失最大。
- **成本**：由于只渲染预算内的工具结果并允许重复选择，ContextRender 在保持性能的同时将平均输入 token 与标准化成本压到远低于 Full history 的水平，形成"性能—成本"散点图上的优势前沿（图 4）。表 1 的相对变化显示，其成本相对 Full history 的下降幅度与受预算约束基线相当，但性能下降幅度明显更小。
- **Later-Used Result Recall（关键机制证据）**：ContextRender 在复用事件发生前完整保留相关早期工具结果的比例显著高于所有基线。消融实验（表 2）进一步显示：
  - 仅用新近度（CR–Recency）的召回率随结果年龄快速衰减，>25 轮的结果几乎无法召回；
  - 仅用语义相关性（CR–Relevance）在旧结果语义上与当前查询"看起来相似"时有效，但无法捕获"值被复用但语义不相关"的情形；
  - 新近度+相关性组合（CR–Recency+Relevance）优于单信号，但仍明显低于加入观测复用信号的版本；
  - 完整版本（CR–Full，含 Reuse）在各年龄分桶（≤3、4–10、11–25、>25 轮）上都取得最高召回，说明观测复用信号是捕获"长期、低语义相关但持续被引用"信息的关键。
  - 值得注意的是，加入复用信号后任务性能未必线性提升，作者解释为：召回提升与渲染预算竞争之间存在权衡，部分被召回的结果会挤占其他有用上下文，因此组合信号的效果需要在具体任务分布上评估。
- **预算敏感性**：随 B 增大，各方法性能总体上升并趋近 Full history，但 ContextRender 在较小预算下就已接近饱和，说明其选择策略对预算的利用效率更高；基线在预算较小时下降更陡。
- **总体主张验证**：实验结果支持论文核心论点——**显式追踪早期工具结果的"观测复用"关系，比单纯依赖新近度或语义相关性更能指导上下文选择**，从而在有限预算下兼顾长时程任务性能与推理成本。

## 7. 局限与作者未充分讨论的问题

- **单次运行、无统计检验**：所有任务每方法仅执行一次，未报告方差、置信区间或显著性检验，性能差异的稳健性存疑。
- **复用检测依赖精确词汇匹配**：TFA 基于区分大小写的整词匹配与启发式模式（长度、字符类型），对改写、格式化差异、语义等价但字面不同的复用（如日期格式变化、路径拼接、URL 编码）会漏检；纯 Titlecase 单词、短值（<6）被排除，可能低估复用。
- **召回评测的单一来源**：复用事件集来自单一 GPT-4.1 Full history 轨迹，且以词汇标准定义，可能无法覆盖其他模型或真实用户行为中的复用模式。
- **成本模型简化**：使用统一缓存命中率、标准化参考美元，且不计入图存储、嵌入调用（除 token 计费外）、本地选择计算与服务器通信开销，实际部署成本可能与报告有偏差。
- **超大结果压缩兜底未触发**：论文称该路径在实验中未被触发，因而其正确性与预算行为缺乏实证。
- **嵌入质量与截断**：工具结果仅取前 8000 字符做嵌入，长结果后半部分信息可能影响相关性判断；查询向量权重（0.4/0.6）与效用权重（均为 1.0）、λ=0.3、γ=0.2、去冗余系数 0.5 等超参数未做敏感性分析。
- **泛化范围有限**：仅评估两个基准（AppWorld、8-objective QA）与三种执行模型，未涉及代码仓库级软件工程、浏览器操作等更长时程、更多工具类型的场景。
- **安全与隐私未讨论**：持久化完整工具结果与嵌入可能长期保存敏感信息（邮箱、ID、凭证），论文未讨论访问控制、数据保留策略或与隐私法规的兼容性。

## 8. 对领域与实践的启示

- **从"选择什么"转向"追踪如何使用"**：上下文管理的信号可以从静态属性（新近度、相似度）扩展到**执行依赖的动态证据**，这是一种可迁移到其他智能体记忆系统的设计范式。
- **完整结果优于摘要**：在需要精确值复用的任务中，保留完整工具结果并在需要时重新选中，比有损摘要更能避免"重新获取"的额外调用与错误。
- **可复用的工程抽象**：以独立服务器 + 适配器的方式接入多种运行时（opencode、AppWorld、OpenClaw、Meta ARE），不修改提示与评分逻辑，降低了在现有智能体框架中落地上下文管理的改造成本。
- **预算应显式建模**：将历史预算 B 与模型上下文窗口解耦，使系统可以在远低于窗口上限的预算下运行，直接转化为成本收益。
