## 摘要
搜索智能体会调整其查询，但固定的搜索接口使候选处理和证据呈现不受智能体直接控制。我们的轨迹分析表明，支持性段落可能被检索到却从未传递给智能体；一项同页 oracle 干预表明，改变返回的证据可以减少后续搜索。我们提出程序化搜索智能体（PSA），其将针对候选的局部可执行计算作为搜索动作的单元。PSA 统一了持久候选工作区、灵活的原语组合和有选择的证据呈现。它增量生成程序单元，这些单元复用候选、执行依赖操作，并选择智能体接下来检查的内容。运行时在每个单元内解析指定的数据依赖，而智能体在新证据到来时跨单元调整其搜索策略。我们在 InfoSeek-Eval 和 BrowseComp-Plus 上，使用五种策略骨干且不进行任务特定训练，将 PSA 与基于查询的智能体和基于工具的智能体进行比较。三种接口共享搜索基底，基于工具的智能体还共享 PSA 的原语和持久工作区。相对于基于查询的智能体，PSA 在两个基准上分别将宏平均任务成功率提高了 4.00 和 7.56 个百分点；在各骨干内，最后一步 token 的减少平均为 28.3% 和 33.9%。这些结果支持将智能体控制从查询重构扩展到对检索证据的处理和呈现。代码将在获批后发布。

## Abstract
Search agents adapt their queries, yet fixed search interfaces leave candidate processing and evidence presentation outside the agent's direct control. Our trajectory analysis shows that supporting passages can be retrieved yet never delivered to the agent; a same-page oracle intervention shows that changing the returned evidence can reduce subsequent search. We introduce Programmatic Search Agent (PSA), which makes a local executable computation over candidates the unit of a search action. PSA unifies a persistent candidate workspace, flexible primitive composition, and selective evidence presentation. It incrementally generates program cells that reuse candidates, execute dependent operations, and select what the agent inspects next. The runtime resolves specified data dependencies within each cell, while the agent adapts its search strategy across cells as new evidence arrives. We compare PSA with the Query-based Agent and Tool-based Agent on InfoSeek-Eval and BrowseComp-Plus using five policy backbones without task-specific training. All three interfaces share the search substrate, and the Tool-based Agent also shares PSA's primitives and persistent workspace. Relative to the Query-based Agent, PSA improves macro-averaged task success by 4.00 and 7.56 percentage points on the two benchmarks, respectively; within-backbone reductions in final-step tokens average 28.3% and 33.9%. These results support extending agent control beyond query reformulation to the processing and presentation of retrieved evidence. Code will be released subject to approval.

## 1. 核心问题与研究动机

- **背景**：LLM 搜索智能体已能交替进行推理与检索、改写查询以追踪线索（ReAct、IRCoT、Search-R1 等）。但在主流 `search(query)` 固定接口下，**候选处理与证据呈现**完全由检索流水线决定：保留哪些候选、如何排序、返回哪些段落，智能体都无法直接干预。
- **核心提问**：智能体是否只应改写查询，还是也应控制已检索候选的**处理与呈现**方式？
- **动机性实证分析（基于 BrowseComp-Plus 的 Query-based Agent 轨迹）**：
  - 42.7% 的已验证支持性段落**从未被送达**智能体，尽管它们已进入抽取候选集；后续搜索仅能找回其中 27.2% 的遗漏。平均段落送达召回率为 65.1%。
  - **同页 oracle 干预**：在同一页内用被遗漏的支持段落替换已选段落（保持查询、检索页面、流水线、返回条数不变），在**完全遗漏**情形下使判断式任务成功率提升 16.7 个百分点，后续搜索决策数下降 64.0%；而**部分遗漏**无净收益。
- **整体含义**：瓶颈不只在"找不到证据"，也在"已找到却未被呈现"。应把智能体的控制权从查询重构扩展到证据处理与呈现。

## 2. 方法论：Programmatic Search Agent (PSA)

- **核心思想**：把"对候选集合的**局部可执行计算**"作为搜索动作的基本单元。策略生成受限 Python 程序单元（program cell），运行时执行后返回控制权给策略，由策略解释结果并决定下一步。
- **三大机制**：
  - **持久候选工作区（Persistent Candidate Workspace）**：候选集合作为可寻址对象保留（含源标识、内容引用、检索查询来源），可在后续 cell 中复用、合并、再处理，无需重新检索；工作区通过紧凑投影描述（变量名、类型、集合大小）暴露给策略，而非全部内容。
  - **灵活原语组合（Flexible Primitive Composition）**：五个共享原语——`retrieve`、`filter`、`rerank`、`extract`、`dedupe`；支持变量赋值、集合操作、有界循环与条件分支，可在单个 cell 内表达操作图与数据依赖。
  - **选择性证据呈现（Selective Evidence Presentation）**：cell 的最终变量表达式决定"返回什么观察"，未返回的对象仍保留在工作区，后续可再检查或再处理。
- **形式化流程**：
  - 状态：`s_t = (x, H_t, σ(W_t))`，其中 `x` 为问题，`H_t` 为已执行 cell 与观察历史，`W_t` 为保留的候选集合与变量，`σ` 为紧凑投影。
  - 动作：`a_t ~ π_θ(·|s_t)`，`a_t ∈ {Execute(c)} ∪ {Finish(y)}`。
  - 执行：`(W_{t+1}, o_t) = R(c_t, W_t, D)`，`D` 为固定语料。
  - 历史更新：`H_{t+1} = H_t ∥ (c_t, o_t)`。
- **关键设计点**：区分**数据依赖**（运行时可在 cell 内自动解析）与**需要新模型判断的决策**（留给下一轮策略）；一个 cell 可含单次调用（需即时反馈）或依赖链（逻辑已可完全指定）。

## 3. 实验设计

- **数据集 / Benchmark**：

- **对比方法（三种接口）**：
  - **Query-based Agent**：固定 retrieve–filter–rerank–extract 流水线，支持每次决策多个并行 `search(query)`。
  - **Tool-based Agent**：暴露与 PSA 相同的五个原语和持久别名工作区，但依赖的主阶段需分轮次调用（前一调用的别名需下一轮才能消费）。
  - **PSA**：可在单个受限 Python cell 内表达依赖、集合操作、循环与条件。
- **公平性控制**：三种接口共享**同一检索基底**（Qwen3-Embedding-0.6B 精确内积索引、Qwen3-Reranker-0.6B、Qwen3.5-0.8B 确定性段落抽取）；Tool-based Agent 额外共享 PSA 的原语与持久工作区；统一 20/10/10 每次调用上限与 50 次决策预算；所有模型均**不做任务特定训练**。
- **策略骨干（5 个）**：DeepSeek-V4.1-Flash、Hunyuan-4-Preview（非 think 模式）、GLM-5.3-Flash、Qwen3.8-Flash、GPT-5.6-Luna（低推理强度）。
- **附加实验**：
  - **选择性证据呈现对照**（GLM-5.3-Flash，128 个 BrowseComp-Plus 配对任务）：program-selected feedback vs. full-view feedback。
  - **决策预算敏感性**（Qwen3.8-Flash，同一 128 题队列，10/20/30/40/50 决策上限）。
  - **原语级资源核算**（完整 DeepSeek-V4.1-Flash 轨迹）。

## 6. 主要结论与发现

- **任务成功率**：PSA 在 InfoSeek-Eval 上对全部 5 个骨干取得最高成功率，在 BrowseComp-Plus 上 5 个中 4 个最高（例外为 GPT-5.6-Luna，Tool-based 更高）。宏平均：InfoSeek-Eval 为 **81.53% vs 77.53%（Query）vs 79.73%（Tool）**；BrowseComp-Plus 为 **55.45% vs 47.90% vs 48.12%**，相对 Query-based 提升 **+4.00 与 +7.56 个百分点**。
- **Token 效率**：在全部骨干×数据集比较中 PSA 末步 token 最低；相对 Query-based Agent 平均减少 **28.3%（InfoSeek-Eval）与 33.9%（BrowseComp-Plus）**，相对 Tool-based 减少 46.3% 与 54.5%。例如 Qwen3.8-Flash 在 InfoSeek-Eval 上从 93.9K 降至 23.5K，同时成功率从 72.67% 升至 82.00%。
- **召回率**：BrowseComp-Plus 上 PSA 宏平均 Recall 为 56.87%，高于 Query-based（52.41%）与 Tool-based（55.44%）；5 个骨干中 4 个最高（Qwen3.8-Flash 例外）。
- **证据呈现控制有效**：program-selected feedback 相对 full-view 使返回文本减少 37.2%（配对 bootstrap 95% CI: 7.7–56.6%），点估计成功率 +3.91pp、末步 token −24.5%，说明"保留"与"呈现"可以解耦。
- **预算敏感性**：在 30–50 决策预算下，PSA 成功率高出 11.72–13.28pp 且少用 38.3–40.9% 末步 token；但在 10 决策时 PSA 反而较低（35.16% vs 39.06%）。
- **资源核算**：PSA 在 BrowseComp-Plus 与汇总口径上减少检索、重排、抽取工作量；在 InfoSeek-Eval 上原语调用数反而增加，但成功率提升且 token 下降——收益不依赖统一增加检索计算。

## 7. 优点（方法 / 实验设计亮点）

- **问题定位新颖且有实证支撑**：先用自然轨迹量化"证据送达鸿沟"，再用同页 oracle 干预验证因果方向，动机链条完整，而非仅凭直觉提出方法。
- **接口层面的严格受控比较**：三种接口共享检索基底，Tool-based Agent 与 PSA 共享原语与持久工作区，唯一差异是交互单元（查询 / 单次工具调用 / 程序 cell），使结论归因清晰。
- **"保留"与"呈现"解耦**：持久工作区让候选可反复复用，而观察只是程序选定的视图，避免把全部中间结果塞入上下文——这是对长程搜索上下文管理的实质性改进。
- **无需任务特定训练**：在 5 个异构骨干上零训练即取得一致提升，泛化性好、复现门槛低。
- **效率与效果同时改善**：不仅提升成功率与召回率，还显著降低末步 token，属于"双赢"结果。
- **实验补充充分**：除主表外还有配对反馈对照、预算扫描、原语级资源核算与可读的轨迹案例，评估维度多元。
- **诚实的不确定性报告**：给出 bootstrap 置信区间，并明确区分点估计与显著差异。

- **效率指标的局限**：主要效率度量是"末步 token"（最后一次决策调用的输入+输出 token），未计入**总 token 消耗、墙钟延迟、原语调用次数×单次开销、重排/抽取模型的推理成本**。InfoSeek-Eval 上原语调用数上升即说明，末步 token 的下降不必然等于端到端成本下降；缺少统一成本口径使"效率双赢"的结论需谨慎外推。
- **评测环境与语言覆盖**：两个基准均为英文、固定网页语料、问题可被已有标注支持，属于受控离线设定；未在开放真实网页（时效性、噪声、反爬、动态内容）与多语言场景验证，迁移性未知。
- **安全与工程约束未被讨论**：允许模型生成并执行 Python 程序引入沙箱隔离、资源限额、副作用控制与提示注入（检索到的网页内容可能诱导生成危险代码）等风险，论文未给出威胁模型或防护设计。

## 9. 结论性评价与启示

- **核心贡献定位**：本文的主要价值不在于提出新的检索算法，而在于**重新界定智能体与检索系统的接口边界**——把"处理与呈现已检索候选"从流水线的内部实现提升为智能体可编程控制的一等动作。这一视角与"查询改写"路线正交，可作为现有 ReAct / IRCoT / Search-R1 类框架的接口层扩展。
- **方法—证据的一致性**：动机分析（送达鸿沟 + 同页 oracle 干预）、受控接口对照（共享基底、共享原语、仅改交互单元）、以及效率与效果的同步改善，三者构成较完整的论证闭环，方法设计与诊断结论之间对应关系清晰。
- **证据强度分级**：可较有把握接受的结论包括——PSA 在 5 个骨干上成功率与末步 token 的**方向性一致改善**、选择性证据呈现可显著压缩返回文本（CI 不含零）、以及预算充足时（≥30）的优势稳定。需谨慎对待的结论包括——oracle 总体增益 +9.1pp、选择性反馈 +3.91pp 成功率、以及所有未做多重比较校正的单点估计；这些应视为**提示性证据**而非确证。
- **实践启示**：
  1. 若系统已有稳定检索基底且推理预算充裕，把"候选处理"开放为程序化动作是低风险、无需训练的增益路径；
  2. 上下文管理的关键可能不是"检索多少"，而是"呈现多少"——保留与呈现解耦可直接降低上下文膨胀；
  3. 程序化接口并非普适更优，需为低预算/弱代码能力场景保留查询式回退。
- **后续研究方向建议**（基于本文留下的空白）：量化投影粒度与信息损失的权衡；在真实开放网页与多语言上验证；引入端到端成本口径（延迟、总 token、原语开销）重估效率结论；分析程序执行失败模式与自修复；探索与训练式搜索智能体（RL 微调）的结合，即让策略学习"何时该写程序、何时该直接查询"。

## 10. 总体判断

本文是一篇**问题定义清晰、对照设计严谨、结论方向可信但统计强度中等**的接口层研究。其最大亮点是把一个被忽视的工程瓶颈（证据送达与呈现）转化为可检验的科学问题，并用受控实验给出跨模型的一致信号；最大短板是算力/成本信息缺失、动机队列的事后构造、以及若干关键结论的置信区间跨零，使得部分定量增益仍需独立复现来确认。方法本身不依赖训练、复现门槛低，具备较好的可扩展性与被后续工作继承的潜力。
