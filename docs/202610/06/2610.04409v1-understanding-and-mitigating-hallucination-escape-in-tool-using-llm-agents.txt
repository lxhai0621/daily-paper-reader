## ABSTRACT 

Large language models (LLMs) increasingly serve as autonomous agents that in-voke external tools. However, this capability introduces tool hallucination, selecting incorrect tools or generating invalid calls. Existing mitigation methods report sub-stantial improvements, yet we identify a previously overlooked failure mode that we term Hallucination Escape . These methods reduce hallucination on the tool configuration they are tuned on but increase it on other configurations, canceling out the gain. We further investigate this phenomenon and find that hallucination rises sharply when a model’s intrinsic tool-use tendencies conflict with the current tool configuration, and that existing methods reinforce rather than suppress these tenden-cies, which in turn contributes to hallucination escape. Building on these findings, we propose ESCAPE GUARD , a training-free inference-time method that combines conflict-aware gating with configuration-derived attention enhancement to mitigate tool hallucination while preventing hallucination escape. Across six benchmarks on various models, E SCAPE GUARD reduces tool-selection hallucination by 9.0 pp and suppresses hallucination escape, lowering the cross-configuration mean by 23.7 pp and achieving an 89.1% net improvement in paired-query evaluation. We hope this work can encourage evaluation beyond a single tool configuration and pave the way for more reliable tool-using LLM agents. 

## 1 INTRODUCTION 

Large language models (LLMs) increasingly serve as autonomous agents that call external tools to complete tasks, but this capability introduces a tool hallucination: selecting nonexistent or irrelevant tools ( Tool-selection Hallucination ), or generating invalid arguments ( Tool-usage Hallucination ) (Xu et al., 2025; Zhang et al., 2024; Ke et al., 2026). Unlike text hallucination, which produces plausible but incorrect text, a hallucinated tool call can trigger irreversible operations on real systems, making it a more consequential reliability risk (Zhang et al., 2024). To address this problem, existing methods fall into two families. ❶ Training-based methods reshape model behavior through modified data or objectives: Relign adds hesitation-based deferral (Xu et al., 2025), Gorilla adopts retrieval-aware fine-tuning (Patil et al., 2024), and PALADIN fine-tunes on fault-injected trajectories (Vuddanti et al., 2025); ❷ Steering-based methods instead intervene on internal representations: LinSteer steers tool selection with activation-difference vectors (Wu et al., 2026), and PRISMS applies detector-gated directional interventions (Ke et al., 2026). Investigation (§ 4). To answer this, we examine whether models hold intrinsic tool-use tendencies, as the observed behavior suggests models disregard the runtime tool configuration. Concretely, we elicit model outputs without access to the tool configuration and find that models consistently favor specific tools and argument structures ( ρsel =0 .65 ), with hallucination rising sharply when these preferences conflict with the current configuration. We further validate this finding internally through layerwise probes, which detect the conflict with 86.4% accuracy and predict tool hallucination with an AUROC of 0.82. Finally, we analyze existing mitigation methods and find that they reinforce these tendencies (prior strength +0 .08 on average), with stronger reinforcement associated with larger escape ratios (Ew up to 2.42), explaining why they produce and even exacerbate hallucination escape. 

Solution (§ 5). Building on these findings, we propose ESCAPE GUARD , an inference-time method that mitigates tool hallucination while preventing hallucination escape (Figure 1c). The key idea is to redirect the model’s attention back to the runtime tool configuration when a tendency conflict is detected (Figure 5). Specifically, E SCAPE GUARD reuses the frozen conflict probes to identify high-conflict inputs and, only for those inputs, strengthens attention to tool names and descriptions during selection and to the selected tool’s schema during argument generation. This design ties the corrective signal to the current configuration rather than a fixed tendency, allowing it to naturally adapt as tools or queries change. Across six benchmarks on various models, E SCAPE GUARD reduces tool-selection hallucination by 9.0 pp and argument-name hallucination by up to 67% relative, while effectively suppressing hallucination escape along both dimensions: the cross-configuration mean drops by 23.7 pp, and paired-query evaluation shows an 89.1% net improvement. To summarize, our contributions are as follows: ❶ we identify and formally define hallucination escape, a previously unrecognized failure mode in which mitigation reduces hallucination in the tuned configuration but increases it in others (§ 3); ❷ we reveal the mechanism behind it: models hold intrinsic tool-use tendencies that conflict with changed configurations, and existing methods reinforce these tendencies (§ 4); ❸ we propose E SCAPE GUARD , a training-free inference-time method that mitigates tool hallucination while effectively preventing hallucination escape across models (§ 5). 

## 2 BACKGROUND AND RELATED WORK 

LLM-based Agents and Tool Use. LLMs increasingly serve as autonomous agents that invoke tools to complete tasks. Toolformer introduces self-supervised tool-call learning (Schick et al., 2023), ReAct interleaves reasoning with action (Yao et al., 2023), and ToolLLM scales to real-world APIs (Qin et al., 2024). As these capabilities expand, so does the risk of erroneous tool invocations. 

Tool Hallucination and Mitigation. Tool hallucination occurs when a model’s tool invocation is inconsistent with available tools or task requirements (Xu et al., 2025; Patil et al., 2024; Liu et al., 2026; Xiong et al., 2025), including tool-selection hallucination (invoking nonexistent or irrelevant tools) and tool-usage hallucination (generating undefined parameters or ungrounded values). Existing mitigations includes: ❶ Training-based methods reshape behavior through modified objectives: Relign (Xu et al., 2025) introduces hesitation-based deferral, PALADIN (Vuddanti et al., 2025) improves fault recovery through annotated trajectories, and Gorilla (Patil et al., 2024) reduces API hallucination via retrieval-aware fine-tuning; ❷ Steering-based methods instead intervene on internal activations: LinSteer (Wu et al., 2026) manipulates tool selections via activation steering, and PRISMS (Ke et al., 2026) applies detector-gated interventions for distinct failure modes. However, both evaluate only under the tuned-on tool configuration. ## 3 PHENOMENON : H ALLUCINATION ESCAPE 

Existing mitigation methods report reductions, yet their evaluations keep tool definitions fixed, varying only the number, combination, and availability of tools. In practice, tools serving the same function may differ in naming and argument specifications. We evaluate them under varied tool configurations and queries, revealing a consistent failure mode and defining it as hallucination escape. 3.1 EVALUATION SETUP 

Evaluation Protocol. The cross-configuration evaluation covers two aspects. ❶ Tool Configuration: for each query, the tool list always contains one correct tool whose definition varies systematically. We construct six configurations (Figure 2): C 1 (standard) uses original names, descriptions, and arguments; C 2 (tool replacement) substitutes a functionally equivalent tool with a different name; C 3

(description change) rewrites functional descriptions; C 4 (argument renaming) replaces argument names; C 5 (mixed) simultaneously changes the tool name, description, and argument names; C 6

(distractor injection) adds tools with similar names but mismatched functionality. All configurations were constructed using GPT-5.6-Terra, manually reviewed, and validated to preserve a valid solution (Appendix A). ❷ Query Task: under the same tool list, we construct pairs of related queries requiring different tools to test whether fixing one query introduces errors on another (Appendix B). 

Methods, Models, and Data. We reproduce five mitigation methods spanning both categories. For training-based methods, we adopt Relign (Xu et al., 2025), PALADIN (Vuddanti et al., 2025), and Gorilla (Patil et al., 2024); for steering-based methods, we adopt LinSteer (Wu et al., 2026) and PRISMS (Ke et al., 2026). All use the original code and are trained or calibrated on standard-configuration (C 1) data. Experiments use LLaMA-3.1-8B-Instruct (Meta, 2024) and Qwen-3.5-9B (Qwen Team, 2026). Configuration evaluation data are sampled from BFCL V3 and Seal-Tools (∼1,000 examples × 6 configurations). For query changes, 120 pairs (240 queries) are constructed from BFCL. All are repeated over three random seeds; see Appendix C for dataset selection. 

Evaluation Metrics. ❶ For cross-configuration evaluation, we measure hallucination by: Tool-Selection Hallucination Rate (TSHR), the fraction of queries where the model selects an unavailable or incorrect tool; and Tool-Usage Hallucination Rate (TUHR), conditional on correct selection, decomposed into fabricated argument names (ANHR) and incorrect values (AVHR). Since C 1 – C 3

and C 6 preserve the argument schema, we report TSHR alone; for C 4 and C 5, which also modify arguments, we report OHR = TSHR + (1 − TSHR ) × TUHR. Cross-configuration mean ¯H(m)

and variance Var( m) aggregate these metrics. ❷ For cross-query evaluation, we report Repair Rate (fraction of errors corrected), Transfer Damage Rate (fraction of repairs introducing new errors on the paired query), and Net Improvement = Repair × (1 − Damage ). The two findings above reveal a consistent pattern: existing methods shift hallucination across configurations rather than reducing it overall. We formalize this as follows. 

Definition 3.1 (Hallucination Escape). Let m be a mitigation method and C = {c1, . . . , c K } the configuration set. Method m exhibits hallucination escape if: (1) ∃ C ↓ ⊂ C : H(m, c k) < H (base , c k);(2) ∃ C ↑ ⊂ C \ C ↓: H(m, c j ) > H (base , c j ); (3) ¯H(m) ≥ ¯H(base ).The empirical results show that all five methods satisfy this definition: they reduce hallucination on their tuned configuration yet increase it on others. The pattern manifests across both tool configurations and queries. Meanwhile, tool-usage hallucination remains largely immune to all methods, suggesting a distinct underlying mechanism. ## 4 INVESTIGATION : T HE MECHANISM OF HALLUCINATION ESCAPE 

The previous section shows existing mitigation methods reduce hallucination on their tuned configu-ration but increase it on others. 5.1 DESIGN OF ESCAPE GUARD 

The core idea of E SCAPE GUARD is to detect when a model’s intrinsic tendencies conflict with the runtime tool configuration and, only in those cases, strengthen the model’s attention to the relevant tool definitions. This requires addressing three questions: what to attend to, when to intervene, and 

how to enhance attention. Accordingly, E SCAPE GUARD operates in three stages: input preparation, conflict-aware gating, and context-specific attention enhancement, described below. 

Stage ❶: Input Preparation. Given a query q and tool configuration C, E SCAPE GUARD first identifies the token spans that will serve as attention targets in later stages. Specifically, for each tool t ∈ C, it records the token spans of each tool’s name ( Sname (t)), description ( Sdesc (t)), and argument schema ( Sschema (t)) during input serialization. These spans define what the model should attend to when intervention is triggered.

Ablation Study. We ablate four components on LLaMA-3.1-8B and Qwen-3.5-9B (Appendix H.10, Table H.13). Each contributes: the conflict gate avoids unnecessary reweighting; stage-specific enhancement outperforms random context token enhancement; the correct conflict layers are essential; and input-dependent enhancement outperforms fixed steering vectors. These results show that conflict-aware, configuration-grounded intervention can mitigate tool hallucination without the escape effect that undermines existing approaches. 

## 6 DISCUSSION 

ESCAPE GUARD consistently reduces tool hallucination and prevents hallucination escape across six backbones as an inference-time method. That said, the six tool configurations and architectures studied, though representative, are not exhaustive. The tendency-conflict mechanism accounts weakly for argument-value errors, and E SCAPE GUARD ’s AVHR improvements are correspondingly modest. Gains are also smallest under distractor injection ( C6), likely because confusable tools dilute the enhanced attention signal. Addressing argument-value errors, improving distractor robustness, and extending to broader architectures remain promising directions for future work. 

## 7 CONCLUSION 

We identify hallucination escape, a failure mode in which mitigation methods reduce tool hallucination on their tuned configuration but increase it on others. We trace this to intrinsic tool-use tendencies that existing methods reinforce, and propose E SCAPE GUARD , a training-free method that detects tendency conflicts and redirects attention to the runtime configuration. Across various models and benchmarks, E SCAPE GUARD reduces tool-selection hallucination by 9.0 pp while effectively suppressing hallucination escape. ## A TOOL CONFIGURATION CONSTRUCTION 

A.1 CONFIGURATION CONSTRUCTION RULES 

Tool Replacement Rules ( C2). The replacement tool name uses different lexical forms to re-duce direct matching to the original. For example, currency_conversion.get_rate →

fx_historical_lookup (rather than get_currency_rate , which retains the keywords “currency” and “rate,” allowing the model to infer functionality). The functional description remains complete and accurate, ensuring that the correct answer can be obtained by reading the description. 

Description Change Rules ( C3). The tool name remains unchanged while the functional description’s wording and emphasis are altered, reflecting the versatility of the same tool across different scenarios. For example, the description of currency_conversion.get_rate is “Get the currency conversion rate from one currency to another at a specified date,” which is changed to “Retrieve the foreign exchange mid-market reference between two ISO 4217 currency codes for a given valuation date.” The correct tool-query mapping remains intact. 

Argument Renaming Rules ( C4). Argument names are replaced with alternative surface forms to reduce reliance on familiar names. For example, from_currency → source_unit ,

to_currency → target_unit , date → temporal_ref . The functional descriptions of arguments remain accurate, while their surface forms change. 

Mixed Changes Rules ( C5). The tool name, functional description , and argument names are all simultaneously replaced, with argument order randomly shuffled. This represents the most comprehensive change scenario closest to real-world deployments. 

Distractor Tool Construction Rules ( C6). Injected distractor tools satisfy the following condi-tions: (1) the tool name is highly similar to high-frequency tool names in the model’s prior (e.g., 

currency_conversion.get_rate_forecast vs. currency_conversion.get_ rate ), maximizing naming confusion; (2) the description partially overlaps with but does not fully match the correct tool (e.g., “Get the forecasted future conversion rate trend between two curren-cies” vs. “Get the currency conversion rate from one currency to another at a specified date”), testing the model’s fine-grained discrimination; (3) 2–3 distractor tools are injected per query, ensuring the total tool list length does not exceed 10 (to avoid confounding factors from excessive context length).

17 Preprint A.3 CONFIGURATION QUALITY CONTROL 

All configurations ( C2 – C6) were initially generated with LLM assistance and then independently verified and refined by two authors for consistency. The construction process followed three stages. 

LLM-assisted generation and independent verification. Configuration variants were initially generated by prompting an LLM with the rules in Section A.1. The full set of variants was then independently reviewed and refined through manual verification, correcting cases where the generated output violated a construction rule or introduced unintended cues. Reviewers worked from the same generated candidates without sharing intermediate edits. 

Reconciliation. The two sets were compared at the tool-name, description, argument-name, and distractor levels. Discrepancies (averaging 8.3% of entries across configurations) were resolved by discussion, preferring for the variant that more completely satisfied the stated construction rules. 

Automated validation. After reconciliation, we ran automated checks to verify that (1) every configuration variant preserves a valid reference solution (i.e., the correct tool and its required arguments remain present and invocable), (2) C2 tool names share no content words with the original, (3) C3 descriptions preserve the original tool’s functional scope, (4) C4 argument names differ from the originals in surface form while the schema remains structurally valid, and (5) C6 distractor tools do not duplicate any existing tool in the list. All queries passed these checks. The validation scripts will be released with the supplementary code.

## C DATASET SELECTION AND DATA CONSTRUCTION 

This appendix describes the data used for controlled evaluation in § 3, behavioral analysis in § 4.1, and internal representation analysis in § 4.2. C.1 CONTROLLED AND PAIRED -Q UERY EVALUATION 

The controlled evaluation uses the single-turn portions of BFCL V3 and Seal-Tools, whose explicit tool definitions and reference calls support controlled configuration changes while preserving a valid solution. Approximately 1,000 source queries yield approximately 6,000 evaluations across C1–C6,with three random seeds, per configuration to account for sampling variance. 18 Preprint The paired-query evaluation uses the BFCL V3 single-turn multi-tool subset: 30 pairs in each of four domains, totaling 120 pairs (240 queries). Each pair shares one tool list but requires different correct tools (Appendix B), isolating query-level effects. C.2 BEHAVIORAL ANALYSIS SET 

§ 4.1 uses a behavioral set of 300 queries sampled equally from BFCL, Seal-Tools, and Glaive Function Calling V2. We select 100 queries from each benchmark to reduce dataset-specific bias while retaining diverse tool names, descriptions, and argument schemas. All selected examples satisfy three criteria: the correct tool is explicitly identifiable, the runtime tool configuration contains a structured argument schema, and the example supports the construction of both tool-selection and argument-level conflicts. For Seal-Tools, we retain single-tool examples with complete tool definitions and valid argument schemas. For Glaive Function Calling V2, we retain examples with unambiguous reference calls and parsable structured arguments. For each query, we construct three conditions: the aligned condition A, the tool-selection conflict condition Btool , and the argument-level conflict condition Barg . In A, the runtime tool and argument schema are consistent with the model’s elicited preference. In Btool , the preferred tool is replaced by a functionally equivalent alternative with a different name and a meaning-preserving description rewrite, while the argument schema remains unchanged. In Barg , the tool name and description remain unchanged, but argument names or types are modified while preserving a valid solution. For closed-book elicitation, we sample K = 10 outputs per query at temperature 0.7. Contextual evaluation under A, Btool , and Barg uses greedy decoding. C.3 PROBING CORPUS AND DATA SPLITS 

The internal representation analysis in § 4.2 expands the behavioral set into a corpus of 1,200 source queries. All 300 behavioral queries are retained, allowing the internal analysis to directly cover the observations established in § 4.1. We add 900 queries from the same three sources to increase sample diversity and improve the stability of layerwise localization: 300 from BFCL, 200 from Seal-Tools, and 400 from Glaive Function Calling V2. G.5 DISENTANGLING CONFLICT FROM CONFIGURATION NOVELTY 

Section 4.2 notes that the Btool condition necessarily introduces renamed tools and rewritten de-scriptions, raising the possibility that probes detect configuration novelty (out-of-distribution surface forms) rather than tendency conflict per se. We conduct two controls to disentangle these factors. 

Novelty-matched control. We construct a third condition, Bnovel , in which tool names and descrip-tions are rewritten to the same degree as Btool but the replacement aligns with the model’s elicited preference, so no tendency conflict exists despite equivalent surface-form novelty. Concretely, for a weather query whose elicited preference (per § 4.1) is fetch_weather_info , condition A presents the tool under this preferred name. Btool renames the tool to a semantically unrelated name such as geo_obs_historical (novel and conflicting), whereas Bnovel renames it to a semanti-cally equivalent paraphrase such as retrieve_weather_data (equally novel in surface form, but still recognizable as a weather-data tool, so the model’s tendency is satisfied without conflict). Both Btool and Bnovel are matched on surface-form edit distance from A. G.6 PROBE FREEZING AND § 5 D ATA ISOLATION 

After layer selection, the final probe for each backbone is fitted using the combined training and validation portion of the probing corpus while keeping the selected representative layer fixed. H.7 MECHANISM VALIDATION 

We further examine whether E SCAPE GUARD increases reliance on the current tool configuration in the direction predicted by § 4. The prior elicited without tool configuration input should remain unchanged because intervention is gated on the conflict score, which falls below the activation threshold τ when tool configuration is absent; in contrast, unconditional steering methods such as LinSteer apply representation shifts regardless of whether tool configuration is present, and consequently alter the prior even outside the conflict condition. PRISMS uses a threshold-based activation mechanism but does not condition on the presence of conflicting tool-configuration input, so it may still shift representations outside the target scenario. Meanwhile, attention to tool-configuration spans and the probability margin of outputs consistent with the current setting should increase for high-conflict inputs.
