## 摘要
大语言模型的最新进展为结构化数据推理带来了新能力，尤其是通过可分析表格的程序辅助工具。然而，许多现有方法只处理单表场景，或假设相关表已经提供。在实践中，用户常常在整个数据库上发起复杂的数据探索查询，其中相关信息可能分布在多个关系中。在这项工作中，我们提出了 DBRAG，一个面向多表问答的检索增强生成框架。DBRAG 首先使用离线表索引检索候选表，用与查询相关的行丰富其摘要，并使用大语言模型对候选表重新排序。随后，程序辅助推理器选择所需的表，并对其完整内容执行操作，同时保持初始提示上下文紧凑。本研究使用的 Spider、GeoQuery 和 ATIS 数据集上的实验表明，该方法在表检索和多表问答方面均有所改进。

## Abstract
Recent advancements in large language models have introduced new capabilities for reasoning over structured data, particularly through program-aided tools that can analyze tables. However, many existing methods address single-table scenarios or assume that the relevant tables are already provided. In practice, users often issue complex data exploration queries over entire databases, where relevant information may be distributed across multiple relations. In this work, we introduce DBRAG, a retrieval-augmented generation framework tailored for multi-table question answering. DBRAG first retrieves candidate tables using an offline table index, enriches their summaries with query-relevant rows, and uses an LLM to rerank the candidates. A program-aided reasoner then selects the required tables and executes operations over their full contents, keeping the initial prompt context compact. Experiments on the Spider, GeoQuery, and ATIS datasets used in this study demonstrate improvements in table retrieval and multi-table question answering.

## 1. 核心问题与整体含义

- **研究动机**：大语言模型（LLM）虽已能通过程序辅助工具分析表格，但现有表格问答方法大多局限于**单表场景**，或默认**相关表已给定**。
- **现实需求**：用户常在整个数据库上提出复杂数据探索查询，相关信息可能分布在多个关系/表中，需要跨表连接、聚合与推理。
- **核心挑战**：
  - 多表问答需要跨表推理，涉及不同 join、union、aggregation。
  - 数据库中表数量庞大，需同时识别主表与辅助连接表。
  - 表规模差异大，宽表/大表可能超出 LLM 上下文窗口。
  - 开放域场景下，表间关系未必有明确主外键，检索需兼顾查询-表相关性与表-表关系。
- **整体含义**：论文提出 **DBRAG**，将 RAG 框架扩展到整个数据库，把多表问答拆解为**多表检索**与**多表推理**两个子任务，在保持提示上下文紧凑的同时提升复杂数据库查询效果。

## 2. 方法论

### 2.1 核心思想

- 将多表 QA 形式化为：给定自然语言查询 \(q\) 和数据库 \(D=\{t_1,\dots,t_N\}\)，目标是选出必要表子集 \(R_q \subset D\)，其中 \(|R_q|=M \ll N\)，再生成答案。
- 整体流程：
  1. **表索引粗排**：从全库中快速召回 top-K 候选表。
  2. **行索引上下文增强**：为候选表补充与查询相关的行。
  3. **LLM 细粒度重排**：选出 top-M 表。
  4. **程序辅助多表推理**：LLM 选择真正需要的表，并通过工具在完整表上执行操作，返回答案。

### 2.2 多表检索

- **Table Index：粗粒度排序**
  - 对每张表构造粗粒度摘要 \(s_i = \{表名, 模式, 随机采样行\}\)。
  - 用编码器 \(f_{enc}\) 得到表嵌入 \(e_i=f_{enc}(s_i)\)，查询嵌入 \(q=f_{enc}(q)\)。
  - 按余弦相似度排序，取 top-K 形成候选集 \(C_q\)。
  - 表嵌入与查询无关，可离线预计算，存入 Table Index。

- **Row Index：上下文行检索**
  - 对数据库中每一行构造行摘要 \(s_r=\{c_1,v_1,c_2,v_2,\dots,c_n,v_n\}\)，并编码存入 Row Index。
  - 对每个候选表 \(t_i \in C_q\)，用查询检索最相关的 L 行。
  - 用相关行替换随机行，形成细粒度摘要 \(s_i^+=\{表名, 模式, 相关行\}\)。

- **LLM 细粒度重排**
  - 输入查询、重排提示 \(p_{rank}\)、细粒度摘要集合和 M。
  - LLM 按**直接相关性、可连接性、覆盖完整性**选择 top-M 表：
    \[
    R_q = L(q, p_{rank}, \{s_i^+|t_i\in C_q\}, M)
    \]
  - 该步骤弥补编码器独立打分的不足，有助于发现互补表。

### 2.3 多表推理

- **表选择**：
  - LLM 从 \(R_q\) 中进一步识别真正必要的表子集 \(R_q^*\)。
  - 判断哪些表可被 join/union 以构造答案。
- **程序辅助 CoT 推理**：
  - 给定选中表摘要 \(S_{R_q}=\{s_i^+|t_i\in R_q\}\)，LLM 生成程序化操作链。
  - 通过 `execute_dataframe_code` 等工具对完整 DataFrame 迭代操作，保留中间结果。
  - 最后用 `final_structured_output` 返回最终表格答案。
  - 关键点：摘要只用于选表和规划，实际执行可访问**完整表内容**，避免上下文长度限制。

## 3. 实验设计

### 3.1 数据集 / Benchmark

- **Spider（MTQA 版本）**：跨域多表 QA，覆盖 138 个领域，是最主要的检索评测集。
- **GeoQuery（GeoQ）**：美国地理数据库上的多表 QA。
- **ATIS**：航班预订关系数据库上的多表 QA。
- 数据集来自 MTQA 对 text-to-SQL 数据的改造：执行 SQL 得到表格答案，排除错误或空结果样本。
- 论文对 ATIS 和 GeoQ 中不可理解的问题，基于对应 SQL 合成了自然语言查询。

### 3.2 对比方法

- **检索任务基线**：
  - Contriever：通用文本检索。
  - DTR：表格专用 dense retrieval。
  - Coarse-rank：仅用本文编码器粗排，不做 LLM 重排。
  - JAR：基于混合整数规划联合考虑 query-table 与 table-table 相关性，包括 JAR(Contriever)、JAR(DTR)、JAR(Coarse-rank)。
- **检索消融**：
  - DBRAG(Name and Schema)：摘要仅表名和模式。
  - DBRAG(Random Rows)：用随机行替代相关行。
  - DBRAG(Relevant Rows)：默认设置，使用相关行。
- **推理任务基线**：
  - ReadTable：把整表放入提示，超长则失败。
  - MTQA：基于 TAPEX 预训练/微调的多表推理基线。
- **推理消融**：
  - DBRAG(Name and Schema)。
  - DBRAG(w/o Selection)：不做表选择。
  - DBRAG(Random Rows)。
  - DBRAG(Relevant Rows)。

### 3.3 评价指标

- **检索**：Recall@5，比较 top-5 检索表与真实相关表。
- **推理**：
  - Table EM：整表完全匹配。
  - Row EM / Column EM / Cell EM：分别衡量行、列、单元格匹配。
  - 对 Row/Column/Cell EM 报告 macro 版 P/R/F1，避免大表主导结果。

### 3.4 主要实验设置

- 主干 LLM：GPT-3.5-turbo-0125。
- 编码器：OpenAI text-embedding-3-small。
- 粗排预算 \(K=50\)，细排预算 \(M=5\)，行上下文 \(L=2\)。
- 使用 self-consistency=5，即 5 次独立运行取多数投票。
- 重排模型对比：Llama 3.3 70B-Instruct、Qwen2.5 32B-Instruct、GPT-3.5。

## 6. 主要结论与发现

- **检索效果**：
  - DBRAG(Relevant Rows) 在 Spider 上取得最佳 Recall@5，平均 95.8%。
  - 优于 Coarse-rank（89.5%）、JAR(Coarse-rank)（93.0%）、JAR(Contriever)（90.3%）等。
  - LLM 重排显著优于仅编码器粗排。
  - 使用查询相关行比仅表名/模式、随机行更有效。
- **重排模型影响**：
  - GPT-3.5 在复杂多表查询上优于 Llama 3.3 70B 和 Qwen2.5 32B。
  - 单表查询上三者接近，但多表场景更依赖高级推理能力。
- **推理效果**：
  - DBRAG 在 Spider、GeoQ、ATIS 上多数指标优于 ReadTable 和 MTQA。
  - Spider 上提升尤其明显，因为 ReadTable 常因超上下文失败。
  - 表选择步骤有效；去掉选择后性能下降。
  - 相关行上下文优于随机行和仅名称/模式。
- **参数影响**：
  - 增大粗排预算 \(K\) 通常提升检索性能。
  - 增大行上下文 \(L\) 初期提升推理，但随后进入平台期，说明少量行即可理解表结构语义。

## 7. 优点

- **任务定位清晰**：聚焦开放域多表 QA，而非假设相关表已给定。
- **两阶段检索设计合理**：先表索引粗排，再行索引增强和 LLM 重排，兼顾效率与精度。
- **行级上下文增强有效**：用查询相关行替代随机行，显著提升多表检索和推理。
- **程序辅助推理保持上下文紧凑**：摘要用于选表和规划，执行时访问完整表，缓解上下文限制。
- **多表 CoT 与工具执行结合**：将表选择、join/union 规划、代码执行统一在推理链中。
- **消融较完整**：分别验证名称/模式、随机行、相关行、表选择等组件。
