## 摘要
检索增强生成（RAG）有效地将大型语言模型（LLM）扎根于外部知识，但在处理涉及高不确定性和模糊性的复杂查询——即探索性推理问题（ERP）时存在困难。解决ERP需要具有不明确路径的复杂推理，容易导致检索噪声和错误累积。此外，缺乏端到端的规划机制使得为ERP生成有效轨迹变得困难。受数据库查询规划启发，我们提出了PlanRAG，这是一个将自然语言的ERP建模为逻辑查询树（LQT）的RAG框架。然而，由于结构化SQL与非结构化自然语言之间的表示和优化差距，将ERP转换为LQT并非易事，构建高质量的LQT极具挑战性。为了解决这些问题，我们首先将ERP分解为原子查询，然后使用由涉及多个互补维度的成本模型指导的动态规划将其组织成LQT。最后，我们在LQT上执行迭代聚合、重写、检索和生成，并发处理节点并向上传播中间结果，并通过多线程进一步并行化以提高效率。我们的实验结果表明，在我们新构建的数据集WikiWeb-ERP上，PlanRAG优于最先进的基于迭代和基于图的RAG系统，从而为优化自然语言查询提供了一种新的形式。我们的源代码和数据集可在https://anonymous.4open.science/r/PlanRAG-main-B2C8/获取。

## Abstract
Retrieval-Augmented Generation (RAG) effectively grounds large language models (LLMs) in external knowledge but struggles with \textbf{exploratory reasoning problems (ERPs)} that are the complex queries involving high uncertainty and ambiguity. Resolving ERPs requires complex reasoning with unclear paths, tending to result in retrieval noise and error accumulation. Furthermore, the absence of an end-to-end planning mechanism makes it difficult to generate effective trajectories for ERPs. Motivated by database query planning, we introduce \emph{PlanRAG}, an RAG framework that models ERPs of natural language as \textbf{logical query trees (LQTs)}. However, translating ERPs into LQTs is non-trivial due to representation and optimization gaps between structured SQL and unstructured natural language, making it highly challenging to construct high-quality LQTs. To address these problems, we first decompose ERPs into atomic queries and then organize them into LQTs using dynamic programming guided by a cost model involving multiple complementary dimensions. Finally, we execute iterative aggregation, rewriting, retrieval, and generation over LQTs, processing nodes concurrently and propagating intermediate results upward, with further parallelization across multiple threads for efficiency. Our experimental results show that PlanRAG outperforms state-of-the-art iteration-based and graph-based RAG systems on our newly constructed dataset, \textbf{WikiWeb-ERP}, thereby providing a new formulation for optimizing natural language queries. Our source code and dataset are available at https://anonymous.4open.science/r/PlanRAG-main-B2C8/.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **研究问题**：现有检索增强生成（RAG）系统在处理**探索性推理问题（ERP）**时表现不佳。ERP是指具有高不确定性和模糊性的复杂查询，其推理路径不明确，实体之间以模糊、涌现的方式耦合，难以直接分解。
- **核心挑战**：
  - **检索噪声扩散**：由于ERP的不确定性和歧义性，检索过程常返回大量不相关文档，淹没LLM。
  - **错误累积**：基于迭代的RAG方法顺序处理子查询，早期错误会传播到后续步骤，导致复合幻觉和不稳定推理。
  - **缺乏端到端规划**：现有方法依赖人工标注的轨迹或分解规则，没有完整的查询优化机制。
- **启发**：数据库查询规划（将SQL编译为逻辑查询树并通过代价模型优化）提供了一种结构化路径，可以减少歧义和检索噪声。论文受此启发，提出将自然语言查询建模为逻辑查询树（LQT）。

## 2. 论文提出的方法论：核心思想、关键技术细节、公式或算法流程

- **核心思想**：PlanRAG框架将ERP建模为LQT，通过三个阶段模拟数据库查询规划：**查询解析**（query parsing）、**逻辑优化**（logical optimization）和**物理执行**（physical execution）。
- **关键技术细节**：
  1. **原子查询生成（Atomic Query Generation）**：利用LLM将ERP分解为原子查询，每个查询对应单个关系三元组（subject, predicate, object），确保语义原子性和可检索性。原子查询之间有三种语义关系：Parent-child、Sibling、Unrelated。
  2. **逻辑查询树构建（LQT Construction）**：基于Selinger动态规划算法组织原子查询。
     - **关系预处理（Relation Preprocessing）**：先评估所有原子查询对的关系，标记“Unrelated”的查询对在后续DP中直接剪枝，减少LLM调用次数。
     - **循环预防（Cycle Prevention）**：合并节点时检查是否引入环，保证LQT为有向无环图（DAG）。
     - **上下文感知合并（Context-aware Merging）**：将部分构建的LQT作为上下文，让LLM评估候选节点合并的语义兼容性。
     - **代价模型（Cost Model）**：从五个维度评价候选LQT：
       - 树大小（节点数|V|）——鼓励覆盖更多原子查询
       - 结构密度（边数|E|）——鼓励丰富依赖
       - 树深度（Depth）——惩罚过深线性链
       - 树平衡（Balance）——惩罚不平衡结构
       - 语义相似度（Sim）——用BGE模型计算LQT文本与原始查询的相似度，乘以系数α（≥1）
     - 总代价公式：Cost(T) = - [ |V| + |E| - Depth(T) - Balance(T) + α·Sim(T) ]
     - 通过DP搜索最小代价的LQT：T* = argmin_T Cost(T)
  3. **LQT执行（LQT Execution）**：自底向上并行执行。
     - 叶节点直接检索并生成答案：Ans(v) = Generate(Retrieve(v))
     - 非叶节点先聚合子节点查询和答案作为上下文，重写当前查询，然后检索和生成：v' = Rewrite(v, Ctx(v))，然后Ans(v') = Generate(Retrieve(v'))
     - 利用多线程并行处理同一层的独立节点，减少延迟。总执行时间为O(d·(T_LLM + T_retrieval))，d为树深度。
- **时间复杂度分析**：
  - LQT构建理论为指数级O(2^n)，但实际原子查询数通常≤15，且关系预处理将LLM调用次数降为O(n^2)。
  - 并行执行在最佳平衡树时为O(log n·(T_LLM+T_retrieval))，最坏线性链时为O(n·(T_LLM+T_retrieval))。

## 6. 论文的主要结论与发现

- PlanRAG在WikiWeb-ERP上所有指标均优于所有baseline（Acc 26.43 vs 第二好LEGO-GraphRAG 25.48）。
