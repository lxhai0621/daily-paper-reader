## 摘要
自主AI代理越来越依赖外部知识存储，然而大多数检索流水线只提供相关性，而不提供关于来源、版本身份、完整性、可追溯性或时间点重建的持久保证。我们将此形式化为上下文治理，并提出了ContextNext，这是一个用于受治理的、可被AI消费的知识库的开放规范与参考实现。ContextNext并不替代检索增强生成（RAG）；它在检索之下提供治理层，在检索系统对工件进行操作之前，确定哪些工件是经批准的、当前的、可溯源的、且完整性已验证的。

该规范结合了带有元数据的类型化Markdown文档、确定性集合代数选择器、contextnest:// URI引用、SHA-256哈希链版本历史、图谱级别检查点、通过模型上下文协议（MCP）获取实时数据的源节点，以及代理上下文消费的审计轨迹。这些机制让组织能够重建哪些知识版本影响了代理输出，以及这些版本在被消费时是否符合AI资格。

我们报告了两个受控实验的首批实证结果。在一个隔离治理与检索故障模式的过期版本攻击中，受治理选择严格帕累托优于BM25稀疏检索，在约三分之一的输入token成本下获得了更高的答案质量通过率（97%对比93-90%）。在一个包含1060个文档的语料库的检索确定性实验中，确定性选择器和BM25在重复相同查询时返回稳定的文档集（Jaccard系数1.0），而稠密+HNSW基线在80%的查询上具有非确定性（平均Jaccard系数0.611，最差情况0.210）。这些结果表明，上下文治理能够解决仅靠检索质量无法设计解决的故障模式。我们在开放许可下发布了核心引擎、CLI和MCP服务器。

## Abstract
Autonomous AI agents increasingly depend on external knowledge stores, yet most retrieval pipelines provide relevance without durable guarantees of provenance, version identity, integrity, traceability, or point-in-time reconstruction. We formalize this as context governance and present ContextNext, an open specification and reference implementation for governed AI-consumable knowledge vaults. ContextNext does not replace Retrieval-Augmented Generation (RAG); it supplies the governance layer beneath retrieval, determining which artifacts are approved, current, attributable, and integrity-verified before retrieval systems operate over them.   The specification combines typed Markdown documents with metadata, deterministic set-algebraic selectors, contextnest:// URI references, SHA-256 hash-chained version histories, graph-level checkpoints, source nodes for live data through the Model Context Protocol (MCP), and audit traces of agent context consumption. These mechanisms let organizations reconstruct which knowledge versions informed an agent output and whether those versions were AI-eligible when consumed.   We report first empirical results from two controlled experiments. In a stale-version attack isolating the governance-versus-retrieval failure mode, governed selection strictly Pareto-dominates BM25 sparse retrieval, with higher answer-quality pass rate (97% versus 93-90%) at about one-third the input-token cost. In a retrieval-determinism experiment over a 1,060-document corpus, deterministic selectors and BM25 return stable document sets across repeated identical queries (Jaccard 1.0), while a dense+HNSW baseline is non-deterministic on 80% of queries (mean Jaccard 0.611, worst case 0.210). These results suggest that context governance addresses failure modes retrieval quality alone is not designed to resolve. We release a core engine, CLI, and MCP server under open licenses.

### 1. 论文的核心问题与整体含义（研究动机和背景）

- **问题**：自主AI代理越来越多地依赖外部知识（如RAG管道），但现有检索机制只提供“相关性”，不提供**版本来源、完整性、可追溯性、时间点重建**等治理保证。例如，一个采购代理可能引用了已废弃的风险阈值政策，因为向量索引无法区分当前版本和归档版本。
- **背景**：随着AI代理承担运营角色（回答政策、起草决策、协调工作流），仅仅模型能力强不够，知识供应链的**可验证治理**成为安全和合规的约束条件。作者将这种差距定义为“上下文治理差距”（Context Governance Gap，CGG）。
- **整篇论文的含义**：ContextNest不是替代RAG，而是**在检索之下提供治理层**，确保只有经批准、当前、可归属且完整性验证过的工件才能被AI消费。这弥补了RAG无法提供的六大属性：来源、版本身份、完整性、确定性选择、可追溯性、时间一致性。

### 2. 论文提出的方法论：核心思想、关键技术细节

- **核心思想**：将上下文视为**一等受治理的工件**，通过规范化的知识库（vault）格式实现可验证性。
- **关键技术细节**：
  - **类型化文档**：每个文档是Markdown文件+YAML前导元数据（类型、标签、状态、作者、时间戳等）。定义了8种节点类型（document/snippet/glossary/persona/prompt/source/tool/reference），类型决定代理应如何处理该文档。
  - **确定性选择器语法**：基于集合代数的查询语言（交集 `+`、并集 `|`、差集 `-`），支持标签、类型、状态等原子词，保证同样查询返回同样结果（满足确定性选择属性）。
  - **地址化URI方案**：`contextnest://path`（最新版）、`contextnest://path@N`（固定到检查点N）、`contextnest://#anchor`（章节级引用）。支持直接、集合和委托（语义搜索）三种解析模式。
  - **哈希链版本历史**：每个文档有SHA-256内容哈希和链哈希（链接前一个版本哈希、作者、时间戳、版本序号），保证篡改可检测。
  - **图谱级检查点**：每发布一次新版本就生成一个全局检查点，记录所有已发布文档的版本号和链哈希（交叉链绑定），支持时点重建。
  - **源节点（Source Node）**：通过模型上下文协议（MCP）声明式指定如何从外部服务获取实时数据，依赖拓扑排序，返回指令而非结果（会话级缓存，可选暂存状态保留）。
  - **审计追踪**：每次上下文注入记录访问的文档URI、版本、检查点、作者、时间戳等，形成证据包。
  - **管理模型**：分层作用域（文档/文件夹/标签/仓库）和角色（查看/编辑/审批），在受管模式下强制职责分离（不能自审自批）。
- **公式/算法**（文字说明）：
  - 链哈希公式：`chain_hash[n] = SHA256(chain_hash[n-1] ":" content_hash[n] ":" version[n] ":" edited_by[n] ":" edited_at[n])`，按RFC 8785规范序列化。
  - 检查点哈希：对前一个检查点哈希、序号、时间、触发者、所有文档的版本映射及链哈希的规范序列化进行SHA256。
  - 选择器求值复杂度O(∑原子词 * 平均倒排列表大小 + 结果集大小)，集运算线性。

### 3. 实验设计

- **实验1：过期版本攻击（Stale-Version Attack）**
  - **语料/场景**：在11.1的合成仓库基础上，为6份已发布文档添加过期的“v2存档”版本（与当前版本在5个具体事实上矛盾）。构造30个查询，每个查询针对一个矛盾事实，答案标准以当前正确版本为准。
  - **对比方法**：
    - 治理选择器（`ctx resolve`）：标签+类型谓词，只能获取已发布的当前版本。
    - BM25（泄露版）：索引包括`.versions/`历史文件，模拟未过滤的检索。
    - BM25（干净版）：只索引当前已发布文档，模拟配置正确的生产RAG。
  - **评判**：所有条件使用Claude Sonnet 4.6作为答案模型，Claude Opus 4.7作为LLM评判（PASS/FAIL）。
- **实验2：检索确定性（Retrieval Determinism）**
  - **语料/场景**：合成1060个文档（10个模板 × 106个服务变体，如payments-service、auth-service等），每个文档有服务标签和主题标签。50个查询，每个查询针对特定服务的具体事实（如“payments-service的回滚阈值”）。每个查询重复20次。
  - **对比方法**：
    - 选择器（`ctx resolve`）：结合服务标签和主题标签的确定性谓词。
    - BM25（k=3）：同样语料上的稀疏检索。
    - 稠密+HNSW：使用bge-small-en-v1.5嵌入，FAISS HNSW（M=16, efConstruction=40, efSearch=4），每5次重建索引并打乱插入顺序以模拟生产环境。
  - **度量**：每次运行的检索文档集之间的平均成对Jaccard相似度。完全确定性要求mean Jaccard = 1.0。

### 6. 论文的主要结论与发现

- **过期版本攻击**：治理选择器严格帕累托优于两种BM25条件——更高的通过率（97% vs 93%和90%）且输入token成本仅约1/3（215 vs 655和725）。识别出BM25的两种失败模式：过期版本投毒（返回已废止答案）和检索遗漏（标签匹配但词汇重叠低导致的漏检）。
- **检索确定性**：选择器和BM25在所有查询上完全确定（Jaccard 1.0）。稠密+HNSW在80%的查询上非确定（平均Jaccard 0.611，最差0.210），意味着重复相同查询可能返回不同的文档集，破坏了可重现性和审计能力。
- **总体结论**：上下文治理能解决仅靠检索质量无法应对的故障模式。治理与检索是互补功能，生产系统应叠加使用：治理层确定哪些文档可消费，检索层在已治理的子集上搜索。

### 7. 优点

- **系统性形式化**：清晰定义了上下文治理的六项必要属性，并给出了证明每个属性在标准RAG抽象中缺失的结构化论证。
- **架构分离**：明确区分治理与检索，既承认RAG的价值，又指出其抽象不包括治理，为实际部署提供了清晰的组合模式。
- **实用性设计**：文档格式基于Markdown+YAML，无需特殊基础设施；提供CLI、MCP Server等工具，便于集成。
- **实验设计聚焦**：实验直接针对论文核心论点（治理 vs 检索的故障模式），而非笼统的QA基准。确定性实验特别有说服力，展示了稠密检索的固有非确定性对可审计性的威胁。
- **开放与可复现**：规范、参考实现、实验夹具均在开源许可下发布，包括Docker化的评估工具。

### 8. 不足与局限

- **实验规模与范围**：实验数量少，语料合成，只测试了小型可控场景。缺乏对真实企业规模（数十万至数百万文档）和多样化检索系统（如混合检索、重排序）的验证。
- **评估方法论**：仅依赖单一LLM评判，可能引入偏见和噪声，未报告人类评估或校准指标（如Cohen's Kappa）。
- **性能与扩展性**：仅报告了选择器求值复杂度，但未给出大规模仓库的端到端延迟、存储开销、索引构建时间等实证数据（E7-E9计划中）。
- **哈希链是“检测性”而非“预防性”**：篡改后检测，不阻止有权限用户的恶意的写入。作者承认需要配合访问控制层。
- **代理人身份超出范围**：审计追踪记录“谁请求”，但不能保证请求者的外部身份，这限制了跨组织信任。
- **协作与实时编辑**：当前设计适合单机或本地优先模式，对多用户实时协作需要额外平台层。
- **没有比较更现代的RAG系统**：只对比了基本的BM25，未测试如GraphRAG、HyDE、密集检索等先进方法。作者承认稠密基线在后续实验中才会有。
