## 摘要
在智能体Web时代，基于LLM的智能体越来越多地将Web服务作为工具调用，然而大多数接口仍然是“静态端点”，难以表达包含循环、条件、连接和重试的长期工作流。我们提出ToolPro，它将智能体的工具意图表示为“可执行的工具程序”，紧凑地编码了带显式效果类型的多步服务交互。ToolPro结合了约束引导的程序构建、用于“恰好一次”状态修改调用的效果感知重放，以及一个配置文件驱动的策略，用于决定何时程序执行优于逐步调用。我们在带有WebAssembly沙箱的MCP风格服务上实例化了ToolPro，并在真实世界应用的各种工作流上进行了评估。ToolPro将端到端延迟降低了最多53.4%，客户端流量减少了最多96.1%，在网络延迟和工作流复杂度更高的情况下收益更大。

## Abstract
In the agentic web era, LLM-based agents increasingly invoke web services as tools, yet most interfaces remain \emph{static endpoints} that poorly express long-horizon workflows with loops, conditionals, joins, and retries. We present ToolPro, which represents an agent's tool intent as an \emph{executable tool program} that compactly encodes multi-step service interactions with explicit effect types. ToolPro combines constraint-guided program construction, effect-aware replay for exactly-once state-modifying calls, and a profile-driven policy that decides when program execution outperforms stepwise calling. We instantiate ToolPro over MCP-style services with WebAssembly sandboxing and evaluate it on diverse workflows of real-world applications. ToolPro reduces end-to-end latency by up to 53.4\% and client-side traffic by up to 96.1\%, with larger gains under higher network latency and workflow complexity.

## 1. 论文的核心问题与整体含义（研究动机和背景）
- **核心问题**：当前LLM智能体调用Web服务时，绝大多数接口仍然是“静态端点”（static endpoints），即单次查询式的API。这种接口天生无法表达包含循环、条件分支、数据绑定、重试等在内的多步工作流，导致智能体必须将工作流碎片化为多个分散的端点调用，并穿插多轮LLM推理，造成大量网络往返、过度/欠取数据、部分失败时级联重试和状态不一致。
- **整体含义**：静态端点是智能体Web服务效率低下的**表示瓶颈**。论文提出将智能体的工具意图表示为**可执行的工具程序**（tool program），作为服务端的一等接口对象，从而将多步交互以紧凑、可检查、可优化的形式提交执行，从根本上解决效率与可控性问题。

## 2. 论文提出的方法论：核心思想、关键技术细节、公式或算法流程
- **核心思想**：将工具意图编码为**带效果类型（READ/WRITE）的可执行程序**，作为客户端提交给服务端运行的对象。服务端在安全沙箱中编译、修复、执行该程序，并负责重试安全和效果隔离。
- **关键技术细节**：
  1. **约束引导的程序构建**（Constraint-Guided Construction）：
     - 客户端：根据意图和工具规格合成候选程序，执行轻量检查（端点覆盖、控制流骨架、值流）。
     - 服务端：应用投影函数Π()将程序改写为受限的接口-程序表面（只允许结构化控制流、统一CALL存根、效果标注）。
     - 服务端：使用编译器诊断和运行时跟踪进行有界原地修复（bounded in-place repair），最多重试给定次数。
     - 失败时回退到逐步调用（stepwise calling）。
  2. **效果感知重放**（Effect-Aware Replay）：
     - 为每个意图实例维护历史日志H（已提交的WRITE调用）和工作日志W（当前执行的WRITE调用）。
     - READ调用始终转发给服务；WRITE调用在重执行时从H中匹配相同(e,a)并缓存结果，不再实际发出，实现**恰好一次**语义。
     - 若修复改变了已提交WRITE的参数或顺序，则禁用重放，回退到逐步调用（fail-closed）。
     - 算法流程（Algorithm 1）：重执行前将W追加到H，清空W并重置标志；HANDLE_CALL中，WRITE优先匹配最早未使用项，否则发出并记录。
  3. **配置文件驱动的合并策略**（Profile-Driven Consolidation Policy）：
     - 基于移动平均估计网络RTT（TRTT）、每步决策开销（TDEC）、构建开销（TBUILD），以及候选程序中的端点调用数N。
     - 计算净收益 ΔT = (N-1)×(TRTT+TDEC) - TBUILD。
     - 若ΔT>0则执行工具程序，否则选择逐步调用。
- **公式**：论文给出了延迟成本模型：
  - 逐步模式：T_step ≈ Σ(TRTT + TDEC + TAPI)
  - 程序模式：T_prog ≈ TBUILD + (TRTT + ΣTAPI)
  无其他复杂数学公式。
