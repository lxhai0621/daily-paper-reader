## 摘要
我们提出 RAGMark，一个面向小规模多 GPU 环境的先进检索增强生成（RAG）系统的模块化基准测试框架。RAGMark 评估多样化的 RAG 组件，包括检索器、向量数据库、提示处理方法以及生成器模型，同时收集详细的各阶段指标，如延迟、GPU 利用率、内存消耗、功耗、首个 token 时间（TTFT）、吞吐量和答案质量。该框架具有高度可扩展性，将 RAG 阶段、计时和资源监控分离为模块化组件，并设计用于高效遍历大型配置空间，同时尽量减少重复的模型和数据库初始化开销。利用 RAGMark，我们在开放域问答数据集上刻画了五种 RAG 工作负载，涵盖不同的检索深度、模型规模、重排序、压缩方法以及向量数据库配置。我们表明，尽管在朴素流水线中自回归生成主导了延迟，但上下文缩减技术会将瓶颈转移至计算、内存带宽和预处理阶段。重排序与压缩产生叠加收益：重排序本身减少了压缩工作量，而两者共同降低了预填充和 KV 缓存遍历成本，使能耗最多降低 66%。我们进一步观察到强烈的跨阶段交互：上游轻微的上下文缩减会级联影响下游延迟、内存流量和能耗。RAGMark 源代码已公开提供：https://github.com/zferic/RAGMark。

## Abstract
We present RAGMark, a modular benchmarking framework for advanced Retrieval-Augmented Generation (RAG) systems targeting small-scale multi-GPU environments. RAGMark evaluates diverse RAG components, including retrievers, vector databases, prompt-processing methods, and generator models, while collecting detailed per-stage metrics such as latency, GPU utilization, memory consumption, power usage, time to first token (TTFT), throughput, and answer quality. The framework is highly extensible, separating RAG stages, timing, and resource monitoring into modular components, and is designed to efficiently sweep large configuration spaces while minimizing repeated model and database initialization overhead. Using RAGMark, we characterize five RAG workloads on open-domain QA datasets across varying retrieval depths, model scales, reranking, compression methods, and vector database configurations. We show that while autoregressive generation dominates latency in naive pipelines, context-reduction techniques shift bottlenecks across compute, memory bandwidth, and preprocessing stages. Reranking and compression produce compounding benefits: reranking reduces compression workload itself, while both jointly reduce prefill and KV-cache traversal costs, lowering energy consumption by up to 66%. We further observe strong cross-stage interactions, where small upstream context reductions cascade through downstream latency, memory traffic, and energy consumption. The RAGMark source code is publicly available at: https://github.com/zferic/RAGMark.

## 2. 方法论：核心思想、技术细节与流程

- **核心思想**：将 RAG 流水线拆解为独立、可插拔的阶段组件，统一测量基础设施，配置驱动地高效扫描大规模配置空间，同时避免重复初始化模型与数据库。
- **五大设计原则**：代表性（逐查询覆盖全阶段）、模块化（基于 Hugging Face 标准接口即插即用）、联合评估（系统性能 + 模型准确率）、效率（查询采样）、可复现（确定性、配置驱动）。
- **核心类设计**：
  - **RAG 阶段类**：`EmbeddingModel`（均值池化编码查询）、`Retriever`（FAISS 索引加载、检索、GPU 传输与分片）、`Reranker`（交叉编码器重打分）、`Compressor`（统一接口，归一化压缩比 r）、`Generator`（因果 LLM 推理，注入自定义 `LogitsProcessor` 测量 TTFT 与逐 token 解码延迟）。
  - **性能剖析类**：`RAGTiming`（逐阶段延迟与资源记录）、`PowerPoller`（NVML 定频采样 GPU/CPU 功耗）、`TracePoller`（GPU 利用率与显存轨迹）。
  - **流水线类**：`StandardPipeline`（单次检索 + 可选重排/压缩）、`IterativePipeline`（多轮检索与生成交错）。
- **执行与部署**：支持单查询模式与批处理模式；每个组件可独立分配到 CPU 或 GPU，索引与生成模型可跨多设备分布。
- **测量方法学**：
  - **延迟与吞吐**：阶段边界墙钟时间戳；生成延迟分解为 TTFT（预填充）与解码时间；端到端为各阶段延迟之和。
  - **内存与资源**：设备级通过 NVML 追踪真实 GPU 显存（含 FAISS 索引），框架级通过 PyTorch API 追踪张量分配；主机侧用 psutil 记录 CPU 利用率与 RSS。
  - **能耗**：NVML 采样功耗与 SM 占用，按查询时长积分估算单查询能耗。
  - **准确率**：EM、ROUGE、F1、BERTScore，均为确定性参考评估，评估期间不需额外 LLM 推理。
- **与 FlashRAG 的集成与差异**：复用 FlashRAG 的数据集下载/预处理、FAISS 索引创建与 QA 评估；但 FlashRAG 面向准确率评估（批量 retrieve-all/embed-all/generate-all），不适合逐查询剖析，因此 RAGMark 的性能测量管线完全独立实现，新增阶段交错执行、NVML 能耗积分与内存归因、统一组件接口、配置驱动扫描编排与逐查询数据分析脚本。

## 6. 主要结论与发现

- **朴素流水线**：LLM 的 TTFT 与解码主导端到端延迟，检索与嵌入即使在 top-k=10 时合计也不超过约 35 ms；FAISS 延迟从 top-k=1 的约 7 ms 增至 top-k=5 的约 27 ms 后增长趋缓，说明主要成本在搜索本身而非取回更多近邻。
- **注意力二次方效应**：L3-8B 的 TTFT 从 top-k=0 的 64 ms 增至 top-k=5 的 185 ms、top-k=10 的 322 ms，且后段增量（+137 ms）超过前段，体现 O(n²) 注意力在长上下文下占主导；1B 模型因隐藏维小仍近似线性。
- **瓶颈转移**：小上下文时预填充受计算约束、解码受 KV 缓存成本影响；大上下文时注意力饱和张量核心，解码转为带宽约束，导致能耗不成比例增长（L3-8B 从 top-k=5 到 10 能耗增长 1.8 倍）。
- **重排收益**：重排开销随检索深度线性增长（约 7–24 ms），但通过截断上下文使 L3-8B 在 top-k=10 的 TTFT 下降 49%（322→165 ms）、解码从 204→128 ms，能耗从 157.5 J 降至 75.5 J（降 52%），ROUGE 变化小于 0.02。
- **压缩收益**：LLMLingua-2 在 L3-8B/top-k=10 下 TTFT 降 66%（322→108 ms）、解码降至 111 ms、GPU0 能耗降 46%（157.5→85.7 J）、内存带宽利用率从 35.5% 降至 25.3%；压缩优于重排的原因是它同时跨文档与文档内压缩上下文。Selective-Context 因开销过大在本流水线中不划算。
- **组合的复合收益**：重排先缩小压缩器输入，使压缩成本约减半（130→58 ms），组合后 L3-8B/top-k=10 能耗降至 52.9 J，相比朴素流水线降低 66%，为全部分析中最大降幅。
- **迭代 RAG**：检索与嵌入开销翻倍，且迭代间存在时间依赖；首轮解码延迟显著更高（L3-8B/top-k=10 达 867 ms vs 次轮 102 ms），源于首轮要求展开式回答、次轮要求简短事实回答。
- **索引与硬件放置**：低批大小下单查询 CPU IVF1000 索引（约 1.1 ms）快于单 GPU（约 3.9 ms）；批大小增至 12 时 CPU IVF300,SQ4 升至约 56 ms，而单 GPU 约 34 ms，GPU 在批量检索下扩展性更好；第二块 GPU 并非总是有益，存在同步开销。
- **权衡可视化**：1B 模型在 k=3/5 时以极低 TTFT（约 0.04 s）取得约 0.33 的 ROUGE；8B 模型 k=8 时 ROUGE 最高（约 0.41）但延迟高 5–8 倍；k 从 3 增至 10 并不稳定提升 ROUGE，却显著增加 TTFT。

## 7. 优点（方法或实验设计亮点）

- **模块化与可扩展性**：阶段、计时、资源监控完全解耦，新增生成器/嵌入/重排器只需指定 Hugging Face 模型标识与设备，新增组件类型只需实现对应类并注册。
- **逐查询、逐阶段细粒度剖析**：区别于 FlashRAG 等批量式评估框架，支持阶段交错执行与毫秒级查询行为刻画。
- **联合评估性能与质量**：同时采集延迟、TTFT、吞吐、显存、能耗、SM/带宽利用率与 EM/ROUGE/F1/BERTScore，能直接分析效率—质量权衡。
- **高效配置扫描**：模型与数据库仅加载一次并复用，配合查询采样与预热，使大规模配置空间扫描可行。
- **测量严谨**：NVML 设备级显存（含 FAISS 索引）与 PyTorch 框架级内存双轨记录，功耗积分估算单查询能耗，结果可复现且开源（GitHub + Zenodo DOI）。
- **跨阶段交互的实证发现**：量化了上游上下文缩减对下游延迟、内存流量与能耗的级联效应，并揭示重排与压缩"成本非线性、收益复合"的特性，具有工程指导价值。

## 8. 不足与局限
