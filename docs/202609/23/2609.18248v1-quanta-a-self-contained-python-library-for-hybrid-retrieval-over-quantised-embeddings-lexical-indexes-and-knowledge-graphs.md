## 摘要
先进的检索增强生成流水线通常由三到四个独立运行的系统组装而成：近似最近邻索引、全文搜索引擎、图数据库和关系型文档存储。每个系统都有自己的部署面、配置模型和故障模式，而将它们绑定在一起的集成逻辑在每个项目中都要重新编写。在这项工作中，我们提出 Quanta，一个开源 Python 库，它通过单一检索 API 统一了基于 4 比特量化嵌入的稠密向量搜索、BM25 全文检索和知识图谱遍历。Quanta 做出了两项设计承诺，这使其有别于现有的混合检索栈。首先，信号通过加权倒数排名融合进行组合，而不是将异构分数归一化到共享范围；我们认为后者是不适定的，因为此类归一化依赖于查询。其次，图是候选扩展器，而不是相关性评分器：遍历扩大候选池，新纳入的文档在标识符允许列表下由稠密索引重新评分，因此结构邻接决定哪些内容被考虑，而内容证据决定其如何排序。

## Abstract
An advanced retrieval-augmented generation pipeline is typically assembled from three or four independently operated systems: an approximate nearest-neighbour index, a full-text search engine, a graph database, and a relational document store. Each contributes its own deployment surface, configuration model, and failure modes, and the integration logic that binds them is written anew in every project. In this work, we present \textsc{Quanta}, an open-source Python library, which unifies dense vector search over 4-bit quantised embeddings, BM25 full-text retrieval, and knowledge-graph traversal behind a single retrieval API. Quanta makes two design commitments, which distinguish it from existing hybrid retrieval stacks. First, signals are combined by \emph{weighted reciprocal rank fusion} rather than by normalising heterogeneous scores onto a shared range, which we argue is ill-posed because such normalisations are query-dependent. Second, the graph is a \emph{candidate expander and not a relevance scorer}: traversal widens the candidate pool, and the newly admitted documents are re-scored by the dense indexes under an identifier allowlist, so structural adjacency determines what is considered while content evidence determines how it ranks.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：RAG 使检索质量成为一等关切，但单一信号不足。稠密双编码器泛化好，却在产品编号、法条号、专有名词等稀有 token 上退化；BM25 词法打分恰好补上这一缺口，稠密+词法混合检索已成标准做法。
- **未覆盖的信号**：两者都无法利用"语料所有者已知但文本未陈述"的关系，例如判决引用法条、诊断与诊断之间的共病关系。
- **真正的痛点在于集成而非检索**：当前典型技术栈需拼装 FAISS/Milvus（向量）+ Elasticsearch（BM25）+ Neo4j（图遍历）+ PostgreSQL（存储）四套系统，各自有部署面、配置模型与故障模式，且跨系统的查询编排代码在每个项目中都要重写。编排框架（如 LlamaIndex）减少了样板代码，但没有消除系统本身，且通常把图当作独立查询路径而非统一排序的参与者。
- **论文定位**：提出开源 Python 库 Quanta，以单进程、单一检索 API 统一 4-bit 量化稠密向量检索、BM25 全文检索与知识图谱遍历。作者明确声明这是**系统描述（system description）**，受控检索评测留待未来工作，因此其含义是"工程架构与设计范式的贡献"，而非"检索效果的实证贡献"。

## 2. 方法论

### 2.1 核心思想
- 以单个 `MultiRetriever` 持有命名向量索引、文档存储及三类可选后端（图、词法索引、嵌入缓存），暴露一个异步 `search()` 入口。
- 两条设计承诺：
  1. **融合在排名上做**（加权 RRF），不对异构分数做归一化——作者认为把余弦相似度、BM25、跳距归一化到同一区间是"不适定的"，因为这种归一化依赖查询。
  2. **图是候选扩展器，不是相关性评分器**：遍历只扩大候选池，新纳入文档由稠密索引在 ID 允许列表（allowlist）内重新打分；结构邻接决定"哪些被考虑"，内容证据决定"如何排序"。
- 每个可选组件都有 null 实现，部署可从纯向量检索起步，仅靠配置逐步获得更多信号。Quanta 自身不做嵌入，嵌入提供方留在消费侧。

### 2.2 索引与存储层
- `QuantaIndex` 包装 TurboVec（TurboQuant 的实现）；应用层字符串 ID 与索引的 64 位整数通过固定种子 xxhash-64 映射，拒绝摘要碰撞的插入。
- 内存占用：$n$ 个 $d$ 维向量在 $b$ 比特下占 $ndb/8$ 字节；$10^6$ 条 768 维、$b=4$ 时约 366 MiB，对比 float32 的 2.86 GiB，且完全进程内、无需运维 ANN 服务。搜索在量化表示上**精确**，故查询时间随语料规模线性增长。
- 文档存储有两个后端：`PostgresDocStore`（asyncpg + JSONB 列上的 GIN 索引）与嵌入式 `DuckDBDocStore`。
- 元数据过滤不采用"先取 top-K 再丢弃"的后过滤（在选择性谓词下会隐性损失召回），而是**先解析谓词得到 ID 集合，作为 allowlist 传给索引**，最近邻扫描只覆盖可接受向量。

### 2.3 融合规则（加权 RRF）
- 各腿输出量纲不可比：余弦有界且集中在上端，BM25 无界且随查询长度与集合统计增长，跳距是图与种子集的属性而非查询的属性。
- 融合公式（$r_\ell(d)$ 为文档 $d$ 在腿 $\ell$ 排名中的 1-based 位置）：

$$\text{score}(d)=\sum_{\ell\in L}\frac{w_\ell}{k_{rrf}+r_\ell(d)}$$

- $k_{rrf}$ 默认 60，用于抑制各列表头部；缺失于某腿的文档不贡献该项。每个稠密索引分得 $w_{dense}/|I|$，词法腿为 $w_{bm25}$，图腿为 $w_{graph}$。由于公式对权重齐次，只有比值有意义，无需重新归一化。

### 2.4 图扩展的两遍算法（Algorithm 1）
1. **第一遍（内容检索）**：对每个活跃索引做稠密检索、BM25 检索，分别排序，做 RRF 得到 $R_1$，取 top-`GRAPH_SEED_K` 作为种子。
2. **第二遍（图扩展 + 约束重排）**：从种子出发做有界广度优先遍历（`GRAPH_HOPS` 跳），得到候选标识符集合；计算新标识符 $N=\text{keys}(L_{graph})\setminus\text{covered}(\{L_i\})$；对每个稠密索引以 `allowed_ids = N` 做第二次搜索，把结果 merge 进该索引原排名列表。
3. **最终融合**：对合并后的稠密列表、BM25 列表与图列表再做 RRF，返回 top-k。

- **关键点**：扩展文档不注入合成分数，而是以自身对查询的相似度参与竞争，与第一遍返回的文档"同场竞技"。
- 当 $w_{graph}=0$ 时，图腿从公式中消失，文档的融合分数只取决于其在内容腿中的排名，遍历只产生 $C_1 \to C_2$ 的集合扩张效应，即"图只决定被考虑者，绝不影响排序"。
- **$w_{graph}>0$ 的警告**：作者用数值例子说明其危险性——单稠密索引、$w_{dense}=0.7$、$k_{rrf}=60$、$w_{graph}=0.3$ 时，内容排名第一者得 $0.7/61=0.0115$，而内容排名第四但图腿第一（任意一跳邻居）者得 $0.7/64+0.3/61=0.0159$，直接反超。即图权只要与内容权在同一量级，就不再是"平局打破者"，而是把所有一跳邻居抬到最佳内容匹配之上。因此 Quanta **默认 $w_{graph}=0$**，把调参导向 `GRAPH_SEED_K` 与 `GRAPH_HOPS`。

### 2.5 与 GraphRAG 的区别
- GraphRAG 类系统用语言模型抽取实体图并用于查询聚焦摘要；Quanta 消费**语料所有者编写**的图，嵌入常规 top-k 检索流程，并把图的影响限制在候选选择环节。

## 3. 实验设计

- **性质说明**：论文明确表示这不是检索评测——**没有相关性判断，没有基线排序器，没有对比方法**。第 3 节是随库发布的部署案例研究，只刻画观察到的行为。
- **语料与本体**：Neo4j 中的合成医院记录集，含 100 名患者、30 名医生、12 个 ICD-10 诊断、12 个手术、12 种药物、5 家医院，由九种关系类型连接。本体把随关系变化的属性放在边上（如 HAS_DIAGNOSIS 边携带该患者该诊断的严重度与慢性度），因此同一诊断对不同患者可轻可重。9 条 COMORBID_WITH 边（按证据等级分级）与 10 条 INTERACTS_WITH 边（按严重度分级）**由人工编写而非抽取**，用于检验图扩展是否真的带来文档中未陈述的知识。所有叙事文本为希腊语。
- **索引构成**：五个叙事字段分别建索引——患者摘要（100 向量）、医生专长（30）、诊断描述（12）、手术描述（12）、医学图像（198）；文本用 768 维多语言句编码器，图像用 512 维 CLIP 编码器；全部量化为 4 bit，共 107.3 KiB（float32 为 858 KiB）。
- **检索配置**：注册三个稠密腿（诊断、手术、患者摘要）+ Tantivy BM25 腿 + 图腿，$w_{dense}=0.5$、$w_{bm25}=0.3$、$w_{graph}=0$，文档存储用嵌入式 DuckDB。由于随库的 `Neo4jGraph` 假设同构 `(:DOCUMENT {ID})` 模型而本图并非如此，部署直接实现 `GraphBackend` 接口对接真实 schema，约四十行代码，无需图投影或迁移。
- **代理场景**：同一底座支撑一个工具调用代理，暴露 12 个工具（QuantaIndex 稠密检索、Neo4j 全文索引 + 编辑距离匹配的词法解析、有界 Cypher 遍历）。问题进入推理循环，在 OpenAI 兼容端点与 dispatcher 之间交替；dispatcher 是唯一接触数据的组件。对话历史在配置时持久化到 Redis。
