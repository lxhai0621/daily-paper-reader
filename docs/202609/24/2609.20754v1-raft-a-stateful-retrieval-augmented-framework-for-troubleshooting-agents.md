## 摘要
在企业客户支持中，有效的故障排查智能体依赖于从相似历史案例中检索可操作的指导，然而现有的检索增强生成（RAG）系统将支持案例视为静态文档，忽视了其多阶段、有状态的性质。我们提出 RAFT（Retrieval-Augmented Framework for Troubleshooting Agents，故障排查智能体检索增强框架），一个有状态的 RAG 框架，它将每个已关闭的历史案例抽象为时间线条目的有向链，并在条目级别进行检索，从而浮现出其中间状态与当前活跃案例匹配的案例，并返回以匹配状态为锚点的父案例轨迹；一个可选的案例级图通过可配置的相似度表示连接案例。我们直接评估该检索层，与评估完整智能体系统不同，这无需生产部署。由于公开的多阶段故障排查数据极为稀少，我们将基于 Microsoft Learn Windows Server 文档构建的合成基准与带有由人工创建的重复标签的真实 Apache Jira 问题配对。RAFT 在案例进展的每个阶段都相较原始 RAG 和 GraphRAG 基线提升了案例命中率（Case Hit），并且相较最强基线具有统计显著的提升；Jira 结果为该优势可迁移至真实案例历史提供了方向性证据。我们发布了我们的基准、实现以及 Apache Jira 评估集。

## Abstract
Effective troubleshooting agents in enterprise customer support depend on retrieving actionable guidance from similar historical cases, yet existing retrieval-augmented generation (RAG) systems treat support cases as static documents and overlook their multi-stage, stateful nature. We introduce RAFT (Retrieval-Augmented Framework for Troubleshooting Agents), a stateful RAG framework that abstracts each closed historical case into a directed chain of timeline entries and retrieves at the entry level, surfacing cases whose intermediate states match the active case and returning the parent-case trajectory anchored at the matched state; an optional case-level graph links cases through a configurable similarity representation. We evaluate this retrieval layer directly, which, unlike evaluating a full agent system, requires no production deployment. Because public multi-stage troubleshooting data is extremely rare, we pair a synthetic benchmark built from Microsoft Learn Windows Server documentation with real Apache Jira issues carrying human-created duplicate labels. RAFT improves Case Hit over vanilla RAG and GraphRAG baselines at every stage of case progress, with statistically significant gains over the strongest baseline; the Jira results provide directional evidence that the advantage transfers to real case histories. We release our benchmark, implementation, and the Apache Jira evaluation set.

## 2. 方法论：核心思想与关键技术

### 2.1 核心思想

- RAFT 是两层有状态 RAG 框架：
  - **案例内部**：每个已关闭案例被抽取为按时间顺序排列的有向时间线条目链，每个条目对应调查中一个有意义的技术状态。
  - **案例之间**：可选构建案例级图，通过可配置相似度表示连接案例，用于扩展检索。
- 检索时，不是匹配整个案例，而是匹配“当前活跃案例状态”与历史案例的“中间时间线条目”，并返回以匹配条目为锚点的完整父案例轨迹。

### 2.2 离线索引

- 对每个原始案例 \(h_i\)，抽取结构化表示：
  - 评审评估 \(\rho_i\)：可含案例标签、可操作性判断及理由。
  - 时间线条目 \(\{ \phi_k^{(i)} \}\)：按调查阶段划分。
  - 根因 \(r_i\)、解决步骤 \(a_i\)、排障相关实体 \(e_i\)。
- **Worker–Reviewer 抽取流程**：
  - Worker 按有界批次处理有序 artifacts，携带不断演化的案例状态。
  - 状态更新采用 JSON Patch，支持局部增删改，避免每次重新生成全部输出。
  - 源证据通过只读 SQLite 查询工具按需访问；worker 可使用领域工具。
  - 所有批次处理后，reviewer 检查、修正状态，并产出结构化评估 \(\rho_i\)。
- **时间线条目构建**：
  - 每个条目蒸馏连续 turn 片段，覆盖一个有意义调查阶段。
  - 新条目在“问题框架或当前理解发生实质更新”时开始。
  - 吸收确认、寒暄、微小更新，保持 \(K_i \ll T_i\)，确保条目紧凑且可操作。
- **案例级图 \(G=(V,E)\)**：
  - 可选，无向图，顶点为保留案例的结构化表示。
  - 链接文本可配置；实验中使用“根因 + 解决步骤”拼接。
  - 用语义相似度 + BM25 词法相似度，通过 RRF 融合打分。
  - 保留每个案例 top-k 邻居，过滤低相似度边，对称化，赋 SNN 权重。
  - 支持元数据、实体、评审评估等过滤约束。

### 2.3 在线检索

- 给定查询 \(q\)：
  1. 若提供案例过滤器 \(F\)，先保留满足条件的父案例对应条目。
  2. 对剩余条目计算混合分数：语义 + BM25，经 RRF 融合。
  3. 按分数降序排序。
  4. 贪心将条目提升为父案例，最多选择 \(n\) 个不同案例，且不超过上下文预算 \(B\)。
  5. 对每个选中案例，记录最高分时间线条目索引 \(k_c^*\)，返回完整案例表示和锚定条目。
- 可选：利用案例级图 \(G\) 从种子案例扩展邻居，以获取在根因/解决步骤层面相似但条目级不匹配的补充案例。
- 关键输出：智能体不仅知道“哪个历史案例相似”，还知道“历史案例中哪个调查状态与当前状态匹配”。

## 3. 实验设计

### 3.1 数据集与场景

- **合成开发基准**：
  - 基于 Microsoft Learn Windows Server 故障排查文档构建。
  - 覆盖 7 类：Active Directory、Windows Security、Remote Desktop、Group Policy、Licensing and Activation、Networking、Backup and Storage。
  - 共 826 个合成支持案例，每根因生成 2–4 个案例。
  - 每案例平均约 10.4 条消息、2767 tokens。
  - 每个根因组留出一个案例作为测试查询，其余进入索引语料。
- **Apache Jira 真实评估集**：
  - 来自 Apache Cassandra、Hadoop、HBase、Spark。
  - 利用人工创建的 Duplicate 标签。
  - 从 2082 个原始重复对经过滤、审计后保留 30 个重复组。
  - 最终语料 600 个案例：30 个 gold 目标 + 570 个已 Fixed 干扰项。
  - 所有 30 组可用于 0% 和 30% 进度；60% 进度仅 19 组有足够披露前历史。
  - 未提供 gold 根因/解决步骤标注，因此只报告 Case Hit。

### 3.2 查询构造与指标

- 从测试案例前缀构造查询，进度点：
  - 0%：仅初始症状。
  - 30%：部分调查上下文。
  - 60%：更多诊断上下文。
- 指标：
  - **Case Hit**：是否至少检索到一个与查询共享根因和解决步骤的 ground-truth 相似案例。
  - **Root Cause Coverage**：gold 根因解释中的原子 claim 被检索上下文蕴含的比例，由 LLM 判断。
  - **Resolution Steps Coverage**：gold 修复步骤的对应覆盖率。
- 合成基准平均 5 次独立运行；Jira 使用 5 个索引种子。
- 统计检验：按根因组聚类的 bootstrap 重采样，报告 95% 置信区间。

### 3.3 对比方法

- **Vanilla RAG**：chunk size 256 tokens，overlap 64 tokens，返回 top-ranked chunks 对应的唯一案例。
- **HippoRAG2**：默认配置，开放关系知识图谱 + 个性化 PageRank。
- **Fast-GraphRAG**：默认配置，实体图，预算混合返回实体、关系和 chunk。
- **RAFT**：本文方法。
- **公平性控制**：
  - 所有方法共享相同嵌入模型 `text-embedding-3-large`。
  - 相同索引 LLM `gpt-5.2`。
  - 评估使用 `gpt-5.4`。
  - 合成实验中检索上下文上限 6000 tokens；返回案例级单元的方法最多 5 个不同案例。
  - 不应用元数据过滤，以隔离检索机制影响。
  - 合成语料所有案例均可操作，因此 RAFT 的可操作性过滤不带来额外优势。
