## 摘要
现代LLM智能体在持久工作空间中运行，其累积的历史可能超出GPU KV容量以及模型的原生上下文窗口。现有系统通常将较旧的上下文压缩为摘要，或稍后以文本形式检索，这要么丢失了细粒度的执行证据，要么反复预填充模型已处理过的内容。我们提出KVMem，一种KV上下文虚拟化系统，将溢出的工作空间历史以分页KV状态的形式跨GPU内存、主机内存和NVMe进行持久化。KVMem使用轻量级、模型原生的注意力空间索引来选择相关的历史块，并物化出一个受模型原生上下文窗口限制的、依赖查询的执行视图。对覆盖长达一百万令牌历史的长上下文智能体基准（包括LongMemEval、MemoryAgentBench和AgentLongBench）的广泛评估表明，KVMem通常比压缩式方法（处理上下文溢出的实际标准）实现更高的任务效用和更大的推理效率。在使用Qwen3.8-27B的DeepSWE长上下文测试中，KVMem将任务成功率从仅使用压缩上下文管理的43.8%提升至48.4%。在我们本地部署评估中，KVMem在配备24GB RTX 5090笔记本电脑GPU的现成笔记本电脑上运行Qwen3.6/3.8-27B NVFP4与MTP，虚拟化多达100万令牌的智能体工作空间——是模型原生256K令牌上下文窗口的四倍。在单会话设置中，KVMem生成约50个令牌/秒，为本地智能体执行提供交互响应性。更广泛地说，通过将可寻址工作空间大小与LLM的原生上下文窗口解耦，KVMem为工作空间可增长至超出该窗口的长期运行智能体提供了一条实用路径。

## Abstract
Modern LLM agents operate in persistent workspaces whose accumulated history can exceed both GPU KV capacity and the model's native context window. Existing systems typically compact older context into summaries or retrieve it later as text, either losing fine-grained execution evidence or repeatedly prefilling content that the model has already processed. We present KVMem, a KV-context virtualization system that preserves overflowed workspace history as paged KV state across GPU memory, host memory, and NVMe. KVMem uses lightweight, model-native attention-space indexes to select relevant historical blocks and materializes a query-dependent execution view bounded by the model's native context window. Extensive evaluations on long-context agent benchmarks spanning histories up to one million tokens, including LongMemEval, MemoryAgentBench, and AgentLongBench, show that KVMem generally achieves higher task utility and greater inference efficiency than compaction-based approaches, the de facto standard for handling context overflow. In the DeepSWE long-context test with Qwen3.8-27B, KVMem improves task success from 43.8% with compaction-only context management to 48.4%.   In our local-deployment evaluation, KVMem runs Qwen3.6/3.8-27B NVFP4 with MTP on an off-the-shelf laptop equipped with a 24\,GB RTX 5090 Laptop GPU, virtualizing agent workspaces of up to 1M tokens-four times the model's native 256K-token context window. In a single-session setting, KVMem generates $\sim$50 tokens/s, providing interactive responsiveness for local agent execution. More broadly, by decoupling addressable workspace size from the LLM's native context window, KVMem provides a practical path toward long-running agents whose workspaces can grow beyond that window.

- 现有 agent 工作区系统处理溢出时普遍采用 **文本中心式（text-centric）抽象**：
  - **Compaction（压缩）**：把旧历史改写为摘要，可能丢失对后续步骤至关重要的细粒度证据（如某句话、某个工具输出值、某个约束）；
  - **Text retrieval（文本检索）**：把已处理过的文本重新放回 prompt，导致模型不得不再次对这些内容执行 prefill，重复计算历史 KV。
- 论文的核心洞察：**历史上下文已经通过 prefill 被编码为 KV 状态，不必因移除出执行窗口而丢弃**。借鉴虚拟内存概念，可将“智能体可寻址 KV 工作区大小”与“GPU 上物理驻留的 KV 状态量”解耦，把溢出历史作为可恢复的分页 KV 块保存在 GPU、主机内存和 NVMe 中，在需要时按查询条件物化出一个受限的“执行视图”。
- 由此提出 **KVMem**：一种 KV 上下文虚拟化系统，目标是使长期运行的智能体工作区能够超过模型原生上下文窗口，同时在消费级 GPU 上保持低恢复开销和高任务效用。

## 2. 方法论：核心思想、技术细节与流程

### 2.1 系统总体框架

- KVMem 将完整工作区历史视为“KV 仓库”，并把历史切分为逻辑 KV 块（默认 32 token），每个块是检索评分、选择和移动的最小单元。
- 区分两个视图：
  - **Repository view**：持久化所有历史块及其在 GPU 页面池、主机内存、NVMe 中的副本位置；
  - **Execution view**：只包含当前智能体步骤选中的历史块，按时间顺序排列并映射到紧凑的注意力窗口位置。
- KVMem 在每一步执行中只物化“受执行预算约束的、与当前查询相关”的历史块，而整个工作区仍可寻址。

### 2.2 三大核心机制

KVMem 围绕“何时回看、回看什么、如何回看”三个挑战提出三项机制：

#### (1) 步骤级内存调度（Step-Level Memory Scheduling）— 解决“何时回看”

- 通过分析八条 OpenHands SWE-bench Lite 轨迹中滑动窗口注意力分布的 KL 散度，发现：
  - 同一 agent 步骤内相邻窗口注意力 KL 平均仅 0.070 bits；
  - 跨 agent 步骤边界时 KL 平均为 2.59 bits，约为前者 37.3 倍。
- 因此 KVMem 将历史工作集更新频率设为 **每 agent 步骤一次**：在当前步骤 prefill 结束后、decode 开始前执行一次工作集重构；decode 期间保持该工作集固定，新生成的 KV 追加在视图尾部。这一调度避免了频繁检索的系统开销，同时能在历史注意力发生显著变化时及时回看。

#### (2) 查询条件下的 KV 检索（Query-Conditioned KV Retrieval）— 解决“回看什么”

- 目标：在上百万 token 的工作区中高效识别与当前查询相关的历史 KV 块，且不需扫描全部历史 token 的完整 KV 张量。
- 核心表示：**Mean-K 检索索引**
  - 历史 K 向量因 RoPE 带有位置信息，先将其去除位置编码，得到“与位置无关”的 K 向量；
  - 对每个逻辑块、每一层、每个 KV head，取其块内位置无关 K 向量的均值作为该块的紧凑表示：

    \[
    \bar{k}_{l,b,g} = \frac{1}{|b|}\sum_{i\in b} \tilde{k}_{l,i,g}
    \]

  - 每个块、每层、每 KV head 仅存一个向量，索引尺寸远小于完整 KV；块越小，均值越能保留细粒度语义，同时检索粒度也更细。

- 块评分公式：
  - 对候选块集合 \(C\)，给定查询 token \(m\)、层 \(l\)、查询头 \(h\)（对应 KV 头 \(g(h)\)），计算块相关度：

    \[
    R_b = \sum_m \underset{l,h}{\text{mean}} \, \text{softmax}_{b' \in C}\left( \frac{q_{l,m,h}^\top \bar{k}_{l,b',g(h)}}{\sqrt{d}} \right)_b
    \]

  - 即用缩放点积 + 对候选块的 softmax 归一化，再对查询 token 求和、对层/头取平均。
  - 默认总是保留 sink 和 recent 块，其余筛选基于分数排序；选中的块再按时间顺序重排，并映射到紧凑窗口的新位置。
- 可扩展性设计：
  - 完整 Mean-K 索引常驻主机内存；GPU 只放有界 tile，分批评分并在 tile 间保持全局 softmax 等价性，从而不影响 GPU 显存上界。

#### (3) 分层 KV 管理（Tiered KV Management) — 解决“如何回看”

- 基本思路：将历史 KV 块分层放置于 GPU 页面池、主机内存与 NVMe；执行视图通过页表把非连续物理页面映射成紧凑逻辑顺序，避免额外拷贝。
- **位置一致性处理（Re-RoPE）**：
  - 位置编码后的 K 只在原位置有效；KVMem 保存“位置无关的原始 K”作为唯一权威来源，V 可直接复用；
  - 当块被映射到新位置时，原始 K 重新在新位置应用 RoPE；
  - 已经驻留 GPU 的块可以通过“增量 re-RoPE”复用当前 K；但为限制低精度 GPU 副本上反复原位调整造成的数值误差，限制增量次数，超过阈值后从原始 K 重建。
- 三项关键优化：
  - **Proactive stage-out（主动换出）**：在 prefill chunk n 完成后，由后台异步把已完成块复制到主机内存，并继续持久化到 NVMe；后续工作集切换时，旧块已有副本可立即释放 GPU 页面，避免把 stage-out 放在关键路径。
  - **Retrieval-aware hierarchical reuse（感知检索的分层复用）**：分解连续两步骤的工作集差为 retained/incoming/outgoing；只加载真正不在 GPU 页面池中的块；高检索频率的块优先保留在主机内存，而非经常回落到 NVMe。
  - **Packed and pipelined rematerialization（打包与流水线化重物化）**：把大量碎片化小传输打包为连续 pinned-memory 缓冲区的批量 H2D 传输；GPU 端 scatter 到目标页并执行 re-RoPE；采用流水线重叠：CPU gather batch n+1、H2D 传输 batch n、GPU scatter + re-RoPE 前一 batch 并行执行。

### 2.3 执行流程（单步生命周期）

1. 新 agent 步骤的 chunked-prefill 执行期间，KVMem 在 GPU 上为已完成 KV 块计算 Mean-K 索引，并增量写入主机；
2. 当前步骤 prefill 完成后、decode 前，利用当前查询向量对全部历史块做基于 Mean-K 的检索与评分；
3. 选择有界且按时间顺序排列的历史块，组装成紧凑执行视图；
4. 执行视图通过页表映射到 GPU 页面，并完成批量 re-RoPE；
5. 对当前查询重新执行一遍 prefill（从 checkpoint 恢复），确保模型状态反映
