## 摘要
提示优化可以改进多智能体大语言模型系统，但被优化的提示往往承担着两个纠缠不清的角色：生成与任务相关的内容，以及指定底层代码所依赖的执行关键协议，如消息路由、输出格式和终止信号。因此，旨在改进内容生成的提示编辑可能会无意中破坏协议，导致整个智能体管道失败。我们的关键观察是，这两个角色具有不同的表示形式：执行协议通常是结构化的，而与任务相关的内容通常以非结构化语言表达。基于此，我们提出了控制-数据流分离，即将执行关键的控制表示为有类型的、经过验证的程序对象，而与任务相关的语言则保持为可优化的数据流，用于智能体通信。这种设计允许优化器改进多智能体行为，而不会将路由或格式化接口暴露给提示漂移。在合成推理、协作评审生成和保险评级工作流程中，我们的框架在经验上实现了100%的最终协议有效性，同时持续改进任务性能。

## Abstract
Prompt optimization can improve multi-agent LLM systems, but the prompts being optimized often serve two entangled roles: generating task-relevant content and specifying execution-critical protocols, such as message routing, output formatting, and termination signals, on which the underlying code relies. As a result, a prompt edit intended to improve content generation can inadvertently corrupt the protocol and cause the entire agent pipeline to fail. Our key observation is that these two roles have different representations: execution protocols are typically structured, while task-relevant content is usually expressed in unstructured language. Based on this, we propose control-data flow separation, where execution-critical control is represented as typed, validated program objects, while task-relevant language remains the optimizable data flow for agent communication. This design allows optimizers to improve multi-agent behavior without exposing the routing or formatting interface to prompt drift. Across synthetic reasoning, collaborative review generation, and insurance rating workflows, our framework empirically achieves 100% eventual protocol validity while consistently improving task performance.

- **研究背景**：多智能体大语言模型（Multi-agent LLM）系统（如 AutoGen、MetaGPT 等）依赖多个对话智能体协同完成复杂任务，每个智能体的行为由提示词定义。提示优化（如 TextGrad、DSPy、OPRO）可将提示视为可编辑参数，通过下游任务表现进行迭代优化。
- **核心问题（提示纠缠）**：在多智能体系统中，智能体提示词往往承担两种纠缠在一起的职能——

  2. **控制协议角色**：指定路由目标、输出格式、终止条件等执行协议，控制器需要依靠这些协定解析输出，从而推进流水线。
- **失效模式**：一个旨在提升内容质量的小幅编辑，可能在同时改变了输出结构指令的情况下，导致解析失败、路由到无效智能体、或整个系统崩溃——这类问题不是单纯的回答质量下降，而是整个执行轨迹的断裂。
- **论文的关键观察**：这两种角色具有天然的**表征差异**——执行协议是**结构化**的（离散动作、字段、字母值）；任务内容则是**非结构化**的语言。这一差异应当被明确利用，而不是混在一个文本输出字段中。

## 2. 方法论：控制-数据流分离（Control-Data Flow Separation）

- **核心思想**：将每个智能体输出显式划分为两个通道：
  - **控制通道（Control Channel）**：类型化、可验证的程序对象，包含路由指令、终止信号等执行关键信息。该通道由 schema 约束，运行时强制验证，对于提示优化器"不可编辑"（frozen）。
  - **数据通道（Data Channel）**：自由形式的自然语言消息，是智能体间传递的任务内容，也是**端到端提示优化**允许修改的唯一面。
- **两个通道的消费方式不同**：
  - 程序控制器（如 Python 路由函数）只读取*验证通过的控制对象*；
  - 后续智能体与提示优化器读取*数据流消息*。
- **Schema 与执行机制**：
  - 每个智能体绑定一个控制 schema（本论文中实现为 Python dataclass/Pydantic 对象，可选项用 `Literal[...]` 封闭）；
  - cdsep 库自动生成 schema scaffolding（提示模板），置于**冻结的提示槽**中，优化器无法修改；
  - 运行时解析 LLM 响应为 `(c_hat, m_hat)` 候选对，若控制对象解析失败/未通过校验，则触发有界重试或默认操作（controlled fallback）——**任何无效控制对象永远不会进入路由逻辑**。
- **优化约束**：优化器可以改变智能体*在协议中的策略*（何时停止、选择哪个路由对象），但不能改变*协议本身*（schema 字段、允许值、校验逻辑）。
- **正式保证（Lemma 1, Protocol Stability）**：若满足三个条件——(C1)：路由只接受类型化控制对象并返回 `Agent ∪ terminate`；(C2)：schema scaffolding 冻结在优化器不可访问的提示槽中；(C3)：解析/校验失败经有界重试或默认替代——则任何优化器选择的提示词都无法导致未处理的解析、校验或路由违规。
- **三个组件（对应消融实验）**：Schema 脚手架（C2）为基础保障；解析重试（C3）提供额外可靠性边际；逐示例反馈（per-example feedback）是质量提升的主要动力。

## 8. 局限与不足

- **稳定性 ≠ 语义正确性**：论文明确承认它保证的是“无效控制不会进入路由”，而非输出本身的语义正确性或事实准确性。
- **LLM-as-a-judge 固有局限**：MARG 评估依赖对齐型 LLM 评判，评判本身有位置偏差、自增强偏差等问题；虽然按跨条件保持一致来缓解，但绝对 Jaccard 分数与研究原论文不完全可比（用 gpt-5.4-mini 替代 GPT-4 作 judge）。
- **固定 schema 限制灵活性**：实现假设预先声明的角色与 schema；不支持动态智能体创建或运行时 schema 演化，无法覆盖需要动态拓扑结构的应用场景。
- **实验规模与统计力度有限**：某些更深入的比较使用较少的评估与训练数据（如 12–20 个案例）以及 3 seeds（或分析条件仅 1 seed）；MARG 数据子集规模较小，行业承保案例覆盖的 15 个桶中仅 12 个被填充。
- **产业数据的可追溯性**：行业伙伴数据经过"规范化"处理（如 free-text 金标模糊值被映射到 15 桶数组），虽然提高了可评估性，但规范化本身的正确性也被视作处理前提。
