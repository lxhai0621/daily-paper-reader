## 摘要
长时程大语言模型（LLM）智能体需要上下文组装：运行时必须在硬性上下文窗口预算和字节敏感的提示缓存约束下，决定每个提示中包含哪些内容、按什么顺序排列，以及何时压缩历史记录。在生产级智能体系统中，这一逻辑分散在提示构建器、临时压缩例程、缓存破坏解决方案和各提供商适配层中。我们认为，上下文组装在结构上与关系数据库中的查询执行同构：两者都在硬性预算下运行，利用分层缓存，并依赖统计信息。我们在ContextPipe中采纳了这一原则：一个五阶段流水线（计划-绑定-优化-执行-反馈），由结构化数据源目录、确定性缓存感知优化器和EXPLAIN ANALYZE跟踪支持。我们展示了ContextPipe中的上下文是可审计的、可重放的，并且具备故障隔离能力。使用SWE-bench Pro Qutebrowser子集的初步评估表明，与仅追加的上下文构建策略相比，ContextPipe将总token量减少了31%，LLM调用次数减少了23%，响应时间减少了9%，代价是KV缓存命中率较低。

## Abstract
Long-horizon large language model (LLM) agents require context assembly: the runtime must decide what to include in each prompt, in what order, and when to compact history under a hard context-window budget and a byte-sensitive prompt cache. In production agentic systems, this logic is scattered across prompt builders, ad hoc compaction routines, cache-break workarounds, and per-provider shims. We argue that context assembly is structurally isomorphic to query execution in a relational database: both execute under a hard budget, exploit a tiered cache, and leverage statistics. We adopt this discipline in ContextPipe: a five-phase pipeline (Plan Bind Optimize Execute Feedback) backed by a structured data-source catalog, a deterministic cache-aware optimizer, and an EXPLAIN ANALYZE trace. We show that context in ContextPipe is auditable, replayable, and failure-isolated. A preliminary evaluation using the SWE-bench Pro Qutebrowser subset shows that, compared with the append-only context construction policy, ContextPipe reduces total token volume by 31%, LLM calls by 23%, and response time by 9%, at the cost of a lower KV cache-hit ratio.

- **研究动机**：长时程 LLM 智能体（如自主编码 Agent）需要连续多轮调用大模型，每一轮都需要在**硬上下文窗口预算**与**字节级提示前缀缓存**（prompt cache）的约束下，决定将哪些上下文放入 prompt、按什么顺序组织、何时压缩历史。这个问题被论文称为"上下文组装"（context assembly）。
- **现有痛点**：生产级智能体系统中，上下文决策逻辑分散在 prompt builder、临时压缩例程、缓存兼容补丁、各家云厂商适配器等模块中，缺乏统一抽象。由此导致三种后果：
  - **不可解释**：无法回答"为什么选择这个 prompt 布局"；
  - **缓存易碎**：任何一处字节变化（如 schema 修改、header 切换）都会打破 KV 缓存前缀，导致整段前缀重算；
  - **无法审计与重放**：没有完整的决策日志。
- **核心论断**：上下文组装与关系数据库的查询执行**结构同构**——查询执行有硬内存预算、分层缓冲池、统计信息驱动的优化器；上下文组装同样有 token 预算、前缀缓存、历史统计和压缩策略。因此可以把数据库的整套系统性纪律迁移过来。
- **整体含义**：论文提出 ContextPipe，将每次 LLM 调用建模为一条五阶段流水线，以获得可审计、可重放、故障隔离的上下文组装能力。其目标不仅是降低成本，更是将 agent 运行时中最混乱的部分（prompt 拼装）变成可被工程化治理的子系统。

## 2. 方法论

### 2.1 核心思想

借鉴查询优化器的"声明式意图 + 目录 + 物理计划 + 统计反馈"范式：

- 用户输入视为声明式查询；
- ContextSources 目录扮演 systables/统计信息目录；
- 优化器在显式门控（limits）与压缩层级约束下生成物理布局；
- EXPLAIN ANALYZE 追踪承担审计职能。

### 2.2 五阶段流水线

每个 LLM turn 都经过同一条路径：

1. **Plan（纯函数）**：不进行任何 I/O，仅基于目录快照与统计信息计算：
   - 上下文压力（context pressure）与预留空间；
   - 选择压缩层级（tier）；
   - 各 section 的 token 预算与缓存策略（cache scope、cache markers）；
   - 生成 section manifest。
2. **Bind（唯一外部 I/O 阶段）**：并发获取记忆检索结果、历史消息、工具 schema、技能、emergent context 等，输出**类型化构件**（typed artifacts），而非裸字符串。
3. **Optimize（确定性变换）**：按缓存感知策略执行排序、压缩、清除、spill、缓存标记放置，生成可序列化请求与追踪。
4. **Execute（唯一调用模型的阶段）**：序列化并通过 provider adapter 发送，支持 EXPLAIN-only 模式（不实际调用模型）。
5. **Feedback（唯一写统计阶段）**：记录真实 token 用量、缓存命中/创建、截断事件与缓存破裂归因，供下一轮 Plan 使用。

### 2.3 关键公式

预测性上下文压力：

$$P_{raw} = \frac{T_{used}}{L_{eff}}, \quad P_{pred} = \frac{T_{used} + R_o + R_t + R_s}{L_{eff}}$$

- $L_{eff}$：模型有效输入上限（扣掉系统预留）；
- $R_o$：期望响应预留，取历史分位数（稳态 p75，恢复期 p95），而非平均值；
- $R_t$、$R_s$：扩展思考与工具 schema 增长的预留槽。

预留 $R_o$ 按 "(model, query source)" 分桶统计，避免不同任务分布的相互干扰。

### 2.4 分层压缩门控

由预测压力与原始压力共同选择更严格的一档阈值：

- $P < 0.60$：**Normal**（无压缩）；
- $0.60 \le P < 0.75$：**TrimSchemas**（剪除当轮不可能用到的工具 schema）；
- $0.75 \le P < 0.90$：**CompactHistory**（清除最旧的工具结果，替换为 provider 形状的占位符；超出阈值的对象做 spill）；
- $P \ge 0.90$：**AggressivePrune**（额外丢弃最早的多轮对话，且至少保留 4 轮以上才允许丢弃）。

门控单调性保证：预测压力只能升级 tier、不能降级；存在 `RecoveryState`（如最近一次 prompt-too-long）时强制继续升级。
