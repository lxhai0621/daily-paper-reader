## 摘要
随着 LLM 对话增长到数百轮，全上下文注入会产生 O(N^2) 的累计 token 成本，而有损摘要或硬截断会不可逆地丢弃历史状态。我们提出 Pull，一种会话路由器，它通过本地、确定性的 Purifier（零 LLM 调用，毫秒级延迟）维护可寻址的元数据目录。在查询时，LLM 仅惰性物化其所需的轮次；未物化的轮次仍可访问，但处于折叠状态。与不可逆压缩不同，Pull 的物化是可逆的；后续查询可以展开任何已折叠的轮次。在 LoCoEval（128 段对话，12,780 轮）上，Pull 将每次查询的上下文 token（第 2 阶段）在单跳任务上减少 75.1%，且质量相当（Δ= -0.002，不显著）；在多跳任务上减少 72.0%，且无质量损失（Δ= +0.017）。一项受控路由基准测试（7,831 次查询 × 10 种方法）表明，实体生命周期跟踪在经验上是距离无关路由的前提条件。在 BEAM 1M（14 段对话，263 个问题）上，Pull 相比截断基线将 F1 提高 +55.2%。

## Abstract
As LLM conversations grow to hundreds of turns, full-context injection incurs $O(N^2)$ cumulative token costs, while lossy summarization or hard truncation irreversibly discards historical state. We propose Pull, a session router that maintains an addressable metadata directory via a local, deterministic Purifier (zero LLM calls, millisecond-level latency). At query time, the LLM lazily materializes only the turns it needs; unmaterialized turns remain accessible but collapsed. Unlike irreversible compression, Pull's materialization is reversible; subsequent queries can expand any collapsed turn. On LoCoEval (128 conversations, 12,780 turns), Pull reduces per-query context tokens (Phase 2) by 75.1 percent on single-hop tasks with equivalent quality ($Δ= -0.002$, n.s.) and by 72.0 percent on multi-hop tasks with no quality loss ($Δ= +0.017$). A controlled routing benchmark (7,831 queries x 10 methods) shows that entity lifecycle tracking is empirically a prerequisite for distance-independent routing. On BEAM 1M (14 conversations, 263 questions), Pull improves F1 by +55.2 percent over a truncation baseline.

# 论文总结：Pull —— 面向有状态 LLM 对话的工作记忆惰性物化

## 1. 核心问题与整体含义

- **研究动机（成本—保真度两难）**：LLM 对话增长到数百轮时，主流 API 的"全上下文注入"使单次请求上下文长度线性增长（O(N)），整个会话生命周期的累计重传 token 成本呈**二次方增长（O(N²)）**。
- **实证证据**：对 287 个编程助手会话（59,520 条消息、56 亿计费 token）的分析显示，仅 2.8 亿 token 为原始内容，却计费 56 亿，**放大约 20 倍（≈19.9×）**；查询与历史的实体重叠中位数仅为 **20.7%**，即模型被迫在大量无关历史中搜索。
- **另一极端的问题**：有损摘要（LLMLingua、ICAE 等）或硬截断会**不可逆地丢弃历史细节**（变量定义、分支决策、废弃实现），因果链断裂。
- **关键判断**：作者认为"Lost in Conversation"现象可能并非源于 Transformer 注意力本身，而是源于**输入信噪比**过低。
- **缺失的架构层**：现有工作覆盖了"第一层（全上下文，管理当前查询）"和"第三层（长期记忆，管理跨会话历史）"，但**缺少第二层——实时会话状态路由器**。Pull 即用于填补这一空白。
- **整体含义**：论文将会话管理重新定义为**惰性物化（lazy materialization）**——维护活的元数据目录，LLM 主动"拉取"所需轮次，未物化轮次保持折叠但**可逆展开**，从而在不破坏状态的前提下降低 token 成本。

## 2. 方法论

### 2.1 核心思想
- 将流程解耦为两个在**时间与计算上完全分离**的阶段：
  - **阶段一（在线标注）**：每轮由本地确定性 **Purifier** 生成结构化元数据，**零 LLM 调用**。
  - **阶段二（查询时物化）**：每次查询仅 **2 次 LLM 调用**（Selector + Answerer）。
- 核心是**惰性 + 可逆**：不像压缩那样永久丢弃，未物化轮次仍可访问，后续查询可再展开。

### 2.2 形式化目标
- 给定对话 C=[t₁,…,t_N] 与查询 q，求子集 S ⊆ {1,…,N}：
  - **arg min_S TokenCount(prompt(q,S))**
  - **s.t. L(answer(q,S), answer(q,C)) ≤ ε**
- 由于 answer(q,C) 不可计算，实际用代理：**S = f_θ(q, M0, M10)**，f_θ 为 Selector。

### 2.3 三层存储（类比 OS 内存层级）
- **Active zone（0–300 轮）**：原文 + 元数据。
- **Frozen zone（300–800 轮）**：块摘要 + 元数据 + 归档指针。
- **External archive（800+ 轮）**：第三方存储（如向量库、Mem0、RAG）。

### 2.4 M0 / M10 分工
- **M0（Directory Layer）**：全局摘要目录，每轮约 100 字符的**抽取式**摘要；Answerer 始终读取完整 M0 以获得"位置感知"。
- **M10（Trace Layer）**：实体依赖图 + 生命周期标签 + 分支拓扑；Selector 只读 M10 做路由，无需读原文。

### 2.5 Purifier 关键技术细节（零 LLM）
- 每轮产出六字段元组：抽取式摘要、实体集合、信息密度、保真度分数、生命周期状态、分支 ID。
- **实体抽取**：16 条正则 → 归并为 **13 个类型族**（函数/类定义、snake_case/camelCase/反引号标识符、URL、时间/数值/命名实体等）；标识符有最小长度阈值。
- **生命周期状态机**：4 状态 Σ = {DEF, REF, MOD, DEP}，转移由实体位置与代码签名哈希**确定性**决定（DEF→REF/MOD/DEP）；MOD 与 DEP 互斥。
- **保真度评分**：9 个语用/词汇信号的手工加权和，d ∈ [0,2]（实体 +0.5、意图 +0.4、约束 +0.5、问句 +0.3、对齐 +0.2、关键词密度、字符熵、罕见词、结构化文本加分；短文本 ×0.5、模板化致谢 ×0.3 惩罚）；按阈值分为 KEEP / COMPRESS / FILTER。
- **本地运行开销**：MiniLM ONNX（约 46MB）+ 正则 + 规则；单机（Intel i5-9400F，6 核 2.90GHz，23.4GB RAM，Python 3.12.3）逐轮增量处理 800 轮：**P50 = 3.22 ms/轮，P99 = 32.5 ms**，会话状态内存线性增长至约 30MB。
- **淘汰与归档**：活跃轮 >300 时，按保真度、引用数、长度、近因加权淘汰，冻结为块摘要（50 轮/块）；查询时对相关轮次临时提升保留优先级。

### 2.6 Selector 查询时流程
1. 从 q 解析实体；
2. 在 M10 中匹配相关轮次；
3. 保真度检查；
4. **级联扩展（cascade）**：对 LLM 初始集合 S₀ 中引用到的每个实体，补入其最早定义轮；**仅一跳、无传递闭包、上限 +5 轮（|S| ≤ |S₀|+5）**，且为确定性后处理（非 LLM 决策）；
5. 校验输出（范围检查、去重）；
6. 解析失败时回退到实体匹配 + M0 相似度。
- 输入为**结构化纯文本**（每轮一行，字段含 turn_id、type tag、path、entities、生命周期标记、density、grade、pivot/branch、末尾约 100 字符摘要）；输出为一句理由 + 逗号分隔轮次列表。

### 2.7 Answerer
- 接收完整 M0 + S 中轮次的原文 + 查询 q，生成答案；M0 为抽取式，无 LLM 生成，保证事实一致性。

## 3. 实验设计

### 3.1 数据集 / 场景
- **LoCoEval**（主实验）：首个仓库级长时程对话上下文管理基准；128 样本（64 单跳 + 64 多跳），来自 71 个真实开源仓库，每段 60–138 轮（均值 100），阶段二上下文 35K–224K token；任务为 IE、TA、FC（FC 需 pytest 环境被排除），聚焦 IE+TA 共 256 实例。
- **BEAM 1M**：公开长对话记忆基准，35 段对话 / 700 问题；选取 **14 段对话（263 问题）**，每段 700K–1.8M token，超出 LLM 上下文上限。
- **受控路由基准**（自建）：60 条 SWE-bench 轨迹拼接为 12 个会话（140–1407 步），派生 **7,831 个探测问题**及确定性真值；三层难度：通用检索 53%、状态变更跟踪 22%、对抗性 25%。
- **可逆性探针**：16 个多跳样本。

### 3.2 对比方法
- 主实验：Vanilla（全上下文）、RAG-BM25、RAG-Dense、Random-K、Last-K。
- BEAM：BM25、Dense、Hybrid、Last-K 截断（含同预算 163K 变体）。
- 压缩对比：**LLMLingua2**（r50 与 r28）。
- 受控路由基准的 **10 种零 LLM 方法**：Oracle（上界）、M10-Entity、RAG+Entity、RAG+Timestamp、RAG-Hybrid（BM25+dense，RRF）、RAG-BM25、RAG-Dense、M0-BM25、M0-Keyword、Last-K（K=30）。
- 消融：w/o Cascade、w/o M0、Pure M0，以及五级结构化元数据消融（原始文本 → +Timestamp → +Entity → M10 lifecycle）。

### 3.3 评测设置
- 生成与评判模型：**GLM-5，temperature = 0.0**；独立评判模型：**Qwen3.7plus**（验证同模型评测偏差）。
- 指标：IE/TA 用 LLM-as-a-Judge 的 F1，FC 用 pytest pass@1；token 节省 = 1 − PT_Pull / PT_Full（仅阶段二）。
