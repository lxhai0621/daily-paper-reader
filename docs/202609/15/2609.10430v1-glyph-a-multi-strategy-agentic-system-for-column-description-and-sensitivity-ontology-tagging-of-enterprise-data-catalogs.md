## 摘要
企业数据湖积累表的速度快于人工数据管家记录或分类的速度，导致列缺少描述且治理标签未分配。这种文档债务会削弱数据发现、访问控制和监管合规。我们提出 Glyph，一个生产系统，它将两个耦合问题——列描述生成和用于数据分类的列类型标注——构建为协作的 LLM 智能体，并以有状态图进行编排。Descriptor 将生成过程基于产生每一列的流水线源代码，这些代码通过推理—行动工具循环（主动检索增强生成）按需从企业 GitHub 检索。Tagger 通过并行运行三种互补策略（描述标注器、业务线正则标注器，以及由在向量数据库上微调的对比编码器支持的元数据标注器），从受治理的 275 叶数据分类本体中分配标签，然后使用倒数排名融合（RRF）融合其排序输出。我们使用批内对比目标微调了一个 6 层 MiniLM 元数据编码器，相对于原始基础编码器，在分布内留出划分上将同标签检索从 NDCG@10 0.55 提升至 0.92（MAP@100 0.19→0.90）。我们报告在三个评估组上、以召回加权的 F2 目标衡量的端到端多标签标注质量，一项隔离每种策略和 RRF 融合的消融实验，以及使 Glyph 区别于先前列类型标注工作和商业值/正则敏感性扫描器的工程决策：无值且基于代码的设计、逐标签溯源，以及优雅降级。这些共同使多智能体 LLM 编目可作为生产服务进行审计和运营。

## Abstract
Enterprise data lakes accumulate tables faster than human stewards can document or classify them, leaving columns with missing descriptions and unassigned governance labels. This documentation debt undermines data discovery, access control, and regulatory compliance. We present Glyph, a production system that frames two coupled problems, column description generation and column type annotation for data classification, as cooperating LLM agents orchestrated as stateful graphs. The Descriptor grounds generation in the pipeline source code that produces each column, retrieved on demand from an enterprise GitHub via a reasoning--acting tool loop (active Retrieval-Augmented Generation). The Tagger assigns labels from a governed 275-leaf Data Classification Ontology by running three complementary strategies in parallel (a description tagger, a line-of-business regex tagger, and a metadata tagger backed by a fine-tuned contrastive encoder over a vector database), then fuses their ranked outputs with Reciprocal Rank Fusion (RRF). We fine-tune a 6-layer MiniLM metadata encoder with an in-batch contrastive objective, lifting same-tag retrieval on an in-distribution held-out split from NDCG@10 0.55 to 0.92 (MAP@100 $0.19 \rightarrow 0.90$) relative to the stock base encoder. We report end-to-end multi-label tagging quality under a recall-weighted F2 objective across three evaluation groups, an ablation isolating each strategy and the RRF fusion, and the engineering decisions that distinguish Glyph from prior column-type-annotation work and from commercial value/regex sensitivity scanners: value-free and code-grounded design, per-tag provenance, and graceful degradation. Together these make multi-agent LLM cataloging auditable and operable as a production service.

## 1. 核心问题与研究动机

- **背景**：现代企业数据湖中表的增长速度远超人工作业能力。论文给出的生产环境数据为：单一组织的目录覆盖 **约 340 万列、约 9.8 万张表**，横跨 **4 条业务线（LOB）** 与 **3 种存储后端**（Apache Iceberg、RDBMS、Cassandra 列族存储）。
- **文档债务（documentation debt）**：大量列缺少描述、缺少治理标签。按每分钟标注一列的乐观速率估算，仅该目录就需 **约 30 人年**的专家投入，且目录漂移速度快于任何团队的人工跟进速度。
- **后果**：数据发现困难、访问控制与隐私合规滞后；未记录的 PII 往往在事件发生后才被动发现，而非被主动识别。
- **两个耦合任务**：
  1. **列描述生成**（回答“这一列是什么意思”）；
  2. **列类型标注 CTA / 多标签敏感性分类**（回答“这一列属于哪类数据”）。
- **核心约束——隐私与合规**：Glyph 遵循“**不读单元格值**”的设计原则。很多最敏感的数据集在完成分类之前，读取其数据恰恰是治理所禁止的（鸡生蛋问题）。因此 Glyph 只使用**元数据与产生该列的源代码**作为信号。
- **与既有 CTA 工作的三点结构性差异**：
  - 目标不是开放域类型词表（DBpedia/Schema.org），而是**受治理的企业敏感性本体**（275 个叶标签，含敏感性等级），且类别严重偏斜（`NON_SENSITIVE` 约占 72%）；
  - **隐私保护设计**：编码器只看到结构键 `catalog.database.table.column`，Descriptor 只基于产出源码；
  - **异质策略排名融合 + LLM-as-Judge 自精炼 + 逐标签溯源**，每个标签都带有来源、分数与推理。

## 2. 方法论

### 2.1 整体架构
- Glyph 是一个**图结构的智能体应用**：每个智能体是若干节点（对类型化状态做纯函数）构成的有向图，节点间以普通边与条件边连接，基于 **LangGraph** 实现。
- 状态用 **Pydantic** 模型定义，逐跳校验；配置分三层（环境默认值 → 部署级 `AgentConfig` → 请求级 `HyperParams`）。
- 两个智能体是**可独立部署的 REST 服务**，但天然可组合（Descriptor 生成的描述是描述标注器的理想输入）。两者均以 **temperature 0.0** 解码以保证确定性。

### 2.2 Descriptor Agent（列描述智能体）
四阶段流水线：
1. **Schema 发现**：`fetch_schema` 查询企业数据注册表，获取列名、类型、已有描述等。
2. **源码接地生成（RAG）**：`analyze_batch` 是核心。整表列在**单次 LLM 调用**中分析，**每批最多 50 列**以控制延迟与成本。模型被赋予 **GitHub Enterprise 代码搜索工具**，可自主调用（**每列默认 3 次工具调用预算**，批级封顶后强制收尾），读取匹配上下文，将描述建立在**产出该列的应用代码**上。这是 **active RAG**（推理—行动循环）而非固定稠密检索器。另分配启发式置信度（依据长度、是否含技术与业务术语、是否定位到产出作业、PII 意识等信号，上限 1.0）。代码搜索有速率限制意识：60 秒窗口内 25 次调用后主动暂停 2 秒，并配指数退避（初值 30 秒、倍增、最多 5 次）。
3. **PII 标记**：一等目标，`user_id` 等列被显式加上 PII 警告；自动评分器直接对 PII 意识打分。
4. **数据集描述**：`generate_dataset_ description` 节点从列级结果合成表级业务用途摘要。

**评分与精炼**：`grade_results` 调用裁判模型，按 4 项标准打分——**合理性 0.35、具体性 0.25、完整性 0.25、PII 意识 0.15**；默认配置为**与生成器不同的模型族**（规避 LLM 裁判的自我增强偏差）。低于阈值的列带裁判反馈回到 `analyze_batch`，重试时对最差列重新检索 GitHub，**默认最多 2 轮**。

### 2.3 Tagger Agent（标签智能体）
三种策略并行运行，失效模式互不相关：

- **描述标注器（Description Tagger）**：检索受限式。对每列构造查询 `"{name}: {description}"`（无人工描述时仅用列名），从语义搜索中按余弦阈值 `C` 检索最相似的本体标注，再让 LLM 从中**选择并排序**标签并给出推理。因为候选被约束为真实本体条目且事后校验，**幻觉标签会被拒绝**。本体标注是丰富的自然语言记录，故此处直接使用通用 `all-MiniLM-L6-v2`（384 维）编码器。启用评分时，`evaluate_metrics` 节点以零成本确定性指标 + 批量 LLM-as-Judge 打分，低分列回到 `llm_desc_tagger`，构成有界的 Self-Refine 循环；**只有描述标注器经过此裁判**。
- **正则标注器（Regex Tagger）**：按业务线由领域专家定义的模式规则作用于列名（如 `email` → `EMAIL_ADDR`），提供 T2K 匹配谱系的高精度锚点。
- **元数据标注器（Metadata Tagger）**：仅使用结构元数据（全限定键），本身是一个 RAG 系统：用**微调后的句编码器**编码元数据键，在**精确内积（flat）向量索引**上检索已验证训练语料；向量做 L2 归一化使内积等于精确余弦相似度；相似度超过阈值 `S1` 的候选携带其最近历史邻居的标签。长嵌套类型在干净分隔符边界**截断到 200 字符**。随后 worker 将候选（含内联相似度归因）交给 LLM 选择并排序，每个选中标签带推理记录（如 `[sources: ann=0.92]`）。

**跨策略融合（RRF）**：三种策略产生分数尺度不可比的独立排名列表（ANN 余弦、LLM 置信度、二元规则命中）。`merge_all_tags` 采用**倒数排名融合**：

$$rrf(t) = \sum_{i \in \text{lists containing } t} \frac{1}{k + r_i}, \quad k = 60$$

并按理论最大值 $n_{active}/(k+1)$（即所有活跃源都排第 1 的得分）归一化，得到 $[0,1]$ 置信度，仅当**全体源一致排第一**时才等于 1.0。当多策略提名同一标签时，按固定优先级 `llm_desc_tagger > llm_metadata_tagger > regex_tagger` 决定继承哪一源的溯源字段，置信度取跨策略 RRF 分。融合列表按标注名去重、按名确定性破平排序。

**层级重评分**：`tag_normalizer` 将 RRF 置信度 $c$ 与本体层级权重 $w$ 混合：$\alpha c + (1-\alpha) w$；未分级与高敏感标注 $w=1.0$，低敏感层级（2/3/4 级）分别取 0.75、0.5、0.25。低于最小归一化分数的标签被丢弃并重排，使最终排序同时反映跨策略一致性与受治理的敏感性等级。

表 1 给出了一个 `country` 列（"The 2-letter ISO 3166-1 alpha-2 country code."）的算例：正则标注器投 `INTERNAL`，描述标注器投 `COUNTRY`，元数据标注器同时投 `COUNTRY` 与 `NON_SENSITIVE`（`COUNTRY` 排名更高），归一化 RRF 分数为 `INTERNAL` 0.333、`COUNTRY` 0.667、`NON_SENSITIVE` 0.328。

### 2.4 领域特定嵌入微调
- 动机：元数据键是**简短、缩写密集、非语言化**的，通用编码器无法理解 `uat.core_db.users.uid` 与 `prod.analytics.events.user_id` 是同一概念。微调前 MAP@100 仅约 0.19。
- 模型：**6 层 `all-MiniLM-L6-v2`**（BERT 蒸馏、384 隐藏单元、约 90 MB）。
- 训练数据：从生产系统抽取 `metadata_key → tags` 分配，按标签组构造 (anchor, positive) 对；因少数标签（尤其 `NON_SENSITIVE`，约 72%）占主导，**每标签配对上限定为 3000**，并要求最小分组规模，最终得到 **70,948 个平衡训练对**。
- 目标函数：**MultipleNegativesRankingLoss**（Henderson et al. 2017），scale 20，余弦相似度；批内其他正例充当负例，把同标签列拉近、异标签列推远。
- 评估：按标签随机 10% 的**列级**留出查询集，每标签贡献上限定为 500 个键（**9,242 条查询 vs 83,229 条语料**），用 IR 评估器计算 NDCG、MRR、MAP、Accuracy@k。
- 工程：编码器与向量索引带版本、按时间戳路径发布到 S3 兼容对象存储；索引从同一训练语料重建（嵌入时去掉标签后缀以避免训练/服务偏斜），容器冷启动时只读加载；因规模适中（$10^2$–$10^5$ 向量）使用精确内积索引，超过约 $10^6$ 需换量化或图索引。

## 3. 实验设计

### 3.1 数据集与评测集
- **端到端评测集**：由**数据管家按业务线联合编写**，每组为 `{列元数据, 期望标签}` 用例集合，跨多个 LOB，分为 **Group 1–3 三个组**。
- **表级隔离**：评测集与训练语料表级不重叠——**1,905 张评测表**均不在 **15,205 张表**的向量索引中（两者共用目录与数据库，但无任何评测列在训练或索引时出现过）。
