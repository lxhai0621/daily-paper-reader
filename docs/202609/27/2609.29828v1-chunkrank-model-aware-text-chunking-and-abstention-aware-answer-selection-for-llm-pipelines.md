## 摘要
我们提出 ChunkRank，一个开源 Python 库，它根据目标模型的分词器和上下文窗口推导分块边界，并在每个块独立生成的候选答案中选择答案。它附带一个经过验证的注册表，涵盖 15 家提供商的 90 个模型和六种答案选择方法，并且仅需三个核心依赖项。对于分块，ChunkRank 能根据模型名称自动避免上下文窗口溢出，而基于字符的切分器则会溢出或浪费预算；一项涵盖 11 种语言的保真度研究表明，为什么精确到 token 的预算在英语之外也很重要。在答案选择方面，我们报告了一个负面结果：在 NaturalQuestions、TriviaQA 和 HotpotQA 上，无论使用抽取式还是生成式阅读器，没有任何基于内容的排序器能够可靠地优于直接取第一个非空答案。原因在于阅读器会在缺少答案的块上弃权，而非答案位置。一个长上下文基线表明，在单跳问题上，分块与单次调用阅读效果相当，因此 ChunkRank 面向小窗口和超出窗口的设置。代码、注册表和评估框架已发布。

## Abstract
We present ChunkRank, an open-source Python library that derives chunk boundaries from a target model's tokenizer and context window, and selects an answer among candidates produced independently per chunk. It ships a validated registry of 90 models across 15 providers and six answer-selection methods, and needs only three core dependencies. For chunking, ChunkRank avoids context-window overflow automatically from the model name, whereas character-based splitters overflow or waste the budget, and a fidelity study across 11 languages shows why token-exact budgets matter beyond English. For answer selection we report a negative result: on NaturalQuestions, TriviaQA and HotpotQA, with extractive and generative readers, no content-based ranker reliably beats taking the first non-empty answer. The reason is reader abstention on chunks that lack the answer, not answer position. A long-context baseline shows that chunking matches single-call reading on single-hop questions, so ChunkRank targets small-window and beyond-window settings. Code, registry and evaluation harness are released.

# ChunkRank 论文总结

## 1. 核心问题与整体含义

- **背景动机**：所有部署的 LLM 都有固定的 token 输入预算。虽然上下文窗口从 GPT-3 的 2,048 token 增长到 Gemini 1.5 的 1M、Llama 4 Scout 的 10M，但法律合同、科研语料、代码库、多章节报告等文档仍普遍超出窗口，必须分块处理。
- **现有分块工具的缺陷**：
  - LangChain、LlamaIndex、Haystack、Chonkie 等把分块作为检索框架内部的工具，要求用户手动指定 chunk size，且**从不查询目标模型的分词器**。
  - 不同模型族分词方式差异巨大，同一 512 字符窗口在不同编码器下可能对应 100–400 token，导致静默截断或上下文浪费，且错误往往通过输出质量下降而非显式报错暴露。
  - 缺乏一个**独立、可安装、模型感知、带版本化注册表**的复用资源。
- **第二个被忽视的挑战——答案多重性**：对每个 chunk 独立提问时，LLM 可能给出不同答案，多数应用只返回第一个 chunk 的答案，这一选择既任意又经验上次优。RAG 系统虽排序检索段落，但把检索、索引、分块、生成耦合在一个单体框架内，非 RAG 流程无法直接采用。
- **论文定位**：ChunkRank 是一个填补上述资源空白的开源 Python 库——独立包（而非嵌入大框架的代码片段），带版本化模型注册表、稳定三级 API、公共测试套件与宽松许可证。

## 2. 方法论

### 2.1 核心思想

将流程组织为四个顺序组件：**模型注册表 → 分词器适配器 → 分块器 → 排序器**，各组件接口清晰、可独立替换或扩展。

### 2.2 模型注册表

- 每个条目含五个字段：`model name`、`max context`、`tokenizer backend`（hf 或 tiktoken）、`tokenizer id`、`default reserve`。
- 内置 **90 个模型、15 家提供商**（OpenAI、Anthropic、Google、Meta、Mistral、Microsoft、Alibaba、Cohere、DeepSeek、TII、EleutherAI、IBM、xAI、AllenAI、Hugging Face），上下文窗口从 512（BERT-base）到 10M（Llama 4 Scout）。
- 以纯 JSON 文件随包分发，可 diff、可用普通版本控制扩展；支持运行时 `register_model(...)` 一行注册，内存条目优先于静态 JSON。
- 模型缺失时回退默认：128k 上下文、tiktoken `o200k_base`、512 token reserve。
- **三重验证**：(i) schema 与一致性检查（90 条全部通过 `max_context > reserve > 0`）；(ii) 分词器解析（55 个 tiktoken 编码全部解析，35 个 HF 条目中 19 个可在标准环境加载）；(iii) 上下文窗口审计（对照 Anthropic 实时 Models API 及 27 个其他厂商公开规格，发现并修正两个过时窗口）。

### 2.3 分词器适配器

- 统一接口：`encode(text) → List[int]`、`count(text) → int`。
- 三种后端：
  - **tiktoken**：用于 OpenAI、Anthropic、Mistral、Cohere、DeepSeek、Qwen，进程内缓存。
  - **Hugging Face Transformers**：用于 Meta Llama 及编码器类模型（BERT、T5、Longformer、BigBird），启用 fast tokenization。
  - **字符比例回退**：`⌊|s|/4⌋`，无依赖但对非拉丁文字不准（可 opt-out，非默认）。
- 切换后端只需更新注册表，无需改动应用代码。

### 2.4 分块器

- 有效预算定义为 **B_M = W_M − R_M**（上下文窗口减去为 prompt 模板与生成预留的 token）。
- 硬约束：∀i，|T_M(c_i)| ≤ B_M；软目标：保持跨边界连贯性；用户可配置重叠 δ < B_M。
- **策略一：Token-Budget Sliding Window（默认）**
  - 不做句子边界检测，适合任意语言、无需额外依赖。
  - 内层循环在字符区间 [pos+1, end]（宽度至多 B·r）上**二分搜索**，每 chunk 收敛于 O(log B) 次分词器调用，比几何衰减方案更紧致可预测。
  - 重叠在字符空间按同一 4:1 比例施加，避免每 chunk 额外调用分词器。
- **策略二：Semantic Similarity（可选）**
  - 安装 `sentence-transformers` 后，先按句间余弦相似度分组再施加 token 预算，代价是一次性嵌入。

### 2.5 排序器（答案选择）

- 形式化目标：`a* = arg max S(q, a_i, i, s_i)`，在非空候选集 `A = {(a_i, i, s_i) : a_i ≠ ∅}` 上选取；空答案先被丢弃，所有方法在同一候选集上操作；等分时按文档顺序打破平局。
- 六种方法：
  1. **First non-empty（默认）**：取第一个非空答案，不做 query–answer 打分，无依赖，属"弃权感知"。
  2. **Reader confidence**：取调用方提供的最高置信度（抽取式 span 分数或生成式 log-prob）。
  3. **BM25**：标准 k1=1.5、b=0.75，完全确定性。
  4. **TF-IDF Cosine**：scikit-learn 向量化后余弦相似度。
  5. **Dense Embedding**：句级 transformer 向量余弦，捕获语义改写。
  6. **Cross-Encoder**：对 (q, a_i) 拼接对直接打分（默认 ms-marco-MiniLM-L-6-v2），更准但更慢。

### 2.6 实现与依赖哲学

- 核心系统仅 **3 个运行时依赖**：numpy（≥1.26）、scikit-learn（≥1.5）、rank-bm25（≥0.2.2）；PyTorch 永不是硬依赖，仅在选 `embedding`/`cross-encoder` 时导入。
- 三级 API：Function（一次性）、Pipeline（有状态、跨查询缓存配置）、Component（直接暴露 chunker/ranker）。
- 支持 `AsyncChunkRankPipeline`（`asyncio.to_thread()` 处理 CPU 工作）、`stream()`、`ChunkCache`（以 `(text, model, strategy, overlap)` 的 SHA-256 为键落盘）。
- 目标 Python 3.10–3.13，测试套件四版本全通过。

## 3. 实验设计

- **任务**：长文档单跳 QA——每个样本配一个超出 chunk 预算的文档，答案位于某一连续段落；候选答案由 QA 模型对每个 chunk 独立查询产生。
- **数据集**：
  - NaturalQuestions（NQ）与 TriviaQA：保留答案上下文超过 8,000 token 的样本，各 **500 例**。
  - HotpotQA（distractor）：拼接 10 个干扰段为单文档，答案段平均位置索引 4.6、仅 10% 位于首位，400 例，256-token 预算，仅用于检验位置偏差。
- **分块配置**：6,000-token 预算、64-token 重叠，NQ/TriviaQA 平均 3.5/4.0 chunks。
- **阅读器**：
  - 抽取式：`deepset/roberta-base-squad2`（512-token 窗口、stride 128，全 chunk 读取）。
  - 生成式：Claude Haiku 4.5，每数据集 100 例。
- **Benchmark 与对比方法**：
  - 分块正确性对比 **LangChain `RecursiveCharacterTextSplitter`**（naive/aggressive）、**Chonkie `TokenChunker`**（char 默认 / tiktoken 手动）与 ChunkRank（auto）。
  - 答案选择对比：First、Last、Random、BM25、TF-IDF、Embedding、Cross-Encoder、Reader-confidence，以及 **Oracle**（对 gold 取最高 F1 的上界）。
  - 长上下文基线：把整篇文档单次送入 Claude Haiku 4.5，与 chunked first-non-empty 对比。
- **指标**：Exact Match（EM）、token-level F1、95% bootstrap 置信区间、针对 first-non-empty 的**配对 bootstrap 检验**。
- **多语言保真度**：在 UDHR 第 1 条上测 11 种语言的字符/token 比与 len/4 估计误差。
