## 摘要
企业数据湖中表的累积速度快于人工数据管理员对其进行记录或分类的速度，导致许多列缺少描述且未分配治理标签。这种文档债务会削弱数据发现、访问控制和监管合规。我们提出 Glyph，一个生产系统，将两个耦合问题——列描述生成与用于数据分类的列类型标注——建模为由有状态图编排的协作式 LLM 智能体。Descriptor 将生成过程建立在产生每一列的流水线源代码之上，这些代码通过推理—行动工具循环（主动检索增强生成）按需从企业 GitHub 检索得到。Tagger 通过并行运行三种互补策略（描述标注器、业务线正则标注器，以及基于向量数据库、由微调对比编码器支持的元数据标注器），从受治理的、包含 275 个叶节点的数据分类本体中分配标签，然后使用倒数排名融合（RRF）融合其排序输出。我们使用批内对比目标微调了一个 6 层 MiniLM 元数据编码器，相对于原始基础编码器，在分布内留出集上将同标签检索的 NDCG@10 从 0.55 提升到 0.92（MAP@100 0.19→0.90）。我们报告了在三个评估组上以召回加权 F2 为目标的端到端多标签标注质量、隔离每种策略与 RRF 融合的消融实验，以及使 Glyph 区别于既往列类型标注工作和商业化的基于值/正则的敏感度扫描器的工程决策：无值且基于代码的设计、逐标签溯源，以及优雅降级。这些共同使多智能体 LLM 编目具备可审计性，并能作为生产服务运行。

## Abstract
Enterprise data lakes accumulate tables faster than human stewards can document or classify them, leaving columns with missing descriptions and unassigned governance labels. This documentation debt undermines data discovery, access control, and regulatory compliance. We present Glyph, a production system that frames two coupled problems, column description generation and column type annotation for data classification, as cooperating LLM agents orchestrated as stateful graphs. The Descriptor grounds generation in the pipeline source code that produces each column, retrieved on demand from an enterprise GitHub via a reasoning--acting tool loop (active Retrieval-Augmented Generation). The Tagger assigns labels from a governed 275-leaf Data Classification Ontology by running three complementary strategies in parallel (a description tagger, a line-of-business regex tagger, and a metadata tagger backed by a fine-tuned contrastive encoder over a vector database), then fuses their ranked outputs with Reciprocal Rank Fusion (RRF). We fine-tune a 6-layer MiniLM metadata encoder with an in-batch contrastive objective, lifting same-tag retrieval on an in-distribution held-out split from NDCG@10 0.55 to 0.92 (MAP@100 $0.19 \rightarrow 0.90$) relative to the stock base encoder. We report end-to-end multi-label tagging quality under a recall-weighted F2 objective across three evaluation groups, an ablation isolating each strategy and the RRF fusion, and the engineering decisions that distinguish Glyph from prior column-type-annotation work and from commercial value/regex sensitivity scanners: value-free and code-grounded design, per-tag provenance, and graceful degradation. Together these make multi-agent LLM cataloging auditable and operable as a production service.

- **核心约束与挑战**：

  - 类别极度不平衡：`NON_SENSITIVE` 约占 **72%**。
  - 隐私约束：许多敏感表在分类前禁止读取单元格值，因此 Glyph **从不读取 cell values**，只使用元数据和生产该列的源码。
  - 需要可审计、可生产运维，而非仅研究原型。

## 2. 方法论

### 2.1 总体架构

- Glyph 是由 **LangGraph** 编排的有状态图智能体系统，两个可独立部署的 REST 智能体：
  - **Descriptor**：生成列描述。
  - **Tagger**：分配敏感度/分类本体标签。
- 状态用 Pydantic 模型校验；配置分三层：环境默认、部署级 `AgentConfig`、请求级 `HyperParams`。
- 所有 LLM 解码温度为 **0.0**，强调确定性、可追踪、水平扩展和生产纪律。

### 2.2 Descriptor Agent

- **Schema Discovery**：从企业数据注册表拉取表结构、列名、类型、已有描述等。
- **源码接地生成（Active RAG）**：
  - 将整表列按 **每批最多 50 列**一次性交给 LLM。
  - LLM 可自主调用 **GitHub Enterprise 代码搜索**，默认每列最多 **3 次工具调用**。
  - 通过推理—行动循环检索生产该列的管道源码，用代码而非数据接地描述生成。
  - 代码搜索有速率限制保护：60 秒内 25 次后主动暂停 2 秒，并有指数退避。
- **PII 标记**：对如 `user_id` 等列显式加 PII 警告，评分时直接考察 PII 意识。
- **数据集描述**：从列级结果合成表级业务用途摘要。
- **LLM-as-Judge 自改进**：
  - Judge 按合理性、具体性、完整性、PII 意识四项评分，权重为 **0.35、0.25、0.25、0.15**。
  - 默认使用与生成器不同的模型家族，降低自增强偏差。
  - 低于阈值的列带反馈回到 `analyze_batch`，默认最多 **2 轮**。

### 2.3 Tagger Agent：三策略并行

- **描述标注器**：
  - 查询为 `"{name}: {description}"`，无描述时仅用列名。
  - 用通用 `all-MiniLM-L6-v2` 检索本体候选，LLM 在候选内选择并排序，避免幻觉标签。
  - 可经 LLM-as-Judge 和 Self-Refine 有限循环改进；只有该策略过 judge。
- **正则标注器**：
  - 由领域专家定义业务线特定模式规则，作用于列名。
  - 提供高精度锚点，但覆盖有限。
- **元数据标注器**：
  - 仅输入结构化元数据键 `catalog.database.table.column`。
  - 用微调后的句编码器编码，在 **精确内积 flat 向量索引**中检索历史人工验证标签。
  - 向量 L2 归一化，长类型截断至 **200 字符**；候选带相似度归因，再由 LLM 选择排序。
  - 每个标签记录来源、分数和推理，如 `[sources: ann=0.92]`。

### 2.4 元数据编码器微调

- 基础模型：**6 层 MiniLM**，384 维，约 **90 MB**。
- 训练数据：从生产系统抽取的 `metadata_key → tags` 已验证分配；同标签任意两列构成正对。
- 控制不平衡：每标签最多 **3,000 对**，要求最小群组规模，最终 **70,948 个平衡训练对**。
- 目标函数：**MultipleNegativesRanking Loss**，scale 20，余弦相似度；批内其他正例作为负例。
- 效果：同标签检索 NDCG@10 从 **0.5497 → 0.9225**，MAP@100 从 **0.1888 → 0.9009**。
