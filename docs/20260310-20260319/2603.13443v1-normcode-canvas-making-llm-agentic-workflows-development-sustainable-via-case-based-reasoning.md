我们展示了 NormCode Canvas (v1.1.3)，这是一个已部署的系统，它在两个层面上为多步大语言模型（LLM）工作流实现了基于案例的推理（Case-Based Reasoning）。其基础是 NormCode，一种半形式化的规划语言，其经过编译器验证的作用域规则确保了每个执行检查点都是一个真正自包含的案例，从而消除了标准编排框架中导致检索不可靠和故障无法定位的隐式共享状态。第一层将每个检查点

## Abstract
We present NormCode Canvas (v1.1.3), a deployed system realizing Case-Based Reasoning at two levels for multi-step LLM workflows. The foundation is NormCode, a semi-formal planning language whose compiler-verified scope rule ensures every execution checkpoint is a genuinely self-contained case -- eliminating the implicit shared state that makes retrieval unreliable and failure non-localizable in standard orchestration frameworks. Level 1 treats each checkpoint as a concrete case (suspended runtime); Fork implements retrieve-and-reuse, Value Override implements revision with automatic stale-boundary propagation. Level 2 treats each compiled plan as an abstract case; the compilation pipeline is itself a NormCode plan, enabling recursive case learning. Three structural properties follow: (C1) direct checkpoint inspection; (C2) pre-execution review via compiler-generated narrative; (C3) scope-bounded selective re-execution. Four deployed plans serve as structured evidence: PPT Generation produces presentation decks at ~40s per slide on commercial APIs; Code Assistant carries out multi-step software-engineering tasks spanning up to ten reasoning cycles; NC Compilations converts natural-language specifications into executable NormCode plans; and Canvas Assistant, when connected to an external AI code editor, automates plan debugging. Together these plans form a self-sustaining ecosystem in which plans produce, debug, and refine one another -- realizing cumulative case-based learning at system scale.

#### 1. 论文的核心问题与整体含义（研究动机和背景）
当前的大语言模型（LLM）多步工作流（如 LangChain、LangGraph 等框架）在开发和维护上面临**不可持续性**挑战。核心问题在于：
*   **隐式状态依赖**：中间步骤往往依赖于隐含的对话历史或全局变量，导致检查点（Checkpoint）不自包含。
*   **故障定位难**：当第 $k$ 步失败时，原因可能隐藏在之前的任何环节，难以回溯。
*   **复用与调试成本高**：缺乏一种既能让机器执行、又能让专家直观理解并局部修改的结构化表示。

本论文提出了 **NormCode Canvas**，旨在通过**基于案例的推理（CBR）**和一种名为 **NormCode** 的半形式化规划语言，使工作流的调试、恢复和改进变得结构化、可预测且可持续。

#### 2. 论文提出的方法论
核心思想是利用 **NormCode** 语言的“作用域规则”实现**结构隔离**，确保每个执行节点都是一个独立的“案例”。

*   **NormCode 语言特性**：
    *   **半形式化**：使用自然语言定义概念，但通过特定的符号（`<-` 赋值, `<=` 功能, `<*` 上下文）和缩进强制执行逻辑。
    *   **作用域规则**：编译器在执行前确定每个步骤的输入范围，禁止隐式共享状态。
*   **两级案例推理（Two-Level CBR）**：
    *   **Level 1（具体案例管理）**：将挂起的运行时视为案例。支持 **Fork**（从任意点分叉执行）和 **Value Override**（修改中间值并触发下游“过期”节点的选择性重执行）。
    *   **Level 2（抽象案例学习）**：将整个“计划（Plan）”视为案例。系统包含一个“编译计划”，能将自然语言需求自动转化为新的 NormCode 计划，实现递归进化。
*   **三大结构化能力**：
    *   **C1（直接检查点检查）**：无需重建上下文即可查看任一节点的精确输入输出。
    *   **C2（预执行审查）**：编译器生成自然语言叙述（.ncn），供专家在消耗 Token 前审核逻辑。
    *   **C3（有界选择性重执行）**：修改中间节点后，仅重新运行受影响的下游节点。

#### 6. 论文的主要结论与发现
*   **结构隔离是关键**：通过强制执行作用域规则，消除了 LLM 工作流中常见的“幻觉”和状态污染问题。
*   **两级 CBR 的协同**：Level 1 解决了运行时的调试问题，Level 2 实现了知识的沉淀与自动生成，二者结合形成了自维持的生态系统。
*   **效率提升**：通过选择性重执行（C3）和高比例的语法节点，显著降低了开发调试过程中的 Token 消耗和时间成本。

#### 7. 优点（亮点）
*   **创新的语言设计**：NormCode 兼顾了人类可读性（自然语言标识符）和机器严谨性（强制作用域）。
*   **确定性调试**：C1 能力允许开发者像调试传统代码一样精确检查 LLM 的中间状态。
*   **自我进化能力**：编译管道本身也是一个计划，这种递归设计为自动化 Agent 开发提供了新思路。
*   **语言无关性**：支持中文等多种语言编写计划，具有很强的普适性。

#### 8. 不足与局限
*   **检索依赖人工**：目前的案例检索和 Fork 目标选择仍主要依赖操作者的判断，缺乏自动化的相似度匹配算法。
*   **案例库膨胀**：随着运行次数增加，SQLite 数据库会无限增长，缺乏有效的案例剪枝（Pruning）机制。
*   **复杂逻辑限制**：对于极度复杂的领域逻辑（如 PPT 的双格式渲染），自动编译计划仍需人工干预或高级代码助手的辅助，无法完全自动化生成。
*   **外部资源依赖**：虽然检查点是自包含的，但如果案例涉及外部感知符号（如文件链接），复用时仍需保证外部资源的可用性。
