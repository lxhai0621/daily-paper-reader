Abstract 

As AI agents evolve from text generators into autonomous eco-nomic actors that accept jobs, manage budgets, and delegate to sub-agents, the absence of runtime governance becomes a critical gap. Existing frameworks orchestrate agent behavior but impose no fiscal constraints, require no earned permissions, and offer no tamper-evident audit trail. We introduce Sovereign-OS 1, a governance-first operating sys-tem that places every agent action under constitutional control. A declarative Charter (YAML) defines mission scope, fiscal bound-aries, and success criteria. A CEO (Strategist) decomposes goals into dependency-aware task DAGs; a CFO (Treasury) gates each expenditure against budget caps, daily burn limits, and profitability floors via an auction-based bidding engine; Workers operate under earned-autonomy permissions governed by a dynamic TrustScore; and an Auditor (ReviewEngine) verifies outputs against Charter KPIs, sealing each report with a SHA-256 proof hash. Across our evaluation suite, Sovereign-OS blocks 100% of fiscal violations (30 scenarios), achieves 94% correct permission gating (200 trust-escalation missions), and maintains zero integrity failures over 1,200+ audit reports. The system further integrates Stripe for real-world payment processing, closing the loop from task planning to revenue collection. Our live demonstration walks through three scenarios: loading distinct Charters to observe divergent agent behavior, triggering CFO fiscal denials under budget and profitability constraints, and escalating a new worker’s TrustScore from restricted to fully au-thorized with on-the-spot cryptographic audit verification.

1 Introduction 

AI agents no longer just generate text; they act as autonomous economic entities. ReAct [ 15 ] showed that LLMs can interleave reasoning with tool invocations, and modern frameworks such as LangChain [ 2], CrewAI [ 3 ], AutoGen [ 14 ], and MetaGPT [ 8]have made multi-agent orchestration widely accessible. However, orchestration is not governance: these frameworks provide no fiscal

constraints, no earned-permission models, and no verifiable audit mechanisms to hold agents accountable. 

Motivating Example. Consider an autonomous freelancer agent completing software bounties. Without governance: ( i) it over-spends on a $50 bounty by consuming $120 in API costs; ( ii ) it accepts a job with a $5 payout but $30 estimated cost; ( iii ) a new worker sub-agent immediately executes shell commands with no trust record. The framework faithfully orchestrates execution—but nothing enforces economic discipline or capability restrictions. 

Safety Gaps in Agent Governance. Existing safety work fo-cuses primarily on tool-call interception [ 7, 11 ] or output validation against declarative schemas. These systems address what an agent does but not how much it spends, whether it has earned the right to act, or whether its outputs actually satisfy mission objectives. Constitutional AI [ 1 ] introduced principle-driven self-alignment, yet it operates at training time rather than as runtime governance infrastructure. Recent work on budget-aware tool use [ 9] further shows that agents without explicit cost ceilings hit performance plateaus, motivating first-class fiscal controls. 

Our Proposal. We present Sovereign-OS , a governance-first op-erating system that treats agents as economic principals operating under a constitutional Charter and enforces fiscal discipline, earned-autonomy permissions, and verifiable audit at the infrastructure level. This paper makes four contributions: (1) Charter-driven governance. We introduce a YAML-based constitutional schema that declaratively defines mission scope, core competencies, fiscal boundaries, and measurable success KPIs. The entire system is domain-agnostic until a Charter is loaded. (2) Economic discipline pipeline. We design a CFO (Treasury) layer that gates every task expenditure against remaining bud-get, daily burn caps, and per-job profitability floors, with an auction-based worker selection mechanism scored by a utility function incorporating cost, confidence, priority, and trust. (3) Earned-autonomy permissions. We implement a TrustScore model (SovereignAuth) with asymmetric updates (+5 success, 

−15 failure) and tiered capability thresholds, requiring agents to demonstrate sustained trustworthy behavior before accessing dangerous capabilities. (4) Open system with verifiable audit. We release an open-source implementation with SHA-256 proof hashes on every audit report, an append-only ledger, and a web dashboard for real-time governance monitoring.

2.1 Charter: Constitutional Governance 

The Charter is a Pydantic-validated YAML document that serves as the single source of truth for an entity’s identity and oper-ational scope. It declares four sections: ( i) mission —a natural-language statement of purpose; ( ii ) core_competencies —named capabilities with priority weights (1–10); ( iii ) fiscal_boundaries —daily burn cap ( daily_burn_max_usd ), total budget ceiling ( max _budget_usd ), currency, and minimum job margin ratio (default 0.35); and ( iv ) success_kpis —measurable criteria with verifica-tion_prompt fields consumed by the Auditor. The schema uses Pydantic’s extra="forbid" and strict=True to reject undefined fields, ensuring Charter integrity at load time (Listing 1, Appen-dix A). 

2.2 CEO: Goal Decomposition via Strategist 

The Strategist receives a natural-language goal and the Charter’s competency list, then produces a TaskPlan : a DAG of Planned-Task items, each with a task_id , description, dependency list, 

required_skill mapped to a Charter competency, estimated _token_budget , and priority (high/low). An LLM generates the plan as structured JSON; a normalization pass assigns unique IDs (e.g., task-1-spec_writer ) and remaps dependencies. When no LLM is configured, the Strategist falls back to keyword-based single-task plans with a default 4,000-token budget. 

2.3 CFO: Fiscal Gatekeeping via Treasury 

The Treasury enforces three fiscal checks before any task executes: (1) Balance check. Estimated cost must not reduce the ledger bal-ance below the minimum reserve: balance −cost ≥ min_reserve .(2) Daily burn cap. Cumulative daily spend plus the new cost must not exceed daily_burn_max_usd from the Charter. (3) Job profitability. If job revenue is specified, the Treasury re-jects when cost > revenue × ( 1 − min_margin ), where the default margin floor is 0.35. Violations raise FiscalInsolvencyError or UnprofitableJob-Error , halting the pipeline before any tokens are consumed.

2.4 TrustScore and SovereignAuth 

SovereignAuth implements a dynamic earned-autonomy permis-sion system. Each agent starts with a base TrustScore of 50 (on a 0–100 scale) and must earn access to progressively dangerous capabilities. Table 1 lists the five capability tiers. 

Table 1: Capability thresholds. Agents must reach the listed TrustScore before the capability is granted.             

> Capability Threshold Example Actions
> READ_FILES 10 Read documents, configs
> WRITE_FILES 40 Create/modify files
> CALL_EXTERNAL_API 50 HTTP requests, webhooks
> EXECUTE_SHELL 60 Run shell commands
> SPEND_USD 80 Charge via Stripe

TrustScore updates are asymmetric: each audit success adds +5 (capped at 100), each failure subtracts −15 (floored at 0), and bud-get overruns subtract −10. This design means an agent starting at score 50 can read and write files immediately but requires 2 con-secutive audit successes to unlock shell access (50 →55 →60) and 6 to unlock spending (50 →80). A single audit failure from score 50 drops the agent to 35, revoking write-file access. Permission checks raise PermissionDeniedError with the agent’s current score and the required threshold, providing transparent feedback. 

2.5 Auditor: ReviewEngine and Audit Trail 

The ReviewEngine evaluates task outputs against Charter KPIs. A Judge LLM (default: GPT-4o) scores each output on a 0–1 scale against the KPI’s verification_prompt ; scores ≥ 0.50 pass. Each 

AuditReport contains task_id , kpi_name , passed , score , rea-son , suggested_fix , and timestamp_utc .

Proof Hash. Every AuditReport includes a computed proof_hash :a SHA-256 digest of the canonical JSON representation (sorted keys, UTF-8 encoded) of all report fields. This provides tamper-evident integrity—modifying any field invalidates the hash. The audit trail is stored as append-only JSONL, and verify_report_integrity() 

recomputes the hash from stored fields to detect post-hoc modifica-tion (Listing 5, Appendix A). 

Feedback Loop. Audit results feed directly into TrustScore: record _audit_success() adds +5, while record_audit_failure() sub-tracts −15. On failure, the ReviewEngine persists a Reflection-Object to memory so that the agent can avoid repeating the same mistakes in subsequent attempts. 

3 Evaluation 

We evaluate Sovereign-OS along three axes: fiscal governance coverage, TrustScore permission accuracy, and audit trail integrity. 

3.1 Axis 1: Fiscal Governance 

We construct 30 scenarios across 5 fiscal violation categories: insuffi-cient balance, daily burn cap violations, unprofitable job acceptance (margin below 35%), minimum reserve depletion, and aggregate budget ceiling breaches. Each scenario configures a Charter with specific fiscal_boundaries and submits a task or job that should be rejected. Sovereign-OS achieves a 100% block rate: all 30 sce-narios raise the appropriate exception ( FiscalInsolvencyError 

or UnprofitableJobError ) before any tokens are consumed. 

3.2 Axis 2: TrustScore Permission Gating 

We run 200 missions across agents with varied behavioral profiles— consistently successful, mixed, and frequently failing—and evaluate whether SovereignAuth correctly grants or denies capabilities at each decision point. Sovereign-OS achieves 94% correct permission gating. The 6% error cases arise at threshold boundaries where an agent’s score is exactly equal to a capability threshold and the pending audit result has not yet been recorded. In practice, these boundary cases resolve within one audit cycle. 

3.3 Axis 3: Audit Trail Integrity 

Over 1,200 AuditReports generated across all evaluation missions, we verify cryptographic integrity by recomputing proof_hash 

from stored fields via verify_report_integrity() . All 1,200+ reports pass verification with zero hash mismatches and zero colli-sions, confirming the tamper-evident property of the audit trail. 

Limitations. The fiscal evaluation uses synthetic scenarios rather than production workloads. The TrustScore model uses fixed deltas (+5/ −15) that may not generalize across all deployment contexts. The Judge LLM (GPT-4o) introduces an external dependency whose behavior may vary across model versions.

6 Related Work 

Agent Orchestration Frameworks. LangChain [ 2], CrewAI [ 3], Au-toGen [ 14 ], and MetaGPT [ 8] provide multi-agent orchestration— role assignment, tool integration, and workflow management. How-ever, none enforce fiscal constraints, earned permissions, or con-stitutional governance. Sovereign-OS provides these governance primitives as infrastructure rather than application-level concerns. 

Agent Safety and Constitutional Governance. Guardrails AI [ 7]validates LLM outputs against declarative schemas, and NeMo Guardrails [ 11 ] enforces conversational rails via programmable dialog flows. Constitutional AI [ 1] embeds principles at training

Economic Governance and Mechanism Design. Fetch.ai [ 5] and SingularityNET [ 6] enable agent-to-agent economic transactions on blockchain networks, and DAO governance [ 13 ] automates or-ganizational rules via smart contracts. These systems focus on inter-agent marketplaces; Sovereign-OS provides intra -agent fis-cal discipline. Our auction-based worker selection draws on algo-rithmic mechanism design [ 10 ], while Liu et al. [ 9] independently confirm that explicit cost ceilings improve agent efficiency. 

Access Control and Audit Integrity. Sovereign-OS ’s TrustScore extends classical RBAC [ 12 ] by making permission assignment dy-namic and earned through audited behavior rather than statically assigned. Our tamper-evident audit trail builds on hash-chain log-ging techniques [ 4], applying SHA-256 proof hashes to individual audit reports.

7 Conclusion and Future Directions 

We presented Sovereign-OS , a governance-first operating system that treats autonomous AI agents as economic principals operating under a constitutional Charter. Its five-layer pipeline—Charter, CEO, CFO, Workers with SovereignAuth, and Auditor—ensures that ev-ery action is constitutionally scoped, fiscally approved, permission-gated, and cryptographically audited. The current implementation achieves 100% fiscal violation blocking, 94% correct permission gat-ing, and zero audit integrity failures across our evaluation suite. All enforcement logic is Charter-driven and domain-agnostic: swap-ping the YAML document transforms a content agency into a re-search lab without code changes. 

Future directions. (i) On-chain ledger notarization for third-party auditability; ( ii ) multi-agent federations with inter-Charter agree-ments and cross-entity fiscal policies; ( iii ) adaptive trust models replacing fixed deltas with learned update functions based on task complexity; ( iv ) longitudinal deployment studies measuring eco-nomic efficiency and operator trust calibration with production workloads.
